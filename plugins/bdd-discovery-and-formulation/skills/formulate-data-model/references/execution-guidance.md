# data model BDD formulation 実行指示書

## 背景と目的

この入口は、既存のBDD付きRDB論理設計を対応する業務知識と突き合わせて永続化の業務判断から反証し、確認済みの発見を同じ論理資料へ戻してから物理設計へ進む。論理構造を物理都合で作り替えない。

## 前提

- 既存論理資料に対応する業務知識資料は必須である。無い場合は既存テーブルだけから業務上の正本を推測せず、変更しない。
- イベント列、現在状態、有効期間履歴、派生の選択を業務知識から再評価する。業務イベントの名前や件数だけでイベント列を採らない。
- 既存のBDDとtable構造の対応を説明できることが開始条件である。
- 論理設計の深化と、Read、型、index、分離レベル、配置の物理設計を分ける。
- 確認できない問いに依存するBDDや論理構造は、仮説と分かる形で更新し、確定事項と区別する。
- 対象RDBの製品と版、論理モデリングの手法は入力で受け取る。既定を持たず、決め方を報告する。

## 各工程を実行するときの指示

### challenge-persistence（grill）

`context`には`purpose`（既存の論理設計を反証して同じ資料へ戻し、対象RDBの物理設計へ写す）、`audience`（業務責任者、開発者、DB設計者）、`boundary`（API、DTO、ORM、画面、サービス分割は扱わない）を渡し、題材固有の問いは`questions`で渡す。各問いは既存論理資料のどの永続化上の主張を反証しているかを示し、既存資料と業務の筋から最も筋の良い答えを推奨として添える。Readやindexを論理設計の問いへ混ぜない。

#### 問いの選び方

同梱の内部skill `write-bdd`の重要なシナリオを見つけるQA観点で反例を当て、残った論点を次の3段に分ける。**問うのは第1段と、grillの上限に枠が残れば第2段から**である。第3段は問わず、推奨を仮置きした未決として資料へ載せる。問う数の上限と対話の作法はgrillの公開契約に従う。

| 段 | 論点の性質 | 例 | 扱い |
|---|---|---|---|
| 第1段: 残す事実と業務制約 | 答えで残す事実、履歴の有無、業務制約、または物理設計の前提（製品と版）が変わる。論理テーブルの集合や物理設計の可否が変わる | 「同じ対象へ二人が同時に行ったとき、許してはいけない結果は何か」「規則が変わったとき進行中の対象の記録へ遡及するか」「失敗したとき何を失ってはならないか（残す事実）」「対象RDBの製品と、一つに定めた版は何か」 | 必ず問う |
| 第2段: 境界と履歴の中身 | 答えで新しいBDDの条件・結果や列の値域が決まるが、テーブルの集合は変わらない | 「境界値ちょうど（期限、上限）で残す事実は変わるか」「順序が逆転したとき（取消後の確定など）どの事実を積むか」「重複した出来事は一件に畳むか両方残すか」「保持理由が尽きる条件はあるか」 | 枠が残る分だけ問う。残りは推奨を仮置きし、該当BDDと要素に仮説と明示する |
| 第3段: 値と物理の詳細 | 答えで例の値、想定件数、SLOしか変わらない。または既存資料と対象版の公式資料で確認できる | 「代表的なReadの想定件数はいくらか」「精度と単位の丸めはどちらか」「保存先はどこか（既存構成から提案できる）」 | 問わない。既存資料の値と業務の筋から仮説の値を置き、未決に推奨を書く。保存先は既存構成が読めなければ第1段へ繰り上げる |

同じ段の中では、答えが変えるBDDとテーブルの数が多いものを先に選ぶ。既存資料と対象版の公式資料で確認できることは問わず、根拠として`context`に含める。

### deepen-scenarios と revise-logical-model（論理設計の深化）

確認済みの発見をBDD、table、column、business constraintへ対応づける。仮説に依存するBDDと要素は仮説であることと根拠をその箇所に明示し、未決の節へ推奨・根拠・採らなかった解釈を並べる。BeforeとAfterで全tableを同じ順序に全カラム見出し付きの表として置き、0件の表も変化しない表も省略しない（`write-doc`の`rdb-logical-data-modeling`型の記法に従う）。更新先は入力論理資料と同じパスにする。

### design-physical（物理設計）

更新済み論理構造を固定したまま、典型的なRead、対象RDBの機能根拠（各`### 機能:`節の利用可能な版と根拠の欄）、型、制約、index、分離レベル、配置を決める。論理BDDを物理資料へ複製しない。想定件数やSLOのような入力に無い値は業務の筋から仮説として置き、`## 未決`へ測定で確かめる事項として並べる。冒頭の段落は、どの論理設計をどの製品と版でどう実現するかを読み手の既知の語で文章として運ぶ。

### update-logical-document / document-physical（write-doc）

論理資料は`document_type: rdb-logical-data-modeling`と`update_target`で同じpathを差し替え、物理資料は`document_type: rdb-physical-design`と`output_directory` / `name`で新規に1本保存する。呼び方は同梱の内部skill `write-bdd`の入れ子の段取りを呼ぶ規律に従う。
