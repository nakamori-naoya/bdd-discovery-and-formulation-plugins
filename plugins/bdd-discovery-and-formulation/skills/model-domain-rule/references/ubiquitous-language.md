# ユビキタス言語と英名

ユビキタス言語は、業務の人の言葉を出発点に、業務の人と作り手が同じ判断をできるところまで育てた言葉である。単語を集めた用語集でも、社内語をそのまま正解にしたものでもない。

## 言葉は使われ方で意味が決まる

「予約」の意味は、一行の定義では決まらない。何を予約できるか、いつ成立するか、誰にどんな約束が生まれるか、期限を過ぎると何ができなくなるかを語る中で意味が現れる。だから語を確かめるときは、定義だけを聞かず、その語を使って典型の例、成立しない例、境界ぎりぎりの例を説明してもらう。何を同じものとして数え、何が違えば別の扱いになるかが分かれば、語の意味が決まる。

現場で使われているだけでは足りない。同じ語を部署ごとに違う意味で使っていることも、略語が別の状態を隠していることもある。具体例でずれを見つけたら、名前を分け、関係を言い直し、業務の人自身が判断に使える言葉へ整える。

## 業務の言葉と、実現の言葉を分ける

ユビキタス言語に属する語は、ソフトウェアを全部置き換えても業務の概念として残り、業務の人がその語で例の正誤を判断できる。`ReservationDto`、`POST /reservations`、`status_code = 409`、テーブル名、キュー名は、実現方法を説明する言葉である。「409を返す」を「配送開始後の変更を理由つきで拒否する」と言い換えたとき、初めて業務の判断が見える。

境界は語の見た目では決まらない。「ステータス」でも、業務の人が状態の区分として使い、各状態でできる行いと責任を説明できるなら業務の語になりうる。逆に「顧客」のように業務らしい語でも、契約者、利用者、支払者をまとめて判断を狂わせるなら、そのままでは使えない。合意した語が無ければ新しい語を作らず、入力にある語を仮に置いて、業務の人へ問いとして戻す。

同じ語でも、判断のまとまりが違えば意味が変わることがある。販売の「商品」と倉庫の「商品」を一つに統一せず、それぞれ何を判断するための語かを確かめ、境界を越えるときに何を対応づけるかを決める。

## 英名も、業務の言葉から付ける

コードでは、概念、業務の行い、業務イベントに英名が要る。英名を実装する人がその場で考えると、同じ概念に別の名前が付いたり、データの形から名前が付いたりする。二つの値を束ねただけの型に「組」、二つの概念のつながりに「関係」、保存する行に「データ」や「記録」と名付けるのがその例で、業務の人が読んでも何の判断に使うものかが分からない。

そこで英名もユビキタス言語の一部として、domain-rule資料のユビキタス言語の表に持たせる。業務の言葉ごとに英名を一つ決め、業務の言葉を英語へ置き換えた名前にする。業務イベントの英名は、成立した事実として過去形にする（例：`LoanLent`）。業務の言葉で表せず技術の言葉でしか表せないもの（識別子を採番する仕組み、時計）だけは、技術の言葉で名付けてよい。判断の基準は「業務の人が読んで、何を指すかが分かる名前か」である。

ドメインモデルと実装は、この英名をそのまま使う。英名の無い概念が後から要るようになったら、その場で名前を作らず、業務の言葉と英名の候補をdomain-rule資料への提案として戻す。

## 言葉は完成しない

新しい事例でこれまでの名前が判断を説明できなくなったら、過去の用語集を守らず、会話、資料、コードを一緒に直す。
