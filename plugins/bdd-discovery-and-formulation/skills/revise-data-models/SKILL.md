# 複数の論理データモデルを業務知識から横断改訂する

読み終えると、各論理資料に対応する業務知識を読み取り専用の正本として先に読み、ドメインごとに現在状態・有効期間履歴・イベント列のどれを正本にするかを選び、複数資料で矛盾する分類、時刻、取消・訂正、技術イベントの扱いを一度に直して同じpathへ保存できる。業務イベントの存在だけを理由にイベント表を作らない。業務知識への永続化方式の追記、物理設計、移行、性能、API、DTO、ORMは扱わない。

同じdirectoryの`playbook.yml`が工程順の正本である。[実行指示書](references/execution-guidance.md)を読み、手順に入る前に同梱の内部skill `write-bdd`と`design-data-model`の`SKILL.md`を読み、入力の根拠づけ、業務の言葉、永続化理由、イミュータブルデータモデリング、NULL回避、関係データモデリングの判断規律を全工程へ適用する。

## 入力

| 入力 | 内容 | 満たさないときの扱い |
|---|---|---|
| `user_input` | 横断改訂の目的と追加の設計指示 | 対象と目的を読めなければ止まる |
| `targets` | 1件以上の`{logical_document_path, business_knowledge_paths}`。論理資料と業務知識は対象repositoryに追跡済みの通常fileの絶対path | 最初の事前条件検査で一件でも欠ければ、全資料を変更せず止まる |

論理資料と業務知識の対応は利用者が指定する。directory名や近いファイル名から推測しない。業務知識が存在しない領域は、テーブル設計ではなく`discover-domain`で業務知識を作る対象として返す。

`business_knowledge_paths`は設計判断の入力であり、この入口の更新対象ではない。業務知識に永続化、テーブル、イベント記録、正本方式などのデータモデル関心を追記しない。業務知識の意味が利用者の説明や別の正本と矛盾する場合は、業務上の対象・出来事・後の問いとして何が矛盾するかを返し、業務知識の更新はdomain discovery / formulationの独立した仕事として扱う。

## 判断基準

| 観察対象 | 述語 | 行動 |
|---|---|---|
| 業務知識のシナリオ | 正常系、または一意性・参照整合・値域・原子性・冪等性・競合順序・履歴・読み取り投影が結論を左右する | 業務知識の掲載順でデータモデルBDDへ対応付ける |
| 業務知識の拒否シナリオ | 認可、未対応操作、永続化前の入力受付だけで結論が決まり、論理制約、トランザクション、履歴、読み取り投影のどれも結果を左右しない | データモデルBDDから外し、業務知識を正本として対応表へ対象外理由を残す。全テーブルが変更されないことだけを採用理由にしない |
| 業務知識 | 業務上の対象、状態、業務イベント、規則、後の問いを読める | 正本選択へ進む。対応資料自体が無ければ設計せず止まる |
| 業務イベント | 複数あり、その順序・取消・訂正・判断根拠を後から説明できないと業務が困る | イミュータブルなイベント列を正本候補にする。件数だけでは選ばない |
| 業務イベント | 存在しても、過去の経過が後の判断・説明・権利・義務に使われない | 現在状態を正本候補にし、保存理由のないevent recordを置かない |
| 設定や契約条件 | 名前のある業務イベントは乏しいが、過去時点の値が後の判断を変える | 有効期間履歴を正本候補にする |
| 設定や現在値 | 過去の変更が後の業務判断に影響しない | 更新可能な現在状態を正本候補にする |
| 一度成立した業務上の事実 | event recordとして残す理由がある | イベント系にし、更新・削除せず、取消・訂正も元の事実を参照する追加イベントにする |
| イベント列と現在リソース | 同じ対象のイベントを現在リソースへ反映し、現在リソースをオンライン判断に使う | リソースへ`current_version`を持たせ、対象内で最後に反映済みのイベントversionと一致させる。直近イベントIDやイベント発生時刻は別の業務上の問いに必要な場合だけ重複して持つ |
| 再試行、Outbox、キャッシュ同期、ワーカー回収 | 業務の人が判断・権利・義務を変えた事実ではない | 技術イベントまたは技術リソースに分け、業務イベントへ混ぜない |
| 全論理テーブル | リソース系かイベント系、業務・技術・派生、正本、時刻、変化、根拠を一意に説明できる | 分類表へ一度だけ載せる。リソース成立時刻は`created_at`、イベント成立時刻は`occurred_at`にする |
| 状態列・完了日時・削除フラグ・条件付きNULL | 成立時点の異なる事実、種類差、未成立を一行へ押し込めている | 関係またはイベントを分ける。現在状態として業務上必要なら理由を添えて残す。列名だけではこの述語を真と判定しない |

## 手順

1. **preflight-domain-knowledge。** 対象repository rootをcurrent directoryにし、`targets`をJSON objectのまま標準入力から`python3 scripts/domain_input.py check`へ渡す。終了code 0は正規化済みtarget、1は不足または不正pathの診断、2は入力を読めない状態である。0以外なら一つも変更せず止まる。
2. **analyze-domains。** targetごとに業務知識を読み、業務上の対象、現在状態、業務イベント、後で答える問い、履歴を失う損失を対応付ける。業務シナリオは資料上の順序で全件を棚卸しし、正常系か、永続化保証が結果を左右するかでデータモデルBDDへの採否を決める。採用しない拒否は業務知識だけに残す理由を保持する。現在状態・有効期間履歴・イベント列・派生のうち正本を選び、選ばなかった候補と理由も保持する。業務イベント数は候補を見つける材料であり、採否条件にはしない。業務知識と利用者入力が矛盾するときは、永続化方式を業務知識へ書き込まず、業務意味の矛盾として報告対象へ分ける。
3. **revise-models。** 全targetを同じ文脈で読み、共有概念、同じテーブル、上流・下流の参照を突き合わせる。各資料の分類表を`系列 / 性質 / 論理テーブル / 正本 / 時刻 / 変化 / 根拠`の7列に揃え、論理テーブル定義、ライフサイクル、BDDを同じ判断へ改訂する。採用した業務由来BDDを業務知識の掲載順で先に置き、永続化固有BDDを後へ置く。各BDDは固定した識別子、値、時刻、順序、失敗位置と一つのWhenを持ち、Before/Afterの両側へ全論理テーブルを同じ順序・全カラム見出しで載せる。イベント列と同じ対象の現在リソースには`current_version`を置き、対応する最後のイベントversionとの一致を制約にする。一つの変更が他の論理資料の前提を変える場合は同じ実行で直すが、`business_knowledge_paths`は変更しない。
4. **validate-models。** 改訂本文を`{"documents":[{"path":"<絶対path>","content":"<Markdown>"}]}`として標準入力から`python3 scripts/immutable_model.py check`へ渡す。終了code 0は分類表と論理テーブル定義の構造契約を満たす、1は各違反の`path / detail / howto`、2は入力を読めない状態である。0以外なら保存せず`revise-models`へ戻る。状態列、完了日時、削除フラグ、条件付きNULLの妥当性はこのtoolへ判定させず、業務知識を読んで意味評価する。
5. **update-models。** 検査を通した全文だけを、各`logical_document_path`と同じpathへ保存する。一部だけ保存できた場合は成功扱いにせず、変更済みpathと未変更pathを分けて返す。
6. **report。** targetごとの正本選択と根拠、イベント列を採用・不採用にした理由、業務イベントと技術イベントを分けた箇所、変更した絶対path、検査結果、意味評価として残る未決を報告する。

## 停止条件

**止まる。** 次の場合は全資料を変更せず、確定した範囲、欠けた入力、必要な業務知識、再開条件を返す。

- `targets`が無い、空、形式違反、相対path、symlink、存在しないfile、同じ論理資料の重複を含む
- 一つでも論理資料に対応する業務知識fileが指定されていない、または読めない
- 業務知識を読んでも対象業務を識別できず、設計すると別ドメインの事実を捏造することになる
- `domain_input.py`または`immutable_model.py`が0以外を返し、入力または本文を直しても解消しない
- 同じpathへの保存ができない

**仮説を明示して進む。** 業務知識が存在し、設計対象を識別できるが、履歴の必要性や保持期間が決まらない場合は、後の業務上の問いから最も筋の良い正本を仮説として選び、該当要素と未決へ根拠、採らなかった候補、確認相手を記載して進む。

## 出力

- 同じpathで横断改訂した複数のRDB論理設計
- targetごとの正本選択と、業務知識から辿れる採否理由
- 業務知識の掲載順を保ったデータモデルBDDの採用結果と、永続化が関与しないため対象外にしたシナリオの理由
- 全テーブルのリソース系／イベント系、業務／技術／派生の分類
- 業務知識と入力に意味上の矛盾があった場合は、データモデルへ混ぜず分離した業務知識の修正候補
- 決定論的検査の結果と、意味評価として残した未決
