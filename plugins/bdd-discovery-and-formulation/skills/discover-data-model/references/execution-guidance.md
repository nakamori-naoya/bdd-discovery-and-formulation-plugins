# data model BDD discovery 実行指示書

## 背景と目的

この入口は、テーブルを考える前に、業務イベントによってどの事実を残す必要が生じるかを明らかにする。後の判断や説明に必要な事実、現在状態、履歴、保持理由をBDDで検査してからRDB論理構造へ写す。

## 前提

- 作成・更新・削除はSQL操作ではなく、事実の初成立、別の事実による現在状態の変化、保持理由が尽きた物理削除として扱う。
- 業務上の取消や訂正を、成立済み事実の物理削除と混ぜない。
- Read、index、物理型、SQL、API、DTO、ORM、画面はこの入口の関心外とする。
- 論理構造への配置方法は`modeling_method`で受け取る。既定を持たず、決め方を報告する。

## 各工程を実行するときの指示

### settle（grill）

入力から分からない点だけを1問ずつ確認する。記録の必要を生む業務イベント、事前状態、条件、判断、結果、次状態、残す事実、同一性と粒度、現在状態と履歴、作成・更新・削除の意味、訂正と取消、保持理由、物理削除を許す条件、判断時点と根拠を意識する。テーブルやcolumnの希望を先に聞かない。

`context`には`purpose`（業務イベントから永続化の必要を発見し論理設計へ写す）、`audience`（業務責任者と開発者）、`boundary`（Read、index、物理型、SQL、API、DTO、ORM、画面は扱わない）を渡し、題材固有の観点は`questions`で渡す。

### scenarios（永続化シナリオ）

作成・更新・削除をそれぞれシナリオあり、または業務理由つき対象外にする。一つのシナリオへ複数の業務イベントを混ぜず、何が起きたため何を残すのかを追跡できるようにする。

### logical-model（論理データモデル）

検査済みシナリオから必要な事実だけを写す。現在の姿を持つresourceと、成立済みの出来事を追加するeventを区別し、BeforeとAfterの差分を全tableについて説明できるようにする。冒頭の段落は誰が何を判断・説明するためにどの事実を残すのかを文章で書き、作業記録は本文に置かず報告へ載せる。

### document（write-doc）

`document_type`に`rdb-logical-data-modeling`を渡し、完成本文を`kind: text`の`material`として1本へ保存する。保存先は`output_directory`と`name`でこちらが指定し、既存資料があれば上書きせず停止する。呼び方は[入れ子の段取りを呼ぶ](nested-playbook.md)に従う。
