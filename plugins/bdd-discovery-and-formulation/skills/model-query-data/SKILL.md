# 業務知識のクエリが、残したデータで実現できるかを確かめる

この入口は、業務知識の資料のクエリを、コマンドデータモデルが残すデータだけで実現できるかを確かめ、BDD付きのクエリデータモデルの資料にする。書き込みと読み取りでは関心が違うので、読み取りの約束はここで確かめ、コマンドデータモデルには書き込みの関心だけを残す。永続化が正しくなければ読み取りもできないので、この資料は自分のテーブルを持たず、コマンドデータモデルのテーブルを読むだけである。

根拠にする業務知識の資料は必ず要る。無ければ、先に `write-business-knowledge` で作るよう返す。この資料を立てるかは、業務知識が決めている（クエリがあれば立てる）。業務知識にクエリが無ければ立てず、そう報告して終える。

読むテーブルを定義したコマンドデータモデルは、依頼の入力である業務の分け方の一覧から持ち主が分かる。この資料は他人の資料を確かめることが仕事なので、確かめる相手がそろわないうちは作り始めない。読むテーブルの持ち主の資料が一本も置かれていなければ、何も書かず、どの資料を待つかを返して終える。一部だけ置かれていなければ、そのテーブルを読むクエリは確かめられないので対象外にし、予定の置き場と一緒に未決に書いて、確かめられたクエリで保存する。持ち主の資料ができたら、同じ入口で深めれば埋まる。

作ることと深めることは同じ仕事で、違いはgrillで何を問うかだけにある。

## 返るものを、Beforeの行と取得結果で示す

業務知識のクエリのBDDを掲載順に読み、表示対象の条件、並び順、境界（0件、ちょうど上限、続きの境目）を採る。読み取りの失敗（全体を返せない、一件だけ壊れている）は、保存と実装が決めることなので採らない。一件のBDDでは、Givenに読む人と条件を、Whenにクエリを一つ置き、Beforeに読むテーブルの行を、取得結果に返る項目と順を具体的な値で書く。取得結果の順が並び順の決まりを示すので、同じ値で並びが決まらない行（同じ時刻の二件）も例に入れる。

Beforeの表の列は、コマンドデータモデルの図の列名をそのまま使い、読む列だけを載せる。同じ形の行が多いときは、範囲の一行で書いてよい。ただし先頭、末尾、境界の行は範囲に含めず、値で書く。読み手が結論を読むのは境界の行だからである。行ごとに値が変わる列（出来事の時刻など）を並びの根拠に使う例では、範囲の中の並びが読めなくなるので、範囲の行にしない。

データを読んで決まる拒否（対象の行が無いので拒む）も、取得結果の表で示す。「0件が返る」と「拒まれる」は利用者に見える結果が違うので、どちらなのかを取得結果で書き分ける。

業務知識のすべてのクエリのBDDについて、対応するこの資料のBDDか「対象外」を対応表に置き、対象外にした理由は表の後の本文にまとめて書く。読むだけの業務も、この資料だけで足りる。

## 速さと運び方は書かない

どのデータをどう組み合わせ、どの順で返すかだけを書く。速さ、キャッシュ、投影、index、読み取り元の切り替えは、どれも同じ結果をより速く返すための方式なので物理設計に置く。同じ結果を返すかどうかは、この資料のBDDで確かめられる。

表示対象と並び順を変えない値（一回に返す件数）は、業務知識と同じく、この資料でも判断に使わない。境界の例に要るときは、業務知識が示した置き場（API の契約か品質要求）の値を前提として書く。物理設計の担当が読むべきこと（読み取りを速くする方式の候補など）は、報告ではなく資料の物理設計への申し送りの節に書く。

## 実現できない読み取りは、コマンドデータモデルの欠けとして返す

業務知識のクエリが、コマンドデータモデルの列と行だけでは導けないと分かったら、この資料で列やテーブルを足さない。どのクエリに、どの事実が足りないかを未決に書き、`model-command-data` への変更案として報告で返す。読むために形を決め直すと、同じ事実の形を二つの資料が決めることになるからである。足りないのが業務の決まりそのもの（表示対象の条件が決まっていない）なら、`write-business-knowledge` への変更案として返す。

## 手順

1. 業務知識の資料と、読むテーブルを定義したコマンドデータモデルのうち置かれているものを読み、調べれば分かることを確かめる。業務の分け方の一覧は依頼の入力で、無ければ最初の一問で依頼元と決める。一覧に無い業務が要ると分かったら、止まって依頼元へ返す。
2. grill の規律で、答えで表示対象と並び順が変わる問いだけを問う。業務知識に答えがある論点は問わない。保存の名前は問わない。
3. write-doc skill の `assets/templates/query-data-model.md`（節と検査が読む目印）、`assets/examples/query-data-model.example.md`（見本）、`references/writing-norms.md`（書くときの規範）を読み、直接書いて保存する。新しく作るときは、依頼にある置き場へ `query-data-model.md` の名前で保存する（名前の指定があればそれに従う）。置き場が依頼に無いときだけ問う。深めるときは同じパスへ戻す。仮説で置いたことは、そのBDDと未決に、仮説であること、根拠、採らなかった案を添えて書く。
4. 保存した資料に `python3 scripts/query_model.py check <保存した資料の絶対パス>` を一回かける（パスはこの SKILL.md のディレクトリ基準）。検査は、Beforeに出たテーブルと列が、読むテーブルの表のリンク先のコマンドデータモデルに実在するかを見る。合否はこの資料の違反だけで決まり、リンク先の資料がまだ無いことは未確認として出て、合否に数えない。違反が出たら本文を直して保存し直す。列が本当に無いなら、この資料で作らず、上の差し戻しに回す。持ち主の資料が後から置かれても、この検査はかけ直さない。

資料の集合がそろったら、依頼元が `python3 scripts/query_model.py check-set <置き場の全クエリデータモデルの絶対パス>...` を一回かける。集合の検査は、それぞれの資料を順に判定し、残った違反と、まだ読めない持ち主のリンクを違反として返す。照合の意味は、相手がそろったときに決まるからである。

## 停止条件

分からないことに出会ったら、答えによって資料の結論が変わるかで、止まるか進むかを決める。この資料の結論は、各クエリで読むテーブルと行、返る項目と順、実現できるかどうかである。

結論が変わるなら、推測で埋めずに止まる。何も保存せず、何が分からないか、それで結論のどこが変わるか、推奨する答えと根拠を返す。結論を変えず、例の値にとどまるなら、最も筋の良い仮説を置いて進み、仮説であることを資料に書く。

業務知識の資料が無い、読むテーブルの持ち主の資料が一本も無い、置き場が確かめられない、分け方の一覧に無い業務が要る、検査の違反を直せない、のどれかでも止まる。確かめられたクエリだけで保存し、確かめられないクエリは対象外にして理由を未決に書き、差し戻しを返す。一つも確かめられなければ保存しない。

## 報告

保存した資料の絶対パス（立てなかったときはその理由）、確かめたクエリとBDDの数、読んだテーブルと持ち主の資料、対象外にした業務知識のBDDと理由、実現できない読み取りとコマンドデータモデルへの変更案、持ち主の資料がまだ無くて確かめられなかったクエリ、業務知識への変更案、仮説として置いたことと根拠、未決と確かめる相手、物理設計への申し送りの節を返す。持ち主の資料を待って作らなかったときは、待つ資料の予定の置き場を返す。
