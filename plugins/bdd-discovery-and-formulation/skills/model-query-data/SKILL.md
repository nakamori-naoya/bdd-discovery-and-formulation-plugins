# 業務知識のクエリが、残したデータで実現できるかを確かめる

この入口は、業務知識の資料のクエリを、コマンドデータモデルが残すデータだけで実現できるかを確かめ、BDD付きのクエリデータモデルの資料にする。書き込みと読み取りでは関心が違うので、読み取りの約束はここで確かめ、コマンドデータモデルには書き込みの関心だけを残す。永続化が正しくなければ読み取りもできないので、この資料は自分のテーブルを持たず、コマンドデータモデルのテーブルを読むだけである。

根拠にする業務知識の資料は必ず要る。無ければ、先に `write-business-knowledge` で作るよう返す。この資料を立てるかは、業務知識が決めている（クエリがあれば立てる）。業務知識にクエリが無ければ立てず、そう報告して終える。

読むテーブルを定義したコマンドデータモデルは、依頼の入力である業務の分け方の一覧から持ち主が分かる。この資料は他人の資料を確かめることが仕事なので、確かめる相手がそろわないうちは作り始めない。ただし、「持ち主の資料がまだ無いが、いずれ置かれる」ことと、「持ち主が作業の範囲の外にあり、資料は置かれない」ことを分ける。後者は、分け方の一覧が外の持ち主の資料を宣言していれば、待たずに所与の読み取り元として読む。所与の読み取り元は、テーブルでなくてもよい（配信される静的なファイル、外部の API）。クエリの条件が求める事実を業務の言葉で書き、Before には所与の事実の行として置く。形（列名や型）は持ち主が決めるので書かない。読み取りのために、外の事実をコマンドデータモデルのテーブルへ写さない。同じ事実の持ち主が二つになるからである。範囲の中の持ち主の資料が一本も置かれておらず、所与の読み取り元だけでは確かめられるクエリが無いなら、何も書かず、どの資料を待つかを返して終える。一部だけ置かれていなければ、そのテーブルを読むクエリは確かめられないので対象外にし、予定の置き場と一緒に未決に書いて、確かめられたクエリで保存する。持ち主の資料ができたら、同じ入口で深めれば埋まる。

作ることと深めることは同じ仕事で、違いはgrillへ渡す論点だけにある。

## 返るものを、Beforeの行と取得結果で示す

業務知識のクエリのBDDを掲載順に読み、業務上の対象選択・順位・加工・計算と得られる結果を採る。結果を届けるための件数や区切りは、別の入出力契約を根拠にする。読み取りの失敗（全体を返せない、一件だけ壊れている）は、保存と実装が決めることなので採らない。一件のBDDでは、Givenに判断に必要な条件を、Whenにクエリを一つ置き、Beforeに読む事実を、取得結果に選ばれる対象や導出された値を具体に書く。業務上の順位がある場合は、その順と同順位の扱いも確かめる。

Beforeの表の列は、コマンドデータモデルの図の列名をそのまま使い、読む列だけを載せる。同じ形の行が多いときは、範囲の一行で書いてよい。ただし先頭、末尾、境界の行は範囲に含めず、値で書く。読み手が結論を読むのは境界の行だからである。行ごとに値が変わる列（出来事の時刻など）を並びの根拠に使う例では、範囲の中の並びが読めなくなるので、範囲の行にしない。

データを読んで決まる拒否（対象の行が無いので拒む）も、取得結果の表で示す。「0件が返る」と「拒まれる」は利用者に見える結果が違うので、どちらなのかを取得結果で書き分ける。

業務知識のすべてのクエリのBDDについて、対応するこの資料のBDDか「対象外」を対応表に置き、対象外にした理由は表の後の本文にまとめて書く。読むだけの業務も、この資料だけで足りる。

## 速さと運び方は書かない

どの事実をどう組み合わせ、業務上の選択・順位・計算結果をどう得るかを書く。速さ、キャッシュ、投影、index、読み取り元の切り替えは、どれも同じ結果をより速く返すための方式なので物理設計に置く。同じ結果を返すかどうかは、この資料のBDDで確かめられる。

業務上の対象・順位・計算結果を変えない値（一回に返す件数など）は、業務知識の決まりとして扱わない。境界の例に要るときは、その値の持ち主である入出力契約や品質要求を根拠にする。物理設計の担当が読むべきこと（読み取りを速くする方式の候補など）は、報告ではなく資料の物理設計への申し送りの節に書く。

## 実現できない読み取りは、コマンドデータモデルの欠けとして返す

業務知識のクエリが、コマンドデータモデルの列と行だけでは導けないと分かったら、この資料で列やテーブルを足さない。どのクエリに、どの事実が足りないかを未決に書き、`model-command-data` への変更案として報告で返す。読むために形を決め直すと、同じ事実の形を二つの資料が決めることになるからである。足りないのが業務の決まりそのもの（対象の選び方や計算が決まっていない）なら、`write-business-knowledge` への変更案として返す。

## 手順

1. 業務知識とコマンドデータモデルを読み、各クエリが返す結果と、読む事実の持ち主を確かめる。持ち主の資料がまだ無ければ、その表や列を推測しない。
2. 業務上の対象・順位・計算結果の結論を変える論点を、入力とともに `grill` に渡す。
3. `write-doc` のクエリデータモデルのtemplate、example、書くときの規範を読み、依頼された置き場に保存する。各BDDで、読む前の行と返る結果を具体に示す。
4. `python3 scripts/query_model.py check <保存した資料の絶対パス>` を一回かける（パスはこの SKILL.md のディレクトリ基準）。構造の違反を直す。最後に業務知識の各クエリから業務上の対象・順位・計算結果の抜けを探し、資料の各読み取りから根拠へ戻って、今は要らない列や読み取りを外す。未決の結果は作らない。

## 停止条件

分からないことに出会ったら、答えによって資料の結論が変わるかで、止まるか進むかを決める。入力にも grill の決定にも出どころを指せない判断は、書き手に自然な既定に見えても分からないことである。入力が触れていないことを「無い」「拒む」「誰それが決める」と書くのも判断に当たる。この資料の結論は、各クエリで読む事実、選択・順位・計算した結果、実現できるかどうかである。

結論が変わるなら、推測で埋めず grill で問う。問いの数や手順の残りを理由に、仮説へ変えない。grill を閉じた後に書きながら見つけた論点も同じで、調べて答えが一つに決まれば根拠を添えて資料に入れ、決まらなければ grill に戻す。利用者が決められず未決で返ったものは、推奨を仮置きして進めてよいが、その箇所と未決に仮置きと書き、結論として断定しない。利用者に問えないときは何も保存せず、何が分からないか、それで結論のどこが変わるか、推奨する答えと根拠を返して止まる。結論を変えず、例の値にとどまるなら、最も筋の良い仮説を置いて進み、仮説であることを資料に書く。

業務知識の資料が無い、範囲の中の持ち主の資料が一本も無く所与の読み取り元でも確かめられない、置き場が確かめられない、分け方の一覧に無い業務が要る、検査の違反を直せない、のどれかでも止まる。確かめられたクエリだけで保存し、確かめられないクエリは対象外にして理由を未決に書き、差し戻しを返す。一つも確かめられなければ保存しない。

## 報告

保存した資料の絶対パス（立てなかったときはその理由）、確かめたクエリとBDDの数、読んだテーブルと持ち主の資料、対象外にした業務知識のBDDと理由、実現できない読み取りとコマンドデータモデルへの変更案、持ち主の資料がまだ無くて確かめられなかったクエリ、業務知識への変更案、仮説として置いたことと根拠、未決と確かめる相手、物理設計への申し送りの節を返す。持ち主の資料を待って作らなかったときは、待つ資料の予定の置き場を返す。
