# コアドメインの共通理解を正本にする

読み終えると、利用者が持つ業務知識から、作りを全部やめても残る決まりだけを、業務の言葉で書いたdomain-rule正本1本へ保存できる。正本は業務の人と開発者が同じ判断を説明するためのものであり、画面、保存、手順、テスト実行は別の資料が担う。探求が先で、記述は後である。何が起きるのかを知らないまま型を埋めると、型の穴を埋める作り話が入る。

同じdirectoryの`playbook.yml`が工程順の正本である。このSKILLを読んだagentが、利用者の入力と明示された資料を保持したまま`steps`を宣言順に辿り、最後まで同じ文脈で判断する。`agent_work: invoking_agent`の工程はこのagentの認知工程、`skill:`の工程は同じpackageに同梱された同名skillの`SKILL.md`をこのagentが同じ文脈で読んで適用する工程、`script:`の工程は明示した入力から閉じた結果を返す決定論的tool、`playbook:`の工程は外部公開Skillの直接呼び出しである。

## 入力

| 入力 | 内容 | 満たさないときの扱い |
|---|---|---|
| `user_input` | 依頼文。題材と、利用者がすでに知っていること | 題材が読めなければ`settle`で問う |
| `referenced_artifacts` | 利用者が明示した既存資料の絶対path | 相対path、読めないpath、symlinkは停止して確認する |
| `output_directory` | 正本を置く既存の書き込み可能な絶対directory | 下の「保存先の決め方」に従う |
| `name` | path要素を含まない`.md`file名。日本語名を許す | 同上 |

**保存先の決め方。** 依頼に資料構成が示されていれば、そのまま使う。示されていなければ、利用者の既存資料のdirectory階層と命名を読み、置き場と名前を一度だけ提案して確認する。既定のpathを持たない。`output_directory`が存在しない、相対pathである、または同名fileがすでにある場合は、書かずに停止して利用者へ返す。同名fileが既存の正本なら、この入口では扱わず既存正本の反証（formulation）が該当すると報告する。

[入力に根拠づける規律](references/input-grounding.md)に従い、利用者の発言、明示された資料、`settle`で確認した決定にない業務用語、業務イベント、役割、決まりを作らない。受け取った事実は、誰が確かめたのかで確からしさが変わるので、確認済み・仮置き・未確認の区別を保ったまま扱う。

## 判断基準

| 観察対象 | 述語 | 行動 |
|---|---|---|
| 候補の記述 | 仕組みを全部やめても残る、業務を知る人がその言葉を使う、破られて困るのは業務である、の3つが成り立つ | 業務の話として残す。どれかが成り立たなければ実装の関心として理由付きでスコープ外に置く。迷ったら業務の話ではない側へ倒す。取りこぼしは次に業務を語れば戻るが、混入した実装の話は正本を腐らせる |
| 業務の話に残ったもの | コア・支援・汎用のどれに当たるか、選ばれる理由を1文で言える | 理由を添えて分類し、コアだけを代表BDDの対象にする。理由が言えなければ分けず`settle`で問う |
| 業務イベント | 過去形の業務事実として書けている | 採る。「〜する」「〜してほしい」の要求や、画面操作・API requestは業務イベントにしない |
| 誰が行えるか | すべてのコマンドとクエリについて、行える役割と行えない場合の業務上の理由が決まっている | 成立条件と同じ重さのコアの決まりとして書く。実現が認証・認可に寄っても業務知識に置き、実現を担うもの（業務判断 / 認証・認可 / 非機能）を添える。判定は「破られたときに困るのは業務か運用か」であり、運用の関心（トークン形式・有効期限、IP/利用者単位のレート制限、管理者操作）は書かない |
| 主体に関する決まり | 成立条件、常に守られること、誰が行えるか、拒むときの理由、BDDの5か所で同じ主体が揃っている | 揃える。片方にだけある決まりは書き漏らしとして戻す |
| 用語 | 業務関係者が仕事の会話と判断で合意して使う語である | ユビキタス言語に載せる。バックエンドの部品名、保存方式、内部状態名、技術語を平易に言い換えただけの独自語は載せず、合意語が無ければ回答責任者つきの未決にする |
| 代表BDDの候補 | 典型、既知の代替、既知の拒否のどれかである | 代表BDDにする。境界値、同値分割、順序逆転、重複、同時実行による体系的な反証は、共通理解を作った後の反証（formulation）が担う |
| 資料化の前提 | 事実、線引き、決定、振る舞い断面、代表BDD、誰が行えるかの表がすべて揃っている | 資料化する。どれかが欠けていれば揃うまで工程を戻す |

## 手順

1. **settle（`grill`）。** [実行指示書](references/execution-guidance.md)の観点を`context`と`questions`に渡し、入力だけでは不明または深掘りが必要な業務の事実、役割、決まり、各コマンドとクエリを誰が行えるかを1問ずつ確かめる。呼び方は[入れ子の段取りを呼ぶ](references/nested-playbook.md)に従う。返った`decisions`と`open_questions`を利用者入力・明示資料と突き合わせる。
2. **ground。** 依頼、参照資料、決定、未決を根拠・仮説・未確認へ区別して`grounded_input`として保持する。
3. **explore。** 同梱skillの判断規律で、業務で起きた事実を時系列に洗い出し、引き金、担い手、前提、業務上の結果、確からしさを`events`と`actors`として保持する。
4. **scope。** [業務の話の境界](references/boundary.md)、[ドメイン](references/domain.md)、[サブドメイン](references/subdomains.md)、[境界づけられたコンテキスト](references/bounded-contexts.md)、[概念の関係](references/concept-map.md)を読み、業務の話と実装の関心に線を引き、残ったものをコア・支援・汎用へ理由付きで分ける。該当が無い区分は「なし」と書く。スコープ外へ落としたものと理由を`implementation_excluded`として保持する。
5. **record-behavior。** [振る舞い発見](references/behavior-discovery.md)、[アクターとステークホルダー](references/actors-and-stakeholders.md)、[業務ルール](references/domain-rules.md)、[ユビキタス言語](references/ubiquitous-language.md)、[共通理解を作る問い](references/questions.md)、[成果物の形](references/discovery-deliverable.md)、[BDDの前提・トリガー・失敗理由](references/scenario-premises.md)を適用し、コアの代表的な振る舞い断面、コマンドとクエリの一覧、誰が行えるかの表、代表BDD、条件マトリクス、完成本文を同じ文脈で作る。冒頭の段落は、誰が何をなぜ行う業務かを読み手の既知の語で文章として運ぶ。型の読み方の解説やメタ情報の一覧は本文に書かない。
6. **validate（`scripts/scenario_matrix.py`）。** 条件マトリクスをsystem temporary directoryの一時fileへ書き、`python3 scripts/scenario_matrix.py check --file <条件マトリクスJSON>`を実行する。pathはこのSKILLと同じdirectoryを基準にする。stdoutにJSONを1行ずつ返し、終了codeは0が違反なし、1が違反あり（各行が`path` / `detail` / `howto`）、2が入力を読めない。0以外なら資料化へ進まず、診断に従って`record-behavior`へ戻る。
7. **validate-actors（`scripts/actor-coverage.py`）。** 完成本文を一時fileへ書き、`python3 scripts/actor-coverage.py check --file <完成本文>`を実行する。本文の見出し`## コマンドとクエリ`と`# 誰が行えるか`の配下にある表の第1列（`業務上の行い`）が両方向で一致すれば終了code 0、片方にしか無い行い名があれば1で各行を`kind` / `detail` / `howto`として返し、読めなければ2である。0以外なら`record-behavior`へ戻る。表記ゆれとして報告された行が同義かどうかは、このagentが読んで判断し、第1列を揃える。この2つの見出しと第1列名は、`write-doc`の`domain-rule`型（公開契約の`document_type`）が定める本文の形であり、本文をその型で書くことがtoolの前提である。
8. **document（`write-doc`）。** 完成本文を`{kind: text, content: <完成本文>}`の1要素配列で`material`に、`domain-rule`を`document_type`に、確認済みの`output_directory`と`name`をそのまま渡す。`references`には[成果物の形](references/discovery-deliverable.md)の絶対pathを渡す。返った結果の`status`が`completed`で、`path`が指定した保存先と一致することを確かめ、その`path`を`domain_rule_path`にする。`failed`、結果欠落、path不一致なら理由を報告して停止する。
9. **後片付け。** 保存成功を確認した後に、自分が作った一時fileだけを明示pathで削除する。保存に失敗したときは残す。

## 停止条件

- 題材、または利用者がすでに知っていることが読めず、`settle`でも決まらない
- 業務の話の線引きができない。線が引けないうちに書き始めると、実装の話が混ざったまま正本になる
- コアの範囲が決まらない。支援・汎用まで同じ丁寧さで問い詰めると、いちばん大事なところへ手が回らない
- `grill`が`completed`以外を返した、または`decisions` / `open_questions`が配列でない
- 検査が0以外で終了し、`record-behavior`へ戻しても解消しない
- 保存先が確認できない、既存fileがある、`write-doc`が`completed`以外を返した

停止したときは、どこまで確定し、何が分かれば続けられるかを返す。未決に依存する振る舞いは完成扱いにせず、回答責任者つきの未決として残す。

## 報告

- 保存した正本の絶対pathと、扱った題材
- コア・支援・汎用の線引きと、スコープ外へ落としたものと理由
- コアの代表的な振る舞い断面と、誰が行えるかの表の行数
- 未確認のまま残った事実と、誰に聞けば確かめられるか
- まだ決まっていない論点
