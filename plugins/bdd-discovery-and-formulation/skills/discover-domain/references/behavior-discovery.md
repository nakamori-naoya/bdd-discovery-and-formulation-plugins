# 業務振る舞いを発見する

**振る舞い発見の目的は、機能を列挙することではない。** 業務で何が起きたとき、誰が、どの事実と状態を根拠に、何を判断し、その結果として誰の仕事と状態がどう変わるかを共通理解にする。

## 発見の単位

一つの振る舞い断面を、次の形で捉える。

```text
起点となる業務上の役割の目的
+ 協働する業務上の役割
+ 事前の業務状態
+ 起きた業務イベント
+ 結果を分ける業務条件
→ 判断権者の業務判断
→ 各役割が確認できる結果
+ 次の業務状態
+ 責任・情報の引継ぎ
+ 次に起きる業務イベント
```

業務イベントは「申込みが届いた」「支払期限が過ぎた」のような、業務上すでに起きた事実で書く。ボタン押下やAPI requestではない。事前状態と条件を混ぜず、状態は出来事の直前に対象がどうなっていたか、条件は同じ状態と出来事でも判断を変える事実として扱う。

## 発見の工程

1. **範囲と目的を置く。** 誰にどんな価値を届ける業務判断を扱うか決める。
2. **業務上の役割を出す。** 起点役割、事実の提供者、判断権者、拒否できる役割、影響を受ける役割、結果を知る役割を分ける。
3. **業務イベントを過去形で並べる。** 人の行為、外部からの通知、期限到来も候補にする。
4. **直前の状態を問う。** 対象だけでなく、協働する役割が保持する責任や待ち状態も見る。
5. **典型の組合せを一つ作る。** 役割・事前状態・イベント・条件を明記し、判断、結果、次状態、引継ぎまでつなぐ。
6. **既知の違いを置く。** 業務担当者が普段区別している代替や拒否があれば、典型との違いを記録する。
7. **業務ルールへ束ねる。** 複数の断面を説明する判断・制約・不変条件を短い文にする。
8. **未決と技術事項を分ける。** 未決は回答責任者つきの問い、API・DTO・通信・保存方式は行き先つきの除外事項にする。
9. **代表BDDを書く。** 共通理解を具体的に読める典型・既知の代替・既知の拒否だけをGiven・When・Thenにする。

ここでは未知の欠陥を探すために入力を体系的に変えない。境界値、同値分割、順序、重複、同時実行などによる反証はformulationで行う。

## 複数アクターの協働

複数の役割が登場するなら、単なる登場人物一覧にしない。誰が開始し、誰が事実を提供し、誰の権限で判断し、誰が結果を受け取り、次の責任が誰へ移るかを時間順に確かめる。通知は伝達手段ではなく、その通知を受けたことが次の業務判断を開始する場合に業務イベントとなる。

## ユビキタス言語を育てる境界

候補語ごとに二つを問う。

1. ソフトウェアを全て置き換えても、その事実や決まりは残るか。
2. 業務に責任を持つ人が、正しいか誤りかを判断できるか。

両方が真なら候補として業務資料に置き、典型例、反例、境界例の中で同じ判断に使えるかを確かめる。業務の人が使う語でも、役割や文脈ごとに意味が割れるなら一つに統一しない。API、DTO、HTTP、DB、queue、endpointなど、実現方法だけを表す語は技術設計へ移す。業務上の意味へ言い換えられるなら言い換える。たとえば「409を返す」ではなく「配送開始後の変更を理由つきで拒む」と書く。
