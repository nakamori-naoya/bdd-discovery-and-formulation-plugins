# 業務振る舞い発見資料を作る

**成果物は代表BDDを含むdomain-ruleの正式な定義である。** 業務の人と開発者が、QAによる反証より前に判断の構造を共通理解にするために作る。

## 読み手と用途

- 業務責任者は、用語、判断、権限、状態変化が正しいかを確認する。
- 開発者とQA担当者は、何が合意済みで、どこが未決かを知る。
- BDD定式化の担当者は、代表BDDを反証の出発点にする。

この資料は、画面、API、DTO、database、message schemaなどの実現方法を決めず、本文にも書かない。入力にあった実現の記述は、外した理由と送り先を報告に載せる。

## 構成

冒頭の段落は、誰が何をなぜ行う業務かを読み手の既知の語で文章として運ぶ。対象、確定日、決めた人のような作業記録は本文に置かず報告へ載せる。

資料は、ユビキタス言語（業務用語と業務イベントを見出しごとに。業務の言葉と英名の対応を含む）、概念、常に守られること、状態と、その移り変わり、業務の行い、導出されること、同時に起きたとき、まだ決まっていないこと、BDDの順に、見出しと文章で書く。節の形は`domain-rule`型のtemplateが定める。

業務の行いがこの資料の中心である。コマンドとクエリのそれぞれに見出しを立て、誰が行えるか、それ以外の人が行うと誰が何に困るか、成り立つ条件、拒む理由を、その一か所にまとめる。誰が行えるかは成り立つ条件と同じ重さの決まりなので、別の表へ分けない。分けると、読み手は条件を読みながら権限と拒む理由を別の場所へ探しに行き、どちらか一方だけが直されて食い違う。BDDには、本人以外が行ったときの拒否を、成り立つ条件のBDDと同じ重さで置く。

| 欠けているもの | 何が起きるか |
|---|---|
| 業務イベント | 決まりだけが並び、いつ効くのかが読めない |
| 業務の行いの誰が行えるか | 権限の話が書けず、誰でもできると読まれる |
| 常に守られること | 例外の説明が積み上がり、原則が見えなくなる |
| 状態の移り変わり | 終わったはずのものへ操作できてしまう |
| 業務の行いの成り立つ条件 | 具体例だけが残り、一般の決まりが読み取れない |
| 拒む理由 | 拒否が理不尽に見え、現場で回避される |
| 未決 | 空欄が「決まっている」と読まれ、勝手な解釈で実装される |

どの項目にも確認済み・仮置き・未確認がありうる。束ねるときに確からしさを落とすと、確かめていないことまで確定として本文へ入る。画面・保存・境界のやりとり・手順の組み立ては、どの項目にも当たらないので正式な定義へ入れない。

ルールを先、具体的な断面を後に置く。具体例から新しいルールが見つかったら、先にルール欄へ戻して記載する。

## 振る舞い断面の品質

次を一つの断面に明記する。

| 項目 | 答える問い |
|---|---|
| 目的 | 起点役割は何を成し遂げたいか |
| 起点・協働役割 | 誰が開始し、誰が事実・判断・後続作業を担うか |
| 事前状態 | 出来事の直前、対象と責任はどうなっているか |
| 業務イベント | 何が起きて判断が必要になったか |
| 条件 | 同じ状態とイベントでも、何が違えば結論が変わるか |
| 業務判断 | 誰の権限で、受理・拒否・保留・導出のどれを行うか |
| 観測できる結果 | 各役割は何を知り、得て、失わずに済むか |
| 次状態 | 何が可能または不可能になり、責任はどこにあるか |
| 引継ぎ・後続イベント | 誰が次に行動し、何の事実が次の判断を始めるか |

「協働なし」「追加条件なし」「引継ぎなし」「後続イベントなし」も省略せず明記する。空欄は、調べた結果の不存在なのか、単なる見落としなのかを区別できない。

## 代表BDDの書き方

- 事前状態と結果を分ける条件 → `Given`
- 起点役割と業務イベント → `When`
- 業務判断、観測できる結果、次状態 → `Then`

典型、業務担当者が既に認識している代替、既知の拒否を別scenarioにする。長い協働全体を一つへ押し込まず、合意した業務判断ごとに焦点を切る。未回答の問いが残る断面はBDDにしない。境界値や組合せを体系的に増やすのはformulationで行う。
