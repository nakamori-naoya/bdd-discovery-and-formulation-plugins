# どこまでが業務の話か

**業務の話は、作り方を全部捨てても残る。** 紙と電話で回していた時代にも同じ決まりがあったなら、それは業務の話である。

## 3つの問いで判定する

1. **仕組みを全部やめても、その決まりは残るか。** 残るなら業務の話
2. **業務を知る人が、その言葉を使って話すか。** 使わないなら業務の話ではない
3. **その決まりが破られたとき、困るのは業務か、動かなくなるのはプログラムか。** 前者なら業務の話

**3つとも「はい」でなければ、業務の話として書かない。**

## よく混ざるもの

| 混ざるもの | なぜ業務の話でないか | どうするか |
|---|---|---|
| 画面・操作の順序 | 画面を作り替えれば変わる。業務の決まりは変わらない | その操作で業務上何が起きたかへ言い換える |
| データモデル・保存の形 | テーブル、イベントストア、更新方式など、どこへどう置くかは実現の選択である | 後の業務判断に必要な事実と、業務上どういう状態になったかへ言い換える |
| API・メッセージの形 | endpoint、request、response、status code、schemaは境界を実現する契約である | 誰が誰へ何を求め、どの業務事実が返るかへ言い換える |
| ユースケース・手順の組み立て | 何をどの順に呼び、どこで一連の処理にするかは作りの話 | その手順が守っている業務の決まりを取り出す |
| コード・配置 | class、function、layer、service、repository、配置単位は実装の形である | 一貫して守る業務上の決まりと意味の境界を取り出す |
| 拒否の分類記号 | 記号は業務の言葉ではない | なぜ拒むのか、業務上の理由を書く |
| 運用・非機能の実現方式 | cache、queue、batch、監視、token、rate limit、可用性構成は実現の品質や運用である | 業務上の期限・鮮度・証跡・継続性として判断を変える条件だけ残す |
| テスト・開発工程 | fixture、mock、自動化、QA手法、release手順は正しさを確かめ届ける方法である | 具体例が表す業務条件と観測可能な結果だけ残す |

**言い換えられないものは落とす。** 落としたことと理由は残す。**黙って消すと、次に同じものが同じ場所へ戻ってくる。**

## 落とすのであって、否定するのではない

画面も保存も手順も、作るうえでは要る。ここで決めているのは**それらを業務の正本へ書かない**ということだけである。

**「業務の正本に無いから作らない」ではない。** 「業務の正本は、作りが変わっても変わらない範囲だけを持つ」である。

## 迷ったときの倒し方

**迷ったら業務の話ではない側へ倒す。** 業務の正本へ入れ損ねたものは、次に業務を語ったときにまた出てくる。逆に、実装の話が正本へ紛れ込むと、作りを変えるたびに正本が腐り、誰も直さなくなる。

**取りこぼしは戻ってくるが、混入は腐る。**
