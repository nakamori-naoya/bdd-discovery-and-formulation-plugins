# 業務知識の一つの事実を、どの節に書くか

業務の決まりは、どの業務でも同じ種類に分かれる。この業務の外で決まり、当てにするだけの事実（前提）がある。いつでも成り立つこと（制約）がある。対象が今どの状況にあるか（状況）がある。事実から値を得る方法（計算）がある。そして、ある状況にきっかけが来たときに何を判断し、何が起きるか（行動・出来事と判断）がある。業務知識の節は、この種類と一対一にする。

今のテンプレートのように、同じ決まりを見る角度（概念、常に守られること、行いの条件、拒む理由、状態、同時、用語）で節を切ると、一つの決まりが角度の数だけ書き直される。種類で節を切れば、一つの事実の置き場は一つに決まり、本文の中で重複しない。BDD は具体例であり、本文と役割が違うので、本文と同じ判断を例で示してよい。

## 置き場は、上から順に最初に当てはまる問いで決める

| 問い | 置く節 |
|---|---|
| この業務の外で決まり、この業務はその事実を当てにするだけか | 前提 |
| きっかけに関係なく、いつでも成り立つか。破れていたら、記録そのものが誤りか | 制約 |
| 対象が今どの状況にあるかを決めるか。自分の状態と、前提の事実の組み合わせで決まるか | 状況 |
| ほかの事実から値、区分、選択、順位、同じ一つと数える範囲を得る方法か | 計算 |
| ある状況にきっかけ（人の行動、ほかの業務の出来事、時刻の到来）が来たとき、できるか、何が起きるかか | 行動・出来事と判断 |
| 答えがまだ決まらないか | まだ決まっていないこと |

この業務の核には、条件も値も書かない。何を守る業務か、守れないと誰が困るか、中心にある考え（誰が何を決めるかを含む）だけを書く。条件や値を書くと、下の節の写しになるからである。

同じ文が二つの問いに当てはまりそうなときは、文を分ける。例として「フォロー数は5,000人まで」を考える。範囲（5,000人まで）は制約に、数え方（今フォローしている相手の人数）は計算に、5,000人のときにフォローするとできないことは表のセルに書く。セルは制約を名前で指すだけで、範囲を書き直さない。

## 計算は、区分から量へ連なる

計算には、量を求めるものと、区分を決めるものがある。区分は、その後の量の求め方を変える。勤怠であれば、まず働いた日が法定休日か、所定休日か、所定労働日かを決める。次に、その時間が労働時間に当たるかを決める。最後に、その二つで時間外労働時間と休日労働時間を求める。区分を状況に置かないのは、きっかけで移り変わらず、事実から導かれるからである。

計算には、どの時点の事実を使うかを必ず書く。料金を改定しても返金額を変えないのは、計算がキャンセルした時点の予約金額を使うからである。時点が書かれていない計算は、事実が変わったときの答えが一つに決まらない。

一覧に何を出すか、どの順で見せるか、何件ずつ返すかは書かない。それは読み取りで、業務の答えを変えないからである。誰のものが対象になるかが業務の答えを変えるときだけ、選び方を計算に書く（表示対象になるポストの選び方）。

## 状況と、行動・出来事と判断は、表で書く

状況は、きっかけで移り変わる対象の在り方である。自分の状態だけでなく、前提の事実との組み合わせで判断が変わるなら、その組み合わせに名前を付けて状況にする（支払い済みで、進行中の接客セッションがある予約）。計算の値で決まる在り方（上限に達している利用者）も同じで、名前を付けて状況にする。そうすると、判断の条件が表の行に吸収され、条件を文で書き直さずに済む。

行動・出来事と判断は、読み手の問いをそのまま列にした表にする。列は、いつ（今の状況）、誰が、何をすると、何が起きる、どの決まりによるか、である。一行を左から読めば「この状況のとき、この人がこれをすると、できる（できない）。こうなる。この決まりによる」と一文で読める。

- **いつ：** 状況の名前を書く。対象がまだ無い在り方にも名前を付ける（ロールがまだ無い）。記号で省かない。
- **何が起きる：** 次の状況、起きた出来事（「〜した」）、計算した値を名前で書く。できないときは「できない。」で始め、何が変わらないかを書く。
- **どの決まりによるか：** その行が頼る前提、制約、状況、計算の名前を書く。条件の文は書かない。
- **網羅：** 状況と行いのどの組も表に置く（下の節）。同じ答えになる状況は、`、` で区切って一行にまとめてよい。
- **できない行：** 制約、前提、状況の名前を一つ以上置く。その名前が拒む理由になる。範囲を超えるからできないなら制約を、ほかの業務の事実によるなら前提を、その状況がその行いを受けないだけなら状況を置く（返却済みの貸出は返せない）。

誰がは列で必ず書く。アプリが決めることと、人や AI が選ぶことの分担は、ここで分かれる。人や AI が選んだ中身（どの結論を選ぶか）は、きっかけが運ぶ値として扱う。選び方の基準そのものは表にならないので、核で、誰が何を根拠に決めるかを書く。


## 曖昧さを残さない書き方

- 前提、制約、状況、計算の項目には名前を付ける。ほかの節からは、その名前で指す。制約と前提の名前は、成り立つ状態の言い切りにする（「ロールの名前は空でない」）。破った状態（「名前が空」）を名前にすると、できる行の根拠が逆の意味に読めるからである。
- 同じ状況と同じきっかけで、できる行とできない行に分かれるなら、何で分かれるかを、何をするとの欄の括弧に計算の答えで書く（「ロールを作る（名前の区分が空）」）。分かれ目が表から読めないと、その行の答えが一つに決まらない。
- 数の境界は「以下」「未満」「以上」「より後」で書き、境界ちょうどの答えを書く。
- 「など」「のように」「適切に」「必要に応じて」で開いたままにしない。並べたものがすべてなら、すべてと書く。
- 変わりうる事実を使う計算と判断には、どの時点の事実かを書く。
- 制約には、「〜すると」「〜のとき」を書かない。それが要る決まりは、表のセルか計算である。

## 場合分けは決定表に、量は式に書き、文章で組み立てさせない

制約と計算を文章で書くと、実装する人が文から判定の式を組み立て直し、人ごとに答えが割れる。そこで、例で合意した決まりを、答えが一つに決まる二つの形に移す。順は変えない。まず BDD の例で分かれ目を見つけ、例から決まりを一文で引き出し、最後にその一文を下の形にする。形にしたときに埋まらない欄は、次に議論する例である。

- **列挙：** 取りうる値が決まった数だけある語（区分、計算の答え、分かれ目の答え）は、`列挙：<名前> = <値> | <値> | …` の一行で、それを答えにする計算の項目の中か、状況の節に書く（「列挙：日の区分 = 法定休日 | 所定休日 | 所定労働日」）。値を一か所で言い切るので、読む人も検査も、値がこれで全部だと分かる。
- **式：** 量を求める計算は、`式：<計算の名前> = <式>` の一行で書く。変数は前提と計算の名前、演算は四則と最大・最小・合計だけにする。続けて `単位：` と `丸め：`（丸めないなら「丸めない」）を一行ずつ置き、境界ちょうどの答えを文で添える。例は「式：時間外労働時間 = 最大( 労働時間 − 法定労働時間 , 0分 )」「単位：分」「丸め：丸めない」である。
- **決定表：** 場合で答えが変わる計算と制約は、見出しの最後の列を `答え` にした表で書く。ほかの列は条件で、各欄は値か `どれでも` である。どの値の組み合わせにも、当てはまる行がちょうど一つある（行の順に意味は無い）。制約があるので起こりえない組み合わせは、答えを `起こらない（<制約の名前>）` にした行で閉じる。こうすると、入力の場合分けのどれもがどの結果に着くかが、表から機械で確かめられる。列の名前を列挙の名前にすると、その列の値は列挙の値か `どれでも` に限られ、網羅は列挙の値のすべての組み合わせで確かめられる。計算が自分の名前の列挙を持つなら、答えも列挙の値か `起こらない（…）` に限る。列挙にできない量の列は、値を境界で切って入力のすべての場合を尽くす（「0分」「1分以上」）。列挙の無い列で書かなかった値は、検査にも見えない。
- **合成：** 区分の決定表の答えを、量の式が名前で使う。式の中に場合分けを書かない。

場合分けの無い一つの事実（どの時点の暦で日付を求めるか）は、文で書いてよい。

## 判断の表は、状況と行いのすべての組を持ち、行の分かれ目を計算の答えで書く

何をするとの欄は `<行い>` か `<行い>（<分かれ目>）` にする。誰がと行いの組を一つの行いと数え、状況の節のすべての状況に、その行いの行を置く。受けない組は、状況の名前を根拠にしたできない行にする。組み合わせの欠けは検査が見つける。

同じ状況と同じ行いで答えが分かれるときは、分かれ目を `<計算の名前>が<答え>` を `、` で並べた形にする。その計算は列挙と決定表を持つ区分で、答えは列挙の値である。分かれ目に書かない計算は「どれでも」と読む。答えのどの組にも行がちょうど一つ当てはまるので、自由な文の分かれ目より漏れと重なりが無い。

## 一つの行いで決まりが同時にいくつ破れても、返すものを一つに決める

答えを返す道は二つで、業務に合う方を選ぶ。

- 破れうる組み合わせが少ないなら、分かれ目の決定表で組み合わせごとに行を作り、その行のどの決まりによるかに返す決まりだけを置く（本人ではなく期限も過ぎた取り消しは「本人だけが取り消す」だけを返す）。
- 定義の検査のように制約が多いなら、表の前に `拒む理由の示し方：当たったすべて` か `拒む理由の示し方：欄の順で最初の一つ` を一行置く。どの決まりによるかに制約と前提を二つ以上並べたできない行があるなら、この行は欠かせない。「すべて」は、利用者が一度に全部を直せる。「最初の一つ」は、欄の順が優先の順になる。

別の制約が成り立たないと判定できない制約（存在しない version からは型を導けない）には、制約の本文に `判定の前提：<制約の名前>` を置く。判定の前提が破れたとき、その制約は判定せず、当たったに数えない。こうすると「すべて」の一覧も一つに決まる。

## 業務の型によって、節の厚さが変わる

節の名前と順は、どの業務でも変えない。中身が無い節は消さず、無いことを一文で書く。業務の型によって次のように厚さが変わる。足りない所を、ほかの節に押し込まない。

| 業務の型 | 厚くなる節 | 薄くなる節と扱い |
|---|---|---|
| 状態が一生を持つ（予約、フォロー、実行） | 状況、表 | ― |
| 計算が中心（勤怠の集計、料金、予定時刻） | 計算 | 状況は持たないことがある。表は計算を求めるきっかけの数行になる |
| 定義や設定（ワークフロー定義、ロール） | 制約 | 表は保存する行いの数行になる。制約は値の部分ごとに名前を付けて並べる |
| 読み取りが中心（タイムライン） | 計算（誰のものが対象か） | 状況を持たず、表はほぼ空になる。表示の件数や並びは書かない |
| 期限つきの義務が続く（承認の連鎖、期限までの手続き） | 状況（期限を持つ状況）、表（時刻が来る列） | 「いつまでに必ず起きるべきか」は表では書けない。制約に義務として書き、表では書けないことを明示する |
| 裁量で決める（審査、AI が結論を選ぶ） | 核（誰が何を根拠に決めるか） | 表は選んだ後に起きることだけを書く |

一人の利用者が目的に向かって場面をたどる流れは、業務知識に書かない。ユーザーの目的達成の資料が持つ。

## 業務をまたぐ決まりと名前は、一か所だけが持つ

一つの決まりと名前は、その主語の意味を決める業務の資料一か所だけが持つ。ほかの業務の資料は、それを前提として、名前と持ち主へのリンクで指す。下流（データモデル、ドメインの実装）が状況や出来事の値を使うときは、状況と出来事の名前の後に英名を括弧で添える。英名は、語ごとに先頭だけを大文字にしてつなぐ。

## 形は、読めば分かる言葉で書く

業務知識は、業務の人も読む。値の形は、記号を覚えなくても読める言葉で書く。

- **組：** 全部がそろう形は「A と B からなる」と書く（予約 = 利用者 と 時間 と 部屋 からなる）。
- **どちらか：** ちょうど一つになる形は「A か B のどちらか」と書く。列挙の `|` もこの意味である。
- **無いことがある：** 値が無いこともある項目には「無いことがある」と書く。書いていない項目は、必ずある。
- **計算の入力と出力：** 計算の見出しの下に「<入力> → <出力>」を一行置く（返却期限：貸した日 と 開館カレンダー → 日付）。計算は、ここに挙げた入力だけで答えが決まる。挙げていないもの（今の時刻、別の業務の状態）に頼るなら、入力に挙げる。
- **記録は書き換えない：** 起きたことは、書き換えずに新しい出来事を足すものとして書く（取り消しも「取り消した」という出来事）。

これらは、型の記法を知らない人にも同じ意味で読めるようにするためのもので、プログラムの構文ではない。
