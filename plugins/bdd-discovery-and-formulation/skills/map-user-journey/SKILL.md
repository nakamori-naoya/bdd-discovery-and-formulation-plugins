# ユーザーの目的達成をBDDの場面でつなぐ

この入口は、主たるユーザーが目的を達成するまでを、場面の連なりとしてBDDで書いた資料にする。業務の人と開発者が同じ流れを読むための資料であり、ユースケース、UX Journey map、業務ルールの網羅、保存構造、テスト仕様は別の資料が受け持つ。

作ることと深めることは同じ仕事で、違いはgrillで何を問うかだけにある。資料がまだ無いなら、誰が何を達成するか、どこから始まり何が見えたら終わりかを問う。既存の資料を深めるなら、その資料の場面と接続へ反例を当てる問いを立てる。既存の本文も、書いてあるという理由では確認済みにしない。

## Journeyかどうかを先に決める

Journeyとして扱うのは、1人の主たるユーザーが1つの目的を持ち、開始地点から複数の意味ある場面を、状態の受け渡しでつなぎ、観測できる完了へ進む場合だけである。機能を使うこと自体が目的のもの、意味ある場面が一つだけのもの、対象システム一つの責任を問うものは、Journeyにしない。感情と接点はUX Journey map、個別の業務判断は業務知識の資料、保存する事実と読み取りの実現はコマンドデータモデルとクエリデータモデルへ送る。

Journeyは目的ごとに1本である。同じユーザーと同じ目的で条件だけが違う流れは、同じ1本の分岐にする。目的か完了条件が違えば別のJourneyにする。目的を持って始める役割が複数あるなら、役割と目的の一覧を作り、今回の1本を一つ決め、残りは報告で次の候補として返す。

複数本を頼まれたら、最初に役割と目的の一覧を一回のgrillで合意し、その一覧に沿って1本ずつ同じ手順を繰り返す。2本目からのgrillは、その1本に固有の判断だけを問う。一覧に無い目的が途中で見つかったら、一覧へ戻って合意し直す。Journeyの集合の境界を実行ごとに決め直すと、役割の呼び名と目的の切り方が資料どうしで食い違うからである。

## 目的は動機で決め、誰が観測するかは場面の行為者で表す

目的は、主たるユーザーがなぜそれを始めるかという動機で決め、主たるユーザー自身が観測できるかどうかで言い換えない。自分のものを誰かに届けたい人の目的は、届いたことであって、自分の手元で確かめたことではない。目的の達成を観測できるのが受け手だけなら、受け手の観測の場面を置き、そのWhenに受け手を立て、完了条件を受け手の観測で書く。主たるユーザー自身が観測できることは、その手前の場面のThenに書く。観測の都合で目的を変えると、Journeyが確かめるものが利用者の望みからずれるからである。

## 書くかどうかは、主たるユーザーが気づくかで決める

判定の一問は、「この違いが起きたとき、主たるユーザーは何を見て気づくか」である。気づくなら場面か分岐として書く。気づかないなら書かず、書かないことへの断り書きも書かない。

この一問が、場面の中身も決める。Thenと完了条件は、主たるユーザーが見る、知らされる、判断できる、次にできるようになる、のどれかで書く。期間が始まった、記録が更新された、対象に含まれた、のような内部の成立だけではThenにしない。時間の境界が入力にあれば、包含と除外を変えないまま、その境界でユーザーに見えることや、できることがどう変わるかへつなぐ。

Whenに置く役割は、主たるユーザーか、受け手のように主たるユーザーとやり取りする人だけにする。通知基盤や集計処理のようなシステム上の主体は役割にせず、ユーザーが観測する結果へ畳む。語は入力にある利用者の言葉を使い、内部モデルの造語は作らない。

Givenには、その場面のThenを変えうる前提だけを、値ごと書く。どの場面でも同じ形で効く制限（回数の上限など）は、それで結果が変わる失敗の場面にだけ値を書き、上限に触れない場面には並べない。どこにでも効く条件をすべての場面に書くと、場面ごとの違いが見えなくなるからである。

## 場面は、前の結果から次の前提へつなぐ

各場面には、直前の状態、行う役割、一つの主な働きかけ、観測できる応答、次の状態、次への接続を書く。前の場面の結果から次の場面の前提が成り立つ理由を説明できれば、接続として書く。説明できなければ、最も筋の良い接続を仮説として書き、仮説であることと根拠を添えて未決にする。

分岐、中断と再開、役割の移り変わりでは、分かれる場面、残る状態、再開できる期限と条件、渡す責任と受け手が観測できること、目的の達成へ戻るか別の終わり方をするかを書く。場面の数と資料の長さに上限は置かない。目的に寄与しない場面、同じ結果を繰り返す場面、前後がつながらない場面だけを問題にする。

## 深めるときに当てる反例

既存の資料を深めるときは、次の反例を探す。完了条件が満たされても目的が満たされない例と、目的が満たされても最終地点へ着かない例。観測の都合で目的が言い換えられていないか。前の場面の結果だけでは次の場面を始められない接続、どこからも到達できない場面、完了へ至らない循環。正常な経路へ戻らない分岐の抜け。中断したときに残る状態と、再開できる期限の直前・ちょうど・直後で、ユーザーに見えることが食い違う例。役割が移るときに受け手が受け取らなかった場合の終わり方。見つかった違いのうち確認できた修正は、該当する場面へ戻す。業務判断、保存構造、画面操作が本文へ混ざっていれば、送り先を報告に書いて外す。

## 手順

1. 依頼と渡された資料を読み、調べれば分かることを確かめる。
2. grill の規律で、答えで資料の結論が変わる問いだけを問う。作るときの最初の問いは、目的を持って始める役割とその目的である。深めるときは、どの場面や接続を反証しているかを示し、答えで本文の変更が一つに決まる問いを選ぶ。保存の名前は問わない。
3. write-doc skill の `assets/templates/user-journey-bdd.md`（節と目印）、`assets/examples/user-journey-bdd.example.md`（見本）、`references/writing-norms.md`（書くときの規範）を読み、直接書いて保存する。新しく作るときは、依頼にある置き場へ、目的を利用者の言葉で書いた名前（`.md`）で保存する（名前の指定があればそれに従う）。一つの置き場に何本も並ぶので、型の名前ではなく目的で見分ける。置き場が依頼に無いときだけ問う。深めるときは同じパスへ戻す。同じパスに別の資料がある新規作成は上書きせず止まる。Journeyから外した事項の送り先は、資料に書かず報告に書く。

## 停止条件

分からないことに出会ったら、答えによって資料の結論が変わるかで、止まるか進むかを決める。この資料の結論は、主たるユーザーと目的、開始地点と完了条件、場面の並びと接続と分岐、各場面でユーザーが観測する結果である。

結論が変わるなら、推測で埋めずに止まる。何も保存せず、何が分からないか、それで結論のどこが変わるか、推奨する答えと根拠を返す。主たるユーザーの目的、開始地点、完了条件、場面の接続、今回の1本が決まらないときがこれに当たる。結論を変えず、例の値や場面の呼び名のような表し方にとどまるなら、最も筋の良い仮説を置いて進み、仮説であることを資料に書く。

依頼がJourneyの問いでないときも止まり、そう判断した理由と、向いている資料（ユースケース、UX Journey map、業務知識、コマンドデータモデル、クエリデータモデル）を返す。置き場が確かめられないときも止まる。

## 報告

保存した資料の絶対パス、主たるユーザー、目的、開始地点、完了条件、場面の数と主な接続を返す。役割と目的の一覧と、残りのJourneyの順番、Journeyから外した事項と送り先、仮説として置いたことと根拠、未決と確かめる相手も返す。
