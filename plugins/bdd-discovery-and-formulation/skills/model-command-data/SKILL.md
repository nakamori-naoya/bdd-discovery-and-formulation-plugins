# 業務知識のコマンドから、残す事実をコマンドデータモデルにする

この入口は、業務知識の資料のコマンドを根拠に、誰が後で何を判断し説明するために、どの事実を残すかを決め、BDD付きのコマンドデータモデルの資料にする。テーブルの形は具体的な行で議論するので、資料の主役はBDDごとのBeforeとAfterである。扱うのは書き込み（作成、更新、削除）の関心だけで、どう読むかはクエリデータモデルが、製品、DDL、index、分離レベル、再試行、速さは物理設計が決める。

根拠にする業務知識の資料は必ず要る。テーブル名、画面、API、既存のDDLだけでは代わりにしない。無ければ、先に `write-business-knowledge` で作るよう返す。業務のテーブルの根拠は業務知識だけに求める。業務のテーブルに残す理由が業務知識に書かれていないと気づいたら、要件へ探しに行かず、業務知識への変更案として返す。下流が根拠を上流の外に探すのは、上流の資料が足りない印だからである。技術のテーブルの根拠は、要件の品質要求に求めてよい。この資料を立てるかは、業務知識が決めている（コマンドがあれば立てる）。業務知識にコマンドが無ければ立てず、そう報告して終える。

作ることと深めることは同じ仕事で、違いはgrillで何を問うかだけにある。

## 業務知識のコマンドのBDDから、永続化のBDDを選ぶ

業務知識のコマンドのBDDを掲載順に読み、正常な流れ、制約、同時に起きること、履歴を、この資料のBDDとして採る。認可や、保存する前の受け付けだけで拒否が決まるもの、すでにあるBDDと同じ行の変化にしかならないものは「対象外」、クエリのBDDは「クエリデータモデル」として対応表に置き、対象外にした理由は表の後の本文にまとめて書く。業務知識のすべてのBDDについて、対応するこの資料のBDDか、対象外の理由を追えるようにする。

作成、更新、削除のそれぞれに、BDDがあるか、業務上の理由で対象外かを決める。業務上の取消、失効、終了は削除ではなく、新しい事実を足すことである。削除は、保持する理由が尽きて消してよい条件が業務で決まっているときだけにする。

業務知識の同時実行のBDDは、この資料でもBDDにする。通った側で足される行と、通らなかった側で何も増えないことを行で示し、古い版に基づく書き込みが確定しないことも行で示す。文章だけでは、物理設計が何を守ればよいかを読み取れないからである。

## 保存するのはデータだけで、情報は持たない

データは起きたことをそのまま記録したもので、情報はデータを目的に合わせて加工したものである。保存するのは、起きた事実と、業務が与えた値と、後から導けない技術上の判断の値だけにする。集計、件数、平均、順位、別の見方へ組み替えた一覧は作らない。導いた値を保存すると、元の事実と導いた値が同じことを言い、片方だけが直されたときにどちらが正しいか決められなくなるからである。

その時点の値で決めて、後から同じ値を導けないものは、今の決まりで計算し直せるとしてもデータとして残す。業務が与えた値（貸したときに決まった返却期限）も、技術上の判断が与えた値（送った時点で選んだメールの送信事業者）も同じである。技術上の判断の値は業務のテーブルに置かず、その判断で動く技術処理の要求の列に置く。そこから導ける集まり（ある送信事業者で送った通知の一覧）は情報なので置かない。どの方式を選ぶかは物理設計でも、選んだ結果として後からの説明と回復に要る事実が生まれるなら、その事実はこの資料が持つ。

技術処理の要求のほかにも、後から導けず、失うと業務が続かない技術のデータ（外部の決済サービスが払い戻しの照会に求める取引の識別子など）がある。これは性質を「技術」としたテーブルに置き、根拠の欄は要件の品質要求を指す。どの製品に置くか、どう速く引くかは物理設計が決める。

要件に書かれた保存の形や方式（何をどの表に重ねて持つか、判定を速くするための表）は、要件の事実ではなく物理設計の候補として読む。そこから、後から導けない事実と、失うと業務が続かない事実だけを取り出し、形は型に従う。型で決まることは問わない。要件の記述との差は、資料の物理設計への申し送りの節に書く。後ろの資料の担当が読むべきことは、会話が終われば消える報告ではなく、資料に置く。

許す妥協は一つだけである。イベント列を選んだ対象のリソースは、例外なく `status` と `current_version` を持つ。どちらもイベントから導けるが、楽観ロックと業務の読み取りのために持つ。状態がいま一つしかなく版が動かない対象でも外さない。型が決めた要素を個々の資料の事情で外すと、同じ型の資料が読むたびに違う形になるからである。この妥協をほかの加工した情報へ広げない。

`status` の値は、業務知識の状態名の英名にする。業務知識が状態を持たないと書いた対象では、`status` をその対象を生んだ業務イベントの基底イベントの種類と同じ値にし、`current_version` を1にする。業務知識に無い状態名を作らない。後から対象を変える業務イベントが加わると、業務知識が状態を持つようになり、値の集合だけが変わる。

## 型の外の要素は、記録しないと誰が困るかで決める

型が決めた要素（業務のリソースの `status` と `current_version`、イベントの `version` と `occurred_at`、技術処理の三つの出来事）の外にある候補ごとに、それが無かったら誰が何をできなくなるかを言う。「〜のため」で終わる説明しか無ければ、外すか説明を足す。

列を足す理由は、今の業務知識にある行いだけに求める。まだ業務知識に無い行い（将来の付け替えや移し替え）のために、同じ値をリソースと出来事の両方へ先回りして写さない。今は同じ値を二か所に持ち、どちらを読むかという今要らない判断が生まれるからである。その行いが業務に加わったら、そのときに行った事実を足せば、前の値はそれより前の事実から分かる。

## 保存の単位は、守る決まりを一つの行と版で判定できるところで切る

リソース（同じものとして追い続ける対象）の単位は、一緒に守る業務の決まりが一つの行と版の中で判定できる単位にする。この基準で決まることは問わず、基準で決まらないときだけ grill で問う。入力にドメインモデルの資料があれば、その集約をリソースの単位にし、食い違いは提案として返す。無ければ同じ基準でここで決め、理由を資料に書く。

決まりが「同じ組み合わせで有効なものは一つ」なら、その組み合わせが一つのリソースで、始める・終えるは同じリソースの版を進める業務イベントになる。一回ごとに別の約束（その回だけの期限や条件）が生まれるなら、一回が一つのリソースになる。会員の講座への受講登録（同じ講座に有効な登録は一つ）は前者、図書館の一回の貸出は後者に当たる。決まりが複数の行にまたがる切り方は、同時実行の保証を行の集まりへ押し出す。業務の人が物として語らないもの（「取消済みの登録」）を一行の単位にしていないかも、業務の言葉で確かめる。見本の切り方には倣わず、その題材の決まりに基準を当てる。

## 保存の形とイミュータブルデータモデルの型

複数の意味ある業務イベントがあり、その順序、取消、訂正、または業務知識が求める「後から説明できること」に使うなら、イベント列を選び、イミュータブルデータモデルの型で書く。イベントが無いか乏しく履歴を使わないなら現在の状態、設定値のように過去の時点の値そのものを業務で使うなら有効期間の履歴を選ぶ。選んだ理由は資料に書く。

イミュータブルデータモデルの型は、三つのテーブルでできている。リソースは名前を対象の複数形（`loans`）にし、生まれたときに業務が与えた値と、`status` と `current_version` を持つ。基底イベントは、その対象に起きたどの業務イベントにも共通する事実で、名前は `<対象>_base_events` にし、対象への参照、種類、適用した後の版 `version`、起きた時点 `occurred_at` を持つ。対象と `version` の組は一意で、同じ事前状態から二つの出来事が成立する競合をここで検出する。詳細イベントは種類ごとに固有の事実で、名前は `<対象>_<過去分詞>_events` にし、主キーは基底イベントの識別子である。参照の向きは、リソース ← 基底イベント ← 詳細イベントの一方向にし、図ではリソースと基底イベントを関係の線で結ぶ。

イベントの表は追加だけにする。取消と訂正も元の行を書き換えず、元のイベントを参照する新しい業務イベントとして足す。イベントの表の時刻は、その出来事が起きた時点を表す `occurred_at` の一本だけにする。二本目の時刻が要るように見えたら、二つ目の出来事が起きているので、別のイベントの表にする。業務が与えた日付は起きた時点ではないので、詳細イベントの列にし、意味に「業務が与えた値」と書く。

## テーブルを定義するのは、そのテーブルへ書く業務の資料一本だけ

一つの事実の形を決めるのは、その事実を書く業務の資料だけにする。ほかの業務が書くテーブルを判断に読むとき（登録済みの利用者がいるか）は、定義し直さず、参照の表に読む列と持ち主の資料へのリンクだけを書く。同じテーブルを二本の資料が決めると、列の名前と意味が資料ごとに割れるからである。テーブルの持ち主は、依頼の入力である業務の分け方の一覧と、業務知識のコマンドから導けるので、別に合意しない。技術処理の要求は、その要求を同じ一回の変更で積む業務の資料が定義し、回収と成功もそこに置く。持ち主の資料がまだ置かれていなければ、定義し直さず、予定の置き場へのリンクで参照の表に書いて進む。そのとき、持ち主が決めるテーブル名と列名は推測で書かない。読む列の欄に `未定` とだけ書き、そのテーブルは図にもBDDの行にも載せない。持ち主の資料ができたら、同じ入口で深めて `未定` を持ち主の列に替える。仮置きの印を `未定` の一つに決めておけば、外したかを検査で確かめられる。

## 同期で行うと問題が起きる処理は、Outboxで分ける

メールの送信、外部への通知、注文の後の配送業者への出荷の依頼のように、業務の変更と同じ流れで行うと、外部の遅れや失敗が業務の変更まで止める処理がある。こうした技術処理は業務イベントと分け、要求、回収、成功の出来事で書く。形は [技術処理のライフサイクル](references/technical-process-lifecycle.md) に従う。保存先の製品、キューへの発行、キャッシュの作り直し、止まった要求を探す予定表は、運び方と速さの話なので書かず、資料の物理設計への申し送りの節に書く。

## 深めるときは、反証する主張を一つに決めてから観点を当てる

既存の資料を深めるときは、作成、更新、削除にかかわる主張を一つ選び、境界、順序、重複と繰り返し、同時実行、権限の中での悪用、時間、規則の変更の遡り、失敗したときに何が残ってよいか、を当てる。見るのは、残す事実や履歴や業務制約が変わるかである。index、DBMSの機能、分離レベルだけを変える論点は、資料の物理設計への申し送りの節に書く。

## 手順

1. 業務知識の資料と依頼を読み、調べれば分かることを確かめる。業務の分け方の一覧は依頼の入力で、無ければ最初の一問で依頼元と決める。業務知識、コマンドデータモデル、クエリデータモデルは、この順に前の資料を相手に確かめるので、作る順はこの依存で決まる。一覧にあるほかのコマンドデータモデルのうち置かれているものを読み、読むテーブルの持ち主を確かめる。一覧に無い業務が要ると分かったら、止まって依頼元へ返す。
2. grill の規律で、答えで記録する事実、保存の単位、履歴、保持、削除が変わる問いだけを問う。深めるときは、反証している主張を示す。保存の名前は問わない。
3. write-doc skill の `assets/templates/command-data-model.md`（節と検査が読む目印）、`assets/examples/command-data-model.example.md`（見本）、`references/writing-norms.md`（書くときの規範）を読み、直接書いて保存する。各BDDには固定した識別子、値、時刻、順序と一つのWhenを置き、BeforeとAfterには、そのWhenで読む・書くテーブルと、変わらないことを確かめるテーブルだけを具体的な行で置く。新しく作るときは、依頼にある置き場へ `command-data-model.md` の名前で保存する（名前の指定があればそれに従う）。置き場が依頼に無いときだけ問う。深めるときは同じパスへ戻す。仮説で置いたことは、その要素とBDDと未決に、仮説であること、根拠、採らなかった案を添えて書く。
4. 保存した資料を最初の引数に、置かれているほかのコマンドデータモデルを続けて渡し、`python3 scripts/immutable_model.py check <保存した資料の絶対パス> <ほかのコマンドデータモデルの絶対パス>...` を一回かける（パスはこの SKILL.md のディレクトリ基準）。合否は保存した資料の違反だけで決まり、ほかの資料は持ち主の解決と重複の照合に読むだけである。リンク先の資料がまだ無いことは未確認として出て、合否に数えない。違反が出たら本文を直して保存し直す。同じテーブルを二本の資料が分類している違反は、分け方の一覧で自分が持ち主なら相手の資料への変更案として報告に書き、そうでなければ自分の資料を参照に直す。同じ名前の列がリソースとその詳細イベントの両方にあると、確認を促す警告が出る。先回りした写しでないかを読み直す。隣の資料が後から置かれても、この検査はかけ直さない。

資料の集合がそろったら、依頼元が `python3 scripts/immutable_model.py check-set <置き場の全コマンドデータモデルの絶対パス>...` を一回かける。集合の検査は、それぞれの資料を順に判定し、残った違反と、まだ読めない持ち主のリンクと、持ち主の資料があるのに残った `未定` を違反として返す。照合の意味は、相手がそろったときに決まるからである。

## 停止条件

分からないことに出会ったら、答えによって資料の結論が変わるかで、止まるか進むかを決める。この資料の結論は、何を事実として記録するか、保存の単位と形、テーブルと列と業務制約、BDDごとのBeforeとAfterである。

結論が変わるなら、推測で埋めずに止まる。何も保存せず、何が分からないか、それで結論のどこが変わるか、推奨する答えと根拠を返す。記録するか、保存の単位、履歴を持つか、取消や訂正を新しい事実として積むか、技術処理を諦めてよいか、保持の理由と消してよい条件が決まらないときがこれに当たる。結論を変えず、列の値の細部や例の値にとどまるなら、最も筋の良い仮説を置いて進み、仮説であることを資料に書く。

業務知識の資料が無い、深める対象の資料にBDDかテーブルが無い、置き場が確かめられない、分け方の一覧に無い業務が要る、検査の違反を直せない、のどれかでも止まる。

## 報告

保存した資料の絶対パス（立てなかったときはその理由）、選んだ保存の単位と形とその理由、作成・更新・削除それぞれの扱い、定義したテーブルと参照したテーブル、BDDの数、対象外にした業務知識のBDDと理由、仮説として置いたことと根拠、未決と確かめる相手、業務知識への変更案、検査が未確認とした持ち主のリンクと `未定` として空けた列を返す。物理設計へ申し送る論点は資料の節にあるので、報告ではその節を指す。
