# イミュータブルデータモデルの型

イベントは成立した事実として追記する。出来事から導ける現在状態や版をリソースに重ねて保存するかは物理設計が決める。別のリソースにまたがる制約を一つのリソースの版で守れるとみなさず、この資料には競合する範囲と同時に成立させる事実を示す。

業務の状態が必要なら、その意味は業務知識のユビキタス言語に従う。業務知識に無い状態名を作らない。

イミュータブルデータモデルは、追い続ける対象のリソース、基底イベント、種類ごとの詳細イベントを使う。リソースの名前は対象の複数形（`loans`）にし、生まれたときに業務が与えた値を持つ。分類表でリソースの保存表現を「現在状態」としても、出来事から導ける状態を列に重ねる意味ではない。基底イベントは、その対象に起きたどの業務イベントにも共通する事実で、名前は `<対象>_base_events` にし、対象への参照、種類、確定順を表す `version`、起きた時点 `occurred_at` を持つ。対象と `version` の組は一意にする。詳細イベントは種類ごとに固有の事実で、名前は `<対象>_<過去分詞>_events` にし、主キーは基底イベントの識別子である。参照の向きは、リソース ← 基底イベント ← 詳細イベントの一方向にし、図ではリソースと基底イベントを関係の線で結ぶ。

各イベントに残す値は、業務知識が後から説明できると求める出来事へ戻って決める。当事者、場所、時点など、後から別の事実では再現できないものを落とさない。時点は基底イベントが持ち、種類ごとに異なる値を詳細イベントへ置く。

イベントの表は追加だけにする。取消と訂正も元の行を書き換えず、元のイベントを参照する新しい業務イベントとして足す。イベントの表の時刻は、その出来事が起きた時点を表す `occurred_at` の一本だけにする。二本目の時刻が要るように見えたら、二つ目の出来事が起きているので、別のイベントの表にする。業務が与えた日付は起きた時点ではないので、詳細イベントの列にし、意味に「業務が与えた値」と書く。
