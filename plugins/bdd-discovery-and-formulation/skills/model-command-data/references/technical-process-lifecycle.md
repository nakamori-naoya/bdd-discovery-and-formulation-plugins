# 技術処理のライフサイクル（Outbox）

技術処理では、頼んだ仕事が黙って消えず、完了したか再開が必要かを判断できる事実を残す。業務変更から起きる要求は、その業務変更と同じ一回の変更で確定する。要求を定義する資料が業務の資料と別でも、この保証を両資料の接続契約として示す。技術処理だけの資料は、品質要求と起因する変更契約を根拠にし、業務知識を作り足さない。

## 残す出来事を選ぶ

要求、引受け、成功、失敗、諦め、単位ごとの進捗のうち、後から導けず、失うと再開、重複防止、説明のいずれかができなくなる事実を残す。状態の上書きでは失われる経過が要求されるなら、出来事を追加して記録する。処理を諦めてよいかは、処理を頼んだ側の契約が決める。決まっていない打ち切りを型から加えない。

引受けを記録するのは、同時に二者が処理できない保証や、止まった担い手からの再開にその事実が要るときである。リースはその保証を作る一つの方法に過ぎない。採るなら、失効後の再開と遅れた担い手の成功が競合した結果を決める。失敗を記録するかも、診断、回復、監査にその事実が要るかで決める。リース失効だけから失敗の理由は分からない。

一つの要求が多数の単位に分かれるときは、どの単位の完了を失うと再開の起点や結果が変わるかを見て残す。対象の集合を要求から再現できるなら、単位を決めた出来事を別に積まない。再現できず全体の完了判定に集合が要るなら、集合を確定した事実も残す。速く続けるためだけの位置は物理設計に渡す。

技術処理の出来事は、追い続ける業務リソースの基底イベントと混ぜない。出来事ごとに残す時点は `occurred_at` とし、処理と事実を表す名前を付ける。具体的な表の数、回収の版、担い手、リース長は型から一律に決めない。必要なら、その根拠と未決を資料に示す。

## BDDで確かめること

この資料が定義する事実と契約に限り、要求の同時確定、重複、競合、途中停止、再開、完了を具体的なBeforeとAfterで確かめる。採らなかった引受けやリースの振る舞いをBDDへ加えない。ほかの資料が定義する事実は参照し、同じテーブルを定義し直さない。
