# 技術処理のライフサイクル（Outbox）

Outbox で分けた技術処理は業務の決まりではないが、頼んだ仕事が黙って消えないことをコマンドデータモデルで保証しなければならない。この文書は、その保証を持つテーブルの型を一つに決める。頼んだ仕事を諦めてよいかは、仕事を頼んだ側が決めることで、処理を担う側の型が決めることではない。だから型が決めるのは、諦めずに続けるための形だけである。

## 要求、回収、成功の三つの出来事

一つの処理のライフサイクルは、要求、回収、成功の三つの出来事でできている。どれも追加のみのイベントのテーブルにし、行を更新しない。状態の列で「処理中」「完了」を上書きすると、いつ誰が引き受け、何度やり直したかを後から説明できなくなるからである。

**要求**は、処理を頼んだという事実である。業務イベントと同じ一つの変更で記録する。こうすると、業務イベントが成立したのに要求だけが無い、という状態が起きない。要求は起因の業務イベント（基底イベント）を参照し、そこから導ける値（知らせる相手など）を写さない。ただし、その時点の値で決めて後から導けない技術上の判断（送った時点で選んだ送信事業者など）は、要求の列として持つ。

**回収**は、処理を担う側がその要求を引き受けたという事実である。回収のたびに一行を足し、要求の中での回収の `version` と、引き受けた担い手の識別子を持つ。担い手が無いと、止まった要求の原因を後から調べられない。回収してから一定時間（リース）を過ぎても成功が無ければ、その回収は失効し、要求は再び回収できる。リースが生きているかは、最新の回収の `occurred_at` と長さから導くので、期限の列は持たない。外部への通信はリースの間に行い、その間データベースの行を掴み続けない。

**成功**は、処理が終わったという事実である。一つの要求に一件だけで、どの回収で終わったかを参照する。

回収できる要求は、成功が無く、生きている回収も無い要求である。失敗は何も記録せず、リースの失効で同じ要求が再び回収されるのに任せる。何度失効しても要求は候補に残る。回収の回数や経過した時間は、観測と通知に使い、打ち切りには使わない。

## 諦める出来事は、頼んだ側が決めたときだけ置く

頼んだ側の業務知識か要件が「諦めてよい」と決め、諦めた後に誰が何をするかも決まっているときだけ、`<処理>_abandoned_events` のような諦めた事実の表を足す。それが決まっていないのに型の都合で打ち切りを置くと、「破棄しない」という要求とぶつかり、頼んだ仕事が黙って消える。諦めてよいかが決まらず、答えで資料が変わるなら、推測で置かずに問う。

## 一つの要求が多数の単位に分かれるとき

一つの要求を、宛先の範囲ごとのように多数の単位に分けて進めることがある。単位の完了を事実として残すのは、その完了を失うと再開の起点を決められない段か、やり直すと結果が変わる段だけにする。やり直しても結果が同じで、続きの位置が速さのためだけにあるなら、その位置は物理設計の継続の位置に置く。段の数は型で決めず、この基準で段ごとに決める。

どの段を残すにしても、要求全体の成功を判定するには、どの単位があるかという集合が要る。そこで、単位を決めたという事実を `<処理>_<単位>_planned_events` に追加のみで積み、残すと決めた段の完了を `<処理>_<単位>_completed_events` に積む。要求全体の成功は、決めたすべての単位が完了した後にだけ積み、その業務制約は二つの表を参照して書く。単位の大きさや並べ方は方式なので物理設計が決める。

## 命名と時刻

一つのライフサイクルのテーブルは、処理を表す同じ接頭辞と、出来事を表す過去分詞の `_events` でそろえる。延滞の通知なら `overdue_notice_requested_events`、`overdue_notice_claimed_events`、`overdue_notice_succeeded_events` である。処理の結果として受け手の側で起きること（利用者が通知を読んだ、など）で名前を付けない。この処理が直接担うのは、要求、回収、成功だけだからである。

時刻の列は、業務イベントと同じく `occurred_at` の一本にする。テーブルの名前が出来事を名乗っているので、時刻の列の名前で出来事を言い直さない。

技術処理は基底イベントを置かない。追い続ける対象（リソース）を持たず、要求そのものが最初の出来事で、回収と成功はそれを参照するからである。

リースの長さは、コマンドデータモデルが仮説の値として資料に書き、確かめる相手を未決に残す。

## 運び方と探し方は書かない

どの製品のキューへ発行したか、キャッシュをどう作り直すか、止まった要求を速く探すための予定表は、運び方と速さの話なので物理設計に置く。止まった要求は、リースの失効という事実から導けるので、探すための表をこの資料に置かない。外部と内部の食い違いを確かめる調停も、要求の出どころが業務イベントでなく調停の予定であるだけで、同じ三つの出来事で表す。

## BDDで確かめること

要求、回収、成功を通る正常例に加えて、少なくとも次を具体的な行で示す。リースの失効で同じ要求が再び回収されること。何度失効しても要求が回収の候補に残ること。同じ要求を二つの担い手が同時に回収しようとしたとき、一方だけが回収すること。単位に分かれる処理なら、すべての単位が完了するまで要求全体の成功が積まれないこと。諦める出来事を置いたなら、諦めた要求が以後回収されないこと。
