# 業務知識から、残す事実を論理データモデルにする

この入口は、domain-rule資料を根拠に、誰が後で何を判断し説明するために、どの事実を残すかを決め、BDD付きのRDB論理データモデル資料にする。テーブルの形は具体的な行で議論するので、資料の主役はBDDごとのBeforeとAfterである。RDB製品、DDL、index、分離レベル、再試行、性能はこの入口の外で、物理設計が決める。

根拠にするdomain-rule資料は必ず要る。テーブル名、画面、API、既存のDDLだけでは代わりにしない。無ければ、先にdomain-rule資料を作るよう返す。

作ることと深めることは同じ仕事で、違いはgrillで何を問うかだけにある。資料がまだ無いなら、何を記録するか、履歴を持つか、取消や訂正をどう残すかを問う。既存の資料を深めるなら、その資料の永続化の主張へ反例を当てる問いを立てる。

## 永続化のBDDとして採るものを、業務知識のBDDから選ぶ

domain-rule資料のBDDを掲載順に読み、正常な流れと、制約、同時に起きること、履歴、読み取りが結果を左右するものを、この資料のBDDとして採る。認可や、保存する前の受け付けだけで拒否が決まるものは採らず、対応表に対象外の理由を書く。domain-rule資料のすべてのBDDについて、対応するこの資料のBDDか、対象外の理由を追えるようにする。

作成、更新、削除のそれぞれに、BDDがあるか、業務上の理由で対象外かを決める。業務イベントで初めて成立した事実は作成、別の事実で現在の状態が変わるなら更新である。業務上の取消、失効、終了は削除ではなく、新しい事実を足すことである。削除は、保持する理由が尽きて消してよい条件が業務で決まっているときだけにする。

## 保存するのはデータだけで、情報は持たない

データは、起きたことをそのまま記録したものである。情報は、データを目的に合わせて解釈し、加工したものである。論理データモデルが保存するのは、起きた事実と、業務が与えた値だけにする。集計、件数、平均、順位、別の見方へ組み替えた一覧のテーブルや列は作らない。気温の記録があれば月の平均気温は計算で出せるので、平均気温のテーブルは作らない。導いた値を保存すると、元の事実と導いた値が同じことを言い、片方だけが直されたときに、どちらが正しいか決められなくなるからである。

業務が与えた値は、今の決まりで計算し直せるとしてもデータである。貸したときに決まった返却期限は、後で貸出期間の決まりが変わっても変わらない約束なので、決めたときの値を残す。判断に使うが集計して得る値（借りている冊数、延滞の貸出があるか）は列にせず、BDDのGivenにはその元になる事実の行を置いて、読むときに導く。

許す妥協は一つだけである。リソースのいまの状態`status`と現在の版`current_version`は、イベントから導けるが、楽観ロックと業務の読み取りのためにリソースの列に持つ。この妥協をほかの加工した情報へ広げない。性能のために導いた値を保存する判断は、物理設計が、理由と元の事実との整合の保ち方を添えて行う。

## 記録しないと誰が困るかを言えない要素は置かない

記録する候補ごとに、それが無かったら誰が何をできなくなるかを言う。「〜のため」で終わる説明しか無ければ、外すか説明を足す。モデルのすべての要素は、この資料のどれかのBDDに対応させる。

## 保存の形は、業務知識から選ぶ

複数の意味ある業務イベントがあり、その順序、取消、訂正を後から判断や説明に使うなら、イベント列を選び、イミュータブルデータモデルの型で書く。イベントが無いか乏しく履歴を使わないなら現在の状態、設定値のように過去の時点の値そのものを業務で使うなら有効期間の履歴を選ぶ。業務イベントという語があるだけでイベント列を選ばない。選んだ理由は資料に書く。

イミュータブルデータモデルの型は、三つのテーブルでできている。リソースは同じものとして追い続ける対象で、名前は対象の複数形（`loans`）にし、生まれたときに業務が与えた値と、`status`と`current_version`を持つ。基底イベントは、その対象に起きたどの業務イベントにも共通する事実で、名前は`<対象>_base_events`にし、対象への参照、種類、適用した後の版`version`、起きた時点`occurred_at`を持つ。対象と`version`の組は一意で、同じ事前状態から二つの出来事が成立する競合をここで検出する。詳細イベントは種類ごとに固有の事実で、名前は何が起きたかが分かる過去分詞の`<対象>_<過去分詞>_events`にし、主キーは基底イベントの識別子である。参照の向きは、リソース ← 基底イベント ← 詳細イベントの一方向にする。列の並びや表の置き方は、write-docの`rdb-logical-data-modeling`型が持つ。

## 成立した事実は書き換えず、時刻は出来事に一本だけ置く

イベントの表は追加だけにする。取消と訂正も元の行を書き換えず、元のイベントを参照する新しい業務イベントとして足す。成立した事実と現在の状態を、NULL、汎用の属性、JSON、削除フラグで一行へ押し込めない。成立した時点や種類が違う事実なら、表を分ける。

イベントの表の時刻は、その出来事が起きた時点を表す`occurred_at`の一本だけにする。出来事が起きた日を別の日付の列に持たない。業務がコマンドに時刻を渡すなら、それを`occurred_at`にする。二本目の時刻が要るように見えたら、二つ目の出来事が起きているので、別のイベントの表にする。業務が与えた日付（返却期限）は起きた時点ではないので、詳細イベントの列にし、意味に「業務が与えた値」と書く。

## 同期で行うと問題が起きる処理は、Outboxで分ける

メールの送信、外部への通知、投稿の後のタイムラインの更新のように、業務の変更と同じ流れで行うと、外部の遅れや失敗が業務の変更まで止める処理がある。こうした技術的な処理は業務イベントと分け、要求、回収、成功、失敗の四つの出来事で書く。形と、打ち切りの決め方は [技術処理のライフサイクル](references/technical-process-lifecycle.md) に従う。

## 同時に進んだとき、何を許さないかは業務の言葉で書く

複数の行にまたがる件数や不存在が成立を左右するとき（上限、重複の禁止）は、許される結果と許されない結果、競合する行の組を書く。どの分離レベルと再試行で守るかは物理設計が決めるので書かない。

## 深めるときは、反証する主張を一つに決めてから観点を当てる

既存の資料を深めるときは、作成、更新、削除にかかわる主張を一つ選び、境界、順序、重複と繰り返し、同時実行、権限の中での悪用、時間、規則の変更の遡り、失敗したときに何が残ってよいか、を当てる。見るのは、残す事実や履歴や業務制約が変わるかである。見つかった違いのうち確認できた修正は、BDD、事実、テーブル、列、業務制約へ戻す。index、DBMSの機能、分離レベルだけを変える論点は、この資料に混ぜず物理設計への申し送りとして報告する。

## 手順

1. domain-rule資料と依頼を読み、調べれば分かることを確かめてから、grillで問う。答えで記録する事実、履歴、保持、削除が変わる問いを選ぶ。深めるときは、反証している主張を示す。保存先が依頼に無ければ、利用者の資料の置き場と命名から提案し、それも問う。
2. 本文を組み立てる。各BDDには固定した識別子、値、時刻、順序と一つのWhenを置き、BeforeとAfterには、そのWhenで読む・書くテーブルと、変わらないことを確かめるテーブルだけを具体的な行で置く。domain-rule資料から採ったBDDを掲載順に先に置き、技術的な処理のBDDを後に置く。仮説で置いたことは、その要素とBDDと未決に、仮説であること、根拠、採らなかった案を添えて書く。
3. write-docで保存する。`document_type`は`rdb-logical-data-modeling`、新しく作るときは確かめた`output_directory`と`name`、深めるときは既存の資料を`update_target`にして同じパスへ戻す。同じパスに別の資料がある新規作成は、上書きせず別の名前を問う。
4. 保存したファイルに `python3 scripts/immutable_model.py check < <保存した資料の絶対パス>` を一回かける。この検査は、分類の表、erDiagram、テーブルの定義の見出しが同じテーブルの集合を指すか、イベントの表の名前と`occurred_at`と`version`が型のとおりかだけを見る。列が事実か情報かは読んで判断する。違反が出たら本文を直してもう一度保存する。

## 停止条件

分からないことに出会ったら、答えによって資料の結論が変わるかで、止まるか進むかを決める。この資料の結論は、何を事実として記録するか、対象ごとの保存の形、論理テーブルと列と業務制約、BDDごとのBeforeとAfterである。

結論が変わるなら、推測で埋めずに止まる。何も保存せず、何が分からないか、それで結論のどこが変わるか、推奨する答えと根拠を返す。記録するか、履歴を持つか、取消や訂正を新しい事実として積むか、保持の理由と消してよい条件が決まらないときがこれに当たる。結論を変えず、列の値の細部や例の値にとどまるなら、最も筋の良い仮説を置いて進み、仮説であることを資料に書く。

domain-rule資料が無い、深める対象の資料にBDDか論理テーブルが無い、保存先が確かめられない、grillかwrite-docが完了しない、検査の違反を直せない、のどれかでも止まる。

## 報告

保存した資料の絶対パス、選んだ保存の形とその理由、作成・更新・削除それぞれの扱い、論理テーブルとBDDの数、対象外にしたdomain-rule資料のBDDと理由、仮説として置いたことと根拠、未決と確かめる相手、物理設計へ申し送る論点を返す。
