# ユーザー目的達成BDDの正本を初めて作る

読み終えると、主たるユーザーが目的を達成するまでを、そのユーザーが観測できる場面の連なりとしてBDD正本1本へ保存できる。正本は業務の人と開発者が同じ流れを読むためのものであり、ユースケース、UX Journey map、業務ルールの網羅、保存構造、テスト仕様は別の正本が担う。

同じdirectoryの`playbook.yml`が工程順の正本である。このSKILLを読んだagentが、利用者の入力と明示された資料を保持したまま`steps`を宣言順に辿り、最後まで同じ文脈で判断する。`agent_work: invoking_agent`の工程はこのagentの認知工程、`skill:`の工程は同じpackageに同梱された同名skillの`SKILL.md`をこのagentが同じ文脈で読んで適用する工程、`script:`の工程は明示した入力から閉じた結果を返す決定論的tool、`playbook:`の工程は外部公開Skillの直接呼び出しである。

## 入力

| 入力 | 内容 | 満たさないときの扱い |
|---|---|---|
| `user_input` | 依頼文。誰が何を達成したいか、既知の役割、資料の置き場の指定 | 主たるユーザーか目的が読めなければ`settle`で問う |
| `referenced_artifacts` | 利用者が明示した既存資料の絶対path（業務知識、既存Journey、画面案など） | 相対path、読めないpath、symlinkは停止して確認する |
| `output_directory` | 正本を置く既存の書き込み可能な絶対directory | 下の「保存先の決め方」に従う |
| `name` | path要素を含まない`.md`file名。日本語名を許す | 同上 |

**保存先の決め方。** 依頼に資料構成が示されていれば、そのまま使う。示されていなければ、利用者の既存資料のdirectory階層と命名を読み、主たるユーザーごとに分ける置き場と名前を一度だけ提案して確認する。既定のpathを持たず、提案を繰り返さない。`output_directory`が存在しない、相対pathである、または同名fileがすでにある場合は、書かずに停止して利用者へ返す。同名fileが既存の正本なら、この入口では扱わず既存正本の反証（formulation）が該当すると報告する。

[入力に根拠づける規律](references/input-grounding.md)に従い、利用者の発言、明示された資料、`settle`で確認した決定だけを確定事項にする。

## 判断基準

| 観察対象 | 述語 | 行動 |
|---|---|---|
| 依頼の問い | 複数の意味ある場面が状態を受け渡し、観測可能な完了へ進む連続性を問うている | Journeyとして扱う。対象システム一つの責任、感情と接点、個別の業務判断、保存事実、操作列を問うているなら非該当理由と適切な成果物を返して停止する |
| 目的を持って始める役割 | 役割×目的の一覧で、今回作る1本が一つに決まる | その1本と残りの順番を`journey_set`として保持する。決まらなければ`settle`で問う |
| 場面や分岐の候補 | この違いが起きたとき、主たるユーザーが何を見て気づく | 書く。気づかないなら書かず、書かないことへの断り書きも書かない |
| `When`に置く役割 | 主たるユーザー自身、または主たるユーザーとやり取りする人である | 書く。通知基盤や集計処理のようなシステム上の主体は、主たるユーザーが観測する結果へ畳む |
| `Then`と完了条件 | 主たるユーザーが見る、知らされる、判断できる、次にできるようになる、のどれかで書けている | 書く。期間の開始、対象化、保存状態のような内部の成立だけなら、確認済みの時間境界を保ったまま利用者が観測する結果へ接続する。接続できなければ未決にする |
| 語彙 | 入力根拠にある利用者の言葉である | 使う。内部モデルの造語や未合意の呼び名は作らず未決にする |
| 成功に必要な前提 | 値ごと`Given`に書けている（境界値も含む） | 書く。業務知識の正本にあるという理由で省かない |
| 同じ主たるユーザー・同じ目的で条件だけが違う流れ | 同じJourneyの分岐として書ける | 1本の中の分岐にする。目的が違うなら別のJourneyとして`journey_set`の次候補へ置く |
| 前の場面の結果と次の場面の前提 | 前者から後者が成立する理由を説明できる | 接続として書く。説明できなければ未決にし、推測で埋めない |
| Journeyから外した事項 | 業務知識、非機能要件、別Journey、実現方式のどれに送るか決まる | 送り先を作業記録に残す |

場面数と資料の長さに上限を置かない。目的へ寄与しない場面、同じ結果を繰り返す場面、前後が接続しない場面だけを問題にする。

## 手順

1. **settle（`grill`）。** [実行指示書](references/execution-guidance.md)の観点を`context`と`questions`に渡し、入力から分からない点だけを1問ずつ確かめる。最初の問いは「目的を持って始める役割はどれとどれか、各役割の目的は何か」である。呼び方は[入れ子の段取りを呼ぶ](references/nested-playbook.md)に従う。返った`decisions`と`open_questions`を利用者入力・明示資料と突き合わせる。
2. **ground。** 依頼、参照資料、決定、未決を根拠・仮説・未確認へ区別して`grounded_input`として保持する。
3. **select-journey。** 役割×目的の一覧を作り、今回作る1本と残りの順番を`journey_set`として決める。
4. **map-journey。** 同梱skillの判断規律で、Journeyに該当するかを判定し、主たるユーザー、目的、開始地点、最終地点、完了条件、場面、状態の受け渡し、既知の分岐を`journey_map`として同じ文脈に保持する。
5. **compose。** [Journeyを判定し接続する判断規律](references/journey-judgment.md)、[Journeyの構造](references/journey-structure.md)、[場面のBDD](references/scenario-writing.md)、[BDDの前提・トリガー・失敗理由](references/scenario-premises.md)を適用し、場面ごとの`Given / When / Then`、条件マトリクス、完成本文を作る。冒頭の段落は、誰が何を達成するために、どこから始まり、何が観測できたら完了かを読み手の既知の語で文章として運ぶ。型の読み方の解説やメタ情報の一覧は本文に書かない。
6. **validate（`scripts/scenario.py`）。** 場面草案（`user-journey-bdd`型の本文記法: `## 場面 <連番>: <名前>`、コードフェンス内の`Given:` / `And:` / `When:` / `Then:`、失敗場面の`NOTE: Rule:` / `Source:` / `Reason:`、`**接続**:`）と条件マトリクスをsystem temporary directoryの一時fileへ書き、`python3 scripts/scenario.py check --file <場面草案> --matrix <条件マトリクスJSON>`を実行する。pathはこのSKILLと同じdirectoryを基準にする。stdoutにJSONを1行ずつ返し、終了codeは0が違反なし、1が違反あり（各行が`line` / `kind` / `detail` / `howto`）、2が入力を読めない。0以外なら資料化へ進まず、診断に従って`compose`へ戻る。
7. **document（`write-doc`）。** 完成本文を`{kind: text, content: <完成本文>}`の1要素配列で`material`に、`user-journey-bdd`を`document_type`に、確認済みの`output_directory`と`name`をそのまま渡す。返った結果の`status`が`completed`で、`path`が指定した保存先と一致することを確かめ、その`path`を`user_journey_bdd_path`にする。`failed`、結果欠落、path不一致なら理由を報告して停止する。
8. **後片付け。** 保存成功を確認した後に、自分が作った一時fileだけを明示pathで削除する。保存に失敗したときは残す。

## 停止条件

- 主たるユーザー、目的、開始地点、最終地点、完了条件のどれかが根拠から決まらない。不足項目と確認相手を返す
- 依頼がJourneyの問いではない。非該当理由と適切な成果物（ユースケース、UX Journey map、業務知識、データモデル）を返す
- `grill`が`completed`以外を返した、または`decisions` / `open_questions`が配列でない
- 検査が0以外で終了し、`compose`へ戻しても解消しない
- 保存先が確認できない、既存fileがある、`write-doc`が`completed`以外を返した

停止したときは、どこまで確定し、何が分かれば続けられるかを返す。既存のdomain-ruleやdata model資料は入力根拠として読むが変更せず、そこに不足が見つかれば未決として送り先を記録する。

## 報告

- 保存した正本の絶対path
- 主たるユーザー、目的、開始地点、最終地点、完了条件、場面数と主要な接続
- `journey_set`（役割×目的の一覧、今回作った1本、残りの順番）。正本には書かない作業記録である
- Journeyから外した事項と送り先（業務知識 / 非機能要件 / 別Journey / 実現方式）
- 未決の接続と、確認すべき人
