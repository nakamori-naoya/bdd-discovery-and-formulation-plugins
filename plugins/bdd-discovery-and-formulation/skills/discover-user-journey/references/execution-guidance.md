# User Journey BDD Discovery 実行指示書

## 背景と目的

この入口は、目的を持つユーザーが開始地点から複数の意味ある場面を経て、目的が満たされた最終地点へ到達するまでを、最初のBDD正本として共通理解にする。個々の決まりやデータ構造の網羅ではなく、目的達成までの連続性を主たるユーザーの観測で説明できることを優先する。

## 前提

- 1本の資料は1人の主たるユーザーと1つの目的を中心にする。条件の違いでは本数を増やさない。
- 目的達成に必要な場面数を先に制限しない。
- 利用者の発言、明示された資料、確認済みの決定だけを確定事項にする。
- 業務知識とデータモデルの資料は参照できるが、この入口から変更しない。
- テストの実行、環境、証拠収集は対象にしない。

## 各工程を実行するときの指示

### settle（grill）

最初に「目的を持って始める役割はどれとどれか、各役割の目的は何か」を確かめ、役割×目的の一覧を作れる状態にする。次に、今回作る1本について、誰が、何を達成したいのか、どの状態から始まり、何をもって最終地点へ到達したと判断するかを確かめる。その後、途中で主たるユーザーとやり取りする役割、各場面の働きかけと応答、前後の場面をつなぐ状態、既知の分岐、成功に必要な前提の値を1問ずつ確認する。画面やAPIの操作方法、保存方法、テスト方法は質問しない。

`context`には`purpose`（主たるユーザーの目的達成の連続性を最初の正本にする）、`audience`（業務の人と開発者）、`boundary`（ユースケース、UX Journey map、業務ルールの網羅、保存構造、実現方式、テスト実行は扱わない）を渡し、題材固有の観点は`questions`で渡す。

### select-journey

役割×目的の一覧から今回作る1本と残りの順番を決める。同じ主たるユーザーと同じ目的で条件だけが違うものは1本にまとめる。一覧は報告に載せ、正本には書かない。

### map-journey

目的ではなく機能利用が中心なら非該当として停止する。対象システム一つの責任だけを問うならユースケース候補、感情と接点の改善を問うならUX Journey map候補として返す。複数の意味ある場面が状態を受け渡し、観測可能な完了へ進むときだけJourney mapを作る。

### compose（本文の組み立て）

冒頭の段落で、誰が何を達成するために、どこから始まり、何が観測できたら完了かを文章で書く。場面を順番に並べ、各場面の結果から次の場面の前提へ自然に読み進められるようにする。説明文で接続をごまかさず、Given / When / Thenへ具体的な状態、働きかけ、応答を書く。文章の規律は[場面のBDD](scenario-writing.md)が持つ。

### document（write-doc）

`document_type`に`user-journey-bdd`を渡し、完成本文を`kind: text`の`material`として1本へ保存する。業務知識、データモデル、実装説明、テスト実行記録を混ぜない。保存先は`output_directory`と`name`でこちらが指定し、既存正本があれば上書きせず停止する。呼び方は[入れ子の段取りを呼ぶ](nested-playbook.md)に従う。
