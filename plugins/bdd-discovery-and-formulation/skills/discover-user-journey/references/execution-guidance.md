# User Journey BDD Discovery 実行指示書

## 背景と目的

この入口は、目的を持つユーザーが開始地点から複数の意味ある場面を経て、目的が満たされた最終地点へ到達するまでを、新しいBDDの正式な定義として共通理解にする。個々の決まりやデータ構造の網羅ではなく、目的達成までの連続性を主たるユーザーの観測で説明できることを優先する。

## 前提

- 1本の資料は1人の主たるユーザーと1つの目的を中心にする。条件の違いでは本数を増やさない。
- 目的達成に必要な場面数を先に制限しない。
- 利用者の発言、明示された資料、確認済みの決定だけを確定事項にする。仮説は仮説と分かる形で書く。
- 同種または関連する既存資料は探索の入力根拠になり得る。資料が存在するだけでは止まらず、指定された既存Journey正式な定義を反証して同じpathへ戻す依頼でない限りDiscoveryを続ける。
- 業務知識とデータモデルの資料は参照できるが、この入口から変更しない。
- テストの実行、環境、証拠収集は対象にしない。

## 各工程を実行するときの指示

### settle（grill）

`context`には`purpose`（主たるユーザーの目的達成の連続性を探索して新しい正式な定義にする）、`audience`（業務の人と開発者）、`boundary`（ユースケース、UX Journey map、業務ルールの網羅、保存構造、実現方式、テスト実行は扱わない）を渡し、題材固有の問いは`questions`で渡す。最初の問いは常に「目的を持って始める役割はどれとどれか、各役割の目的は何か」であり、役割×目的の一覧を作れる状態にする。各問いに、依頼と資料から最も筋の良い答えを推奨として添える。画面やAPIの操作方法、保存方法、テスト方法は質問しない。

#### 問いの選び方

依頼と資料を読み切った後に残る論点を、次の3段に分ける。**問うのは第1段と、grillの上限に枠が残れば第2段から**である。第3段は問わない。問えなかった論点と決まらなかった論点は、SKILL.mdの停止条件に従う。問う数の上限と対話の作法はgrillの公開契約に従う。

| 段 | 論点の性質 | 例 | 扱い |
|---|---|---|---|
| 第1段: 骨格 | 答えで主たるユーザー、目的、開始地点、最終地点、完了条件、今回作る1本が変わる。決まらないと場面の並びが変わる | 「目的を持って始める役割はどれとどれか、各役割の目的は何か」「今回の1本は誰の何の達成か」「どの状態から始まるか」「何を見て目的が達成されたと判断するか」 | 必ず問う |
| 第2段: 場面の接続 | 答えで場面の追加・分岐・接続の形が変わるが、両端は変わらない | 「途中で主たるユーザーとやり取りする役割は誰か」「前の場面の結果が次の場面の前提を成立させる理由は何か」「既知の分岐はどれで、元の目的へ戻るか別の終了か」「途中で止まったとき再開できる期限と条件は何か」 | 枠が残る分だけ問う。残りはSKILL.mdの停止条件に従う |
| 第3段: 前提の値と表記 | 答えで`Given`の値や場面名しか変わらない。または業務知識の資料で確認できる | 「成功に必要な前提の具体値（金額、期限）は何か」「その場面の呼び名は何か」 | 問わない。SKILL.mdの停止条件に従い、仮説として未決に推奨を書く |

同じ段の中では、答えが変える場面の数が多いものを先に選ぶ。保存先の提案が要るときは、成果物の置き場は利用者の資料構成に属するので第1段に数える。業務知識の資料で確認できる前提の値は問わず、資料から確かめた前提として`context`に含める。

### select-journey

役割×目的の一覧から今回作る1本と残りの順番を決める。同じ主たるユーザーと同じ目的で条件だけが違うものは1本にまとめる。一覧は報告に載せ、正式な定義には書かない。

### map-journey

目的ではなく機能利用が中心なら非該当として止まる。対象システム一つの責任だけを問うならユースケース候補、感情と接点の改善を問うならUX Journey map候補として返す。複数の意味ある場面が状態を受け渡し、観測可能な完了へ進むときだけJourney mapを作る。

### compose（本文の組み立て）

冒頭の段落で、誰が何を達成するために、どこから始まり、何が観測できたら完了かを文章で書く。場面を順番に並べ、各場面の結果から次の場面の前提へ自然に読み進められるようにする。説明文で接続をごまかさず、Given / When / Thenへ具体的な状態、働きかけ、応答を書く。仮説で接続した場面は仮説であることと根拠をその箇所に明示し、未決の節へ推奨・根拠・採らなかった解釈を並べる。文章の規律は`map-journey`で適用した同梱skillの場面のBDDが持つ。

### document（write-doc）

`document_type`に`user-journey-bdd`を渡し、完成本文を`kind: text`の`material`として1本へ保存する。業務知識、データモデル、実装説明、テスト実行記録を混ぜない。保存先は`output_directory`と`name`でこちらが指定する。出力先と同じpathのfileがあれば上書きせず、`settle`で確認した未使用の名前へ保存する。既存資料の存在だけでは探索を止めず、入力根拠として扱う。呼び方は同梱の内部skill `write-bdd`の入れ子の段取りを呼ぶ規律に従う。
