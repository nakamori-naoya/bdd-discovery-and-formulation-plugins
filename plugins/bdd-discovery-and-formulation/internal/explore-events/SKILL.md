# explore-events（業務で起きる事実を洗い出す）

読み終えると、根拠づけられた入力から、業務の側ですでに起きたこと（業務イベント）を起きた順に、引き金、担い手、前提、業務上の結果、確からしさ付きで一覧にできる。設計も資料の執筆もこのskillの外である。

## 入力

根拠づけられた入力（利用者の発言、明示された資料、確認済みの決定と未決の区別）を、この判断規律を適用するagentが同じ文脈に保持していること。入力が無ければ洗い出しを始めず、何が要るかを返す。

## 判断基準

[何を1件の事実として数えるか](references/grain.md)と、同梱の内部skill `write-bdd`の規律のうちアクターと利害関係者、業務イベント、概念の関係を読んでから始める。ここを読まずに始めると、粒度が途中で変わって並べ直せなくなる。

| 観察対象 | 述語 | 行動 |
|---|---|---|
| 候補の記述 | 業務の側ですでに起きたことを過去形の業務語で言える | 1件として採る。画面操作、保存、通知、バッチのような仕組みの都合は、その裏にある業務の事実へ言い換える |
| 1件の粒度 | 業務の人が1つのこととして語り、結果を別々に取り消せず、引き金が同じである | 1件にする。どれかが違えば分ける |
| 引き金 | 操作・時間・外部・連鎖のどれかに決まる | 記録する。時間と連鎖は現場から出てこないので「誰も何もしなかったら放置されるか」を問う |
| 確からしさ | 業務を知る人がその場で肯定した | `confirmed`。それ以外は`assumed`（根拠のある仮説）または`unknown`のまま先へ渡し、確定事項と混ぜない |
| 要求と事実 | 「〜してほしい」ではなく「〜された」である | 事実として採る。要求、内部の事実、外部契約は混同しない |
| 保存方式 | event recordやEvent Sourcingの採否を決めたくなる | 決めない。後続の永続化設計の関心である |

## 手順

1. [洗い出しの進め方](references/exploration.md)の順で、普通の流れを1本通してから、例外、時間、外部、後始末へ降りる。1つの事実について1つだけ問う。
2. 出た瞬間に、`起きたこと（過去形の業務語） / 担い手 / 引き金 / 前提 / 業務上どう変わったか / 確からしさ / 出所`を1件ずつ一覧へ入れる。会話が進むと誰が何を確かめたのかが混ざるので、まとめて後から入れない。
3. 語が揺れたら両方を出所つきで残し、どちらへ寄せるかは決めない。

## 停止条件

**止まる。** 根拠づけられた入力が無い（何を洗い出すのかが無い）。何が要るかを返す。

**仮説を明示して進む。** 次は止まらず、区別を保って先へ渡す。

- 業務の事実へ言い換えられない候補が残った。一覧へ入れず、何が分かれば言い換えられるかを出力に書く
- 担い手、引き金、前提が現場から出てこない。最も筋の良いものを`assumed`として置き、出所に根拠を書く
- 1つの題材で件数が増え続けて幹が読めなくなった。普通の流れを通す幹だけを残し、題材の分け方を出力に書く

## 出力

- 業務イベントの一覧（件数、各件の引き金・担い手・前提・結果・確からしさ・出所）と関係する役割
- 未確認のまま残った事実と、誰に聞けば確かめられるか
- 業務の事実へ言い換えられず、一覧へ入れなかったもの
