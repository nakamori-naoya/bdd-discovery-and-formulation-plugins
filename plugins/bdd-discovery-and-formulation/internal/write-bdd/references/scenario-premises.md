# BDDの前提・トリガー・失敗理由

BDDは、Given、When、Thenの三つを必ず持つ。Givenには結果の成立または拒否を判断するために必要な業務条件をすべて書き、WhenにはThenを発生させる一つの業務アクションまたは業務イベントを書く。どれか一つでも欠ける記述はBDDシナリオとして扱わない。

## 必要条件を暗黙にしない

必要条件を、`Background`、共通fixture、実行環境の既定値、前のシナリオ、一般常識へ委ねない。必要条件は事実ごとにGivenとAndへ一件ずつ書く。「その他の条件を満たしている」「それ以外は正常である」のような包括表現で置き換えない。

成功シナリオでは、成功に必要な条件をすべて成立させる。単一の失敗を検証するシナリオでは、検証対象の条件だけを不成立にし、その他の必要条件をすべて成立させる。境界シナリオでは検証対象だけを境界値にし、その他の必要条件をすべて成立させる。複数条件の相互作用を検証する場合は、対象となる条件をすべて明記し、単一失敗と区別する。

複数条件と完全に同義な合意済みの業務状態名は使える。ただし、その状態を構成する条件を同じ正式な定義から追跡できなければならない。「有効」「適切」「正常」のように展開できない語で必要条件を隠さない。

必要条件の集合または状態が入力根拠から決まらない場合、暗黙に成立したものとして扱わない。成果を左右するならgrillで確認し、確認できなければ最も筋の良い必要条件を仮説としてGivenに書き、その`source`を「仮説: <根拠>」としてBDDに仮説と分かる形を残し、問いを未決へ置く。

「Givenに書かれていない業務条件は結果に影響しない」と宣言するクロージャは置かない。前提の完全性は宣言ではなく、必要条件の列挙と条件マトリクスで確かめる。

## Whenはトリガーを書く

Whenには、Thenを発生させる一つの業務アクションまたは業務イベントを書く。状態の確認、資料の読解、期待結果の確認をWhenに置かない。Whenが二つ必要なら、別のシナリオへ分けるか、一方をすでに起きた事実としてGivenへ置く。

## 失敗理由を拒む理由へ結ぶ

失敗または拒否を期待するシナリオは、すべてのThenとAndの直後かつGherkinコードブロック内に`NOTE:`を置く。

同じ資料の業務の行いに書いた拒む理由を根拠にする場合は、`Rule:`にその拒む理由の名前を書く。

```gherkin
Then: 貸出は生まれない
  And: 利用者の貸出は変わらない
NOTE:
  Rule: 貸出上限に達している利用者が本を借りる
  Reason: 一人の利用者の貸出中と延滞の貸出は5冊を超えない
```

別資料の決まりを根拠にする場合は、`Source:`へBDD資料から正式な定義の見出しへ向けた相対Markdownリンクを書く。

```gherkin
Then: 貸出は生まれない
NOTE:
  Rule: 貸出上限に達している利用者が本を借りる
  Source: [図書館の貸出の業務知識](../domain/図書館の貸出.md#本を借りる)
  Reason: 一人の利用者の貸出中と延滞の貸出は5冊を超えない
```

成功シナリオには`NOTE:`を置かない。根拠となる拒む理由が無い、または参照先を特定できない場合は、失敗BDDを保存せず決まりの確定へ戻す。

## 条件マトリクス

BDD本文を書く前にJSONの条件マトリクスを作る。各シナリオについて、シナリオ名、種別、期待する成否、対象業務ルール、外部正式な定義、Whenのトリガー、必要な全前提、検証対象、入力根拠、失敗時のNOTEを保持する。

```json
{
  "scenarios": [
    {
      "name": "空きのない利用枠は予約できない",
      "kind": "single_failure",
      "expected": "failure",
      "rule": "予約が成立する条件",
      "source": "[貸会議室予約の業務知識](../domain/貸会議室予約.md#予約が成立する条件)",
      "trigger": {"kind": "action", "text": "予約者が対象の利用枠を予約する"},
      "premises": [
        {"text": "予約者は予約可能顧客である", "state": "satisfied", "target": false, "source": "予約が成立する条件"},
        {"text": "対象の利用枠には確定予約がある", "state": "unsatisfied", "target": true, "source": "予約が成立する条件"}
      ],
      "note": {
        "rule": "予約が成立する条件",
        "source": "[貸会議室予約の業務知識](../domain/貸会議室予約.md#予約が成立する条件)",
        "reason": "利用可能な予約枠が存在するという必要条件を満たさないため"
      }
    }
  ]
}
```

条件マトリクスの検査を通ったシナリオだけを資料へ写す。step数やExamplesの行列数に一律の上限を置かず、必要なGivenや代表例を量だけを理由に削らない。
