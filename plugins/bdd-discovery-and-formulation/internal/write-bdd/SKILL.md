# write-bdd（根拠づけられた入力からBDDを書く共通規律）

読み終えると、依頼と資料からBDDを書くときに、何を事実として書けるか、業務の言葉とは何か、シナリオ1件に何を必ず書くか、既存理解を反証してよい段階か、外部の段取り（`grill` / `write-doc`）へ何を渡し何を受け取るかを、このpackageの6つの公開入口と同梱skillが同じ基準で判断できる。この規律は成果物を作らず、適用する入口または同梱skillの工程の中で働く。入口ごとに違う判断（コアの線引き、Journeyの判定、永続化の3操作、論理構造への配置）はここに無く、それぞれの入口と同梱skillが持つ。

## 入力

この規律を適用する入口または同梱skillの`SKILL.md`と、その入口が同じ文脈に保持する利用者の入力、明示された資料、`grill`の結果。適用先の工程が無ければ何もしない。

## 判断基準

| 観察対象 | 述語 | 行動 |
|---|---|---|
| 事実として書く候補（用語、業務イベント、役割、決まり、記録する事実） | 利用者の発言、明示された資料、`grill`で確認した決定のどれかへ辿れる | 事実として書き、出所を辿れる状態にする。辿れなければ最も筋の良い候補を仮説として置き、仮説であることと根拠を該当箇所と未決に明示する。一般知識やもっともらしい例から補わない。[入力に根拠づける規律](references/input-grounding.md) |
| 語 | 業務関係者が仕事の会話と判断で合意して使い、仕組みを全部やめても残る | 業務の語として使う。部品名、保存方式、内部状態名、技術語を平易に言い換えた独自語は使わず、合意語が無ければ入力にある語を仮置きして未決にする。[ユビキタス言語](references/ubiquitous-language.md) |
| 役割 | 目的、権限、責任を持つ役割として言え、個人名や部署名ではない | 主アクター、支援アクター、利害関係者を分けて書く。各コマンドとクエリについて「誰が行えるか。本人以外が行ったとき誰の何が困るか」を問う。[アクターと利害関係者](references/actors-and-stakeholders.md) |
| 業務イベント | すでに起き、業務上の判断や状態を変えた事実を過去形の業務語で言える | 業務イベントとして採る。要求、通知、画面操作、内部の技術動作は業務の事実へ言い換える。[業務イベント](references/domain-events.md) |
| 概念の置き場（ドメイン、振る舞い、言葉、永続化、BDDの焦点） | どの問いで観察し、矛盾をどの観点へ返すかが決まる | その観点で形作り、他の観点へ送る事項を作業記録に残す。[概念の関係](references/concept-map.md) |
| domain-ruleへ残す候補 | 業務の目的、事実、状態、出来事、権利・義務、判断、成立条件、拒む理由として、実現方式を変えても同じ意味で残る | 業務知識として残す。ユースケースの処理順、画面・操作導線、API・メッセージ契約、データモデル・永続化、コード・層・配置、運用・非機能の実現方式ならdomain-ruleへ混ぜず、その関心が守ろうとしている業務上の意味だけを残し、元の記述と送り先を作業記録へ分ける。[概念の関係](references/concept-map.md) |
| BDDの番号 | 見出しが`### [BDD-<3桁以上の連番>] <業務結果>`で、番号が一つの資料の中で一意である | そのまま使う。番号の一意な範囲は資料一つであり、資料の種類ごとの接頭辞（`BDD-DM-`など）を足さない。ほかの資料やテストから指すときは、リポジトリ相対の資料pathと`#`と番号の組（`docs/lending/業務知識.md#BDD-003`）で指す。同じ資料の続いた番号をまとめて指すときは`BDD-001〜006`と書き、始まりと終わりを含む。更新で既存の番号を振り直さず、消したBDDの番号を別のBDDに再利用しない |
| BDD 1件 | Given / When / Thenを持ち、必要条件を事実ごとにGivenとAndへすべて書き、WhenはThenを発生させる業務アクションまたは業務イベント一つで、失敗・拒否ならThenの直後に`NOTE:`（`Rule:`、別資料なら`Source:`、`Reason:`）を持ち、条件マトリクスで全前提が対応している | 資料へ写す。包括表現やクロージャ宣言で必要条件を隠さない。Whenが二つ要るなら分ける。根拠となる業務ルールが無い失敗BDDは保存せず業務ルールの確定へ戻す。[BDDの前提・トリガー・失敗理由](references/scenario-premises.md) |
| 既存理解（定式化の入口） | 代表的な成功、業務上意味のある別経路、明らかな拒否を、アクター、事前状態、業務イベント、判断、結果、次状態で業務の言葉のまま説明できる | 反証へ進み、どの入力から読み取れたかと残る疑問が反証で扱う深さである理由を短く明示する。説明できなければ発見の段階なので、定式化の工程を始めず発見の入口が該当すると報告する。[定式化へ進める共通理解かを見極める](references/formulation-readiness.md) |
| 反証する主張（定式化の入口） | 反証する主張が一つ決まり、損失の大きさと不確かさで重要度を絞れる | その主張に対する境界、精度、状態、順序、同時実行、権限、時間、規則変更、失敗時保証の観点を当て、答えで本文の変更が一つに決まる問いだけを`grill`へ渡す。[重要なシナリオを見つけるQA観点](references/important-scenarios.md) |
| 外部の段取り（`grill` / `write-doc`） | `playbook.yml`の`requires`と一致する公開Skillへ契約入力objectを直接渡し、公開結果objectを直接受け取れる | 呼ぶ。相手の内部の工程、script、参考資料、設定に触れない。契約IDと版が異なる、必要な公開Skillが無い、結果の`status`や必須keyが契約と違うときは、それを受け取った入口の停止条件に従う。[入れ子の段取りを呼ぶ](references/nested-playbook.md) |

## 手順

1. 入口の手順に入る前に、この`SKILL.md`と、入口の工程が使う参照資料を同じ文脈で読む。発見の入口（`discover-*`）は入力根拠、ユビキタス言語、アクター、業務イベント、概念の関係、BDDの前提・トリガー・失敗理由、入れ子の段取りを読む。定式化の入口（`formulate-*`）はそれに加えて定式化へ進める見極めとQA観点を読む。同梱skill（業務イベントの洗い出し、永続化シナリオ、論理設計）は、その`SKILL.md`が指す資料を読む。
2. `grill`へ問いを渡すときは、入力根拠の規律で「調べれば分かること」を除き、QA観点で反証する主張と重要度を決めてから、答えで成果物の骨格または本文の変更が一つに決まる問いを成果を左右する順に並べる。上限と対話の作法は`grill`の公開契約に従い、返った`open_questions`の推奨を仮置きした未決として保持する。
3. 根拠づけられた入力（`grounded_input`）を作るときは、確認済み・仮説・未確認の区別を保つ。既存資料の記載も仮説であり得るので、記載済みという理由で確定事項にしない。domain-ruleを作成または更新する入口では、既存資料と追加材料を判断基準の「domain-ruleへ残す候補」で分け、実現関心は本文へ写さず、業務上の意味と送り先を保持する。
4. BDDと条件マトリクスを書くときは、判断基準の「BDD 1件」を1件ずつ満たし、条件マトリクスJSONを入口が宣言する検査toolへ標準入力で渡してから資料へ写す。検査の合否は構造契約だけを示し、業務上の正しさは同じagentが読んで判断する。
5. `write-doc`へ渡すときは、同じagentが組み立てた本文を`{kind: text, content: ...}`で`material`に、入口が決めた`document_type`、確認済みの保存先（新規は`output_directory`と`name`、更新は`update_target`）、入口の`references`をそのまま渡し、返った`status`と`path`を入口の手順どおりに確かめる。本文の節構成と記法は、その`document_type`をwrite-docが所有するtemplateが定める。このpackageは資料のtemplateを持たない。

## 停止条件

**止まる。** 適用先の入口または同梱skillが無い（何に適用するのかが無い）。この規律だけを呼ばれたときは、成果物を作らず、どの入口の中で働く規律かを返す。

**仮説を明示して進む。** 根拠へ辿れない候補、合意語の無い語、決まらない役割や必要条件は、止まる理由ではなく仮説を明示して進む理由である。最も筋の良い候補を仮説として置き、仮説であることと根拠を該当箇所と未決に書き、確認は成果物とともに求める。止まるかどうか（必須入力の欠落、公開契約に反する入力、toolの失敗、保存先の不確定）は適用先の入口の停止条件が決める。

## 出力

成果物は無い。適用先の工程が作る`grounded_input`、BDD、条件マトリクス、完成本文と、`grill` / `write-doc`との受け渡しが、この規律を満たしている。
