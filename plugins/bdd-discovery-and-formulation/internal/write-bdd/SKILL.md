# write-bdd（根拠づけられた入力からBDDを書く共通規律）

読み終えると、依頼と資料からBDDを書くときに、何を事実として書けるか、業務の言葉とは何か、シナリオ1件に何を必ず書くか、既存理解を反証してよい段階か、外部の段取り（`grill` / `write-doc`）へ何を渡し何を受け取るかを、このpackageの6つの公開入口と同梱skillが同じ基準で判断できる。この規律は成果物を作らず、適用する入口または同梱skillの工程の中で働く。入口ごとに違う判断（コアの線引き、Journeyの判定、永続化の3操作、論理構造への配置）はここに無く、それぞれの入口と同梱skillが持つ。

## 入力

この規律を適用する入口または同梱skillの`SKILL.md`と、その入口が同じ文脈に保持する利用者の入力、明示された資料、`grill`の結果。適用先の工程が無ければ何もしない。

## 判断基準

### 事実として書けるか

用語、業務イベント、役割、決まり、記録する事実は、利用者の発言、明示された資料、`grill`で確認した決定のどれかへ辿れるときだけ事実として書き、出所を辿れるようにする。辿れなければ最も筋の良い候補を仮説として置き、仮説であることと根拠を該当箇所と未決に書く。一般知識やもっともらしい例から補わない。詳しくは[入力に根拠づける規律](references/input-grounding.md)。

### 業務の言葉か

語は、業務関係者が仕事の会話と判断で合意して使い、仕組みを全部やめても残るものだけを使う。部品名、保存方式、内部の状態名、技術語を平易に言い換えた独自語は使わず、合意語が無ければ入力にある語を仮置きして未決にする（[ユビキタス言語](references/ubiquitous-language.md)）。業務イベントは、すでに起き、業務上の判断や状態を変えた事実を過去形の業務語で名付ける。要求、通知、画面の操作、仕組みの中の動作は業務の事実へ言い換える（[業務イベント](references/domain-events.md)）。

### 誰が行えるかを問うたか

役割は、目的、権限、責任を持つ役割として書き、個人名や部署名にしない。主アクター、支援アクター、利害関係者を分ける。業務の行いごとに「誰が行えるか。本人以外が行ったとき誰の何が困るか」を問う（[アクターと利害関係者](references/actors-and-stakeholders.md)）。

### domain-ruleへ残すか

業務の目的、事実、状態、出来事、権利と義務、判断、成り立つ条件、拒む理由として、実現方式を変えても同じ意味で残るものだけを業務知識に残す。ユースケースの手順、画面、API、データモデル、コードと配置、運用と非機能の実現方式は混ぜず、その関心が守ろうとしている業務上の意味だけを残し、元の記述と送り先を作業記録へ分ける。技術的な処理（回収、送達、再試行、調停）の送り先は論理データモデルである（[概念の関係](references/concept-map.md)）。

### BDDの一件は独立しているか

一件のBDDは Given / When / Then を持ち、必要な前提を事実ごとに Given と And へすべて書く。When は Then を起こす業務の行いか業務イベントを一つだけにし、二つ要るなら分ける。失敗と拒否は Then の直後に `NOTE:`（`Rule:`、別資料なら`Source:`、`Reason:`）を置く。包括的な表現や「他も同様」で前提を隠さない。根拠となる決まりが無い失敗BDDは確定したBDDとして書かず、決まりが無いことを未決に書く（[BDDの前提・トリガー・失敗理由](references/scenario-premises.md)）。

### BDDの番号は資料の中で一意か

見出しは `### [BDD-<3桁以上の連番>] <業務結果>` にし、番号は資料一つの中で一意にする。資料の種類を表す接頭辞は足さない。更新しても番号を振り直さず、消した番号を別のBDDに使わない。ほかの資料から一つのBDDを指すときは、リポジトリ相対の資料pathと`#`と番号の組（`docs/lending/業務知識.md#BDD-003`）で指す。同じ資料の続いた番号は`BDD-001〜006`とまとめて書け、範囲は始まりと終わりを含む。テストの中で BDD をどう表すかは、テストの規約が決める。

### 定式化へ進めてよいか（定式化の入口）

代表的な成功、業務上意味のある別の経路、明らかな拒否を、アクター、事前状態、業務イベント、判断、結果、次状態で業務の言葉のまま説明できるなら、反証へ進む。どの入力から読み取れたかと、残る疑問が反証で扱う深さである理由を短く書く。説明できなければ発見の段階なので、定式化を始めず、発見の入口が該当すると報告する（[定式化へ進める共通理解かを見極める](references/formulation-readiness.md)）。

### 何を反証するか（定式化の入口）

反証する主張を一つに決め、損失の大きさと不確かさで重要度を絞る。その主張に、境界、精度、状態、順序、同時実行、権限、時間、規則の変更、失敗時の保証の観点を当て、答えで本文の変更が一つに決まる問いだけを`grill`へ渡す（[重要なシナリオを見つけるQA観点](references/important-scenarios.md)）。

### 外部の段取りを契約どおりに呼んだか

`grill`と`write-doc`は、`playbook.yml`の`requires`と一致する公開Skillへ契約の入力objectを直接渡し、公開の結果objectを直接受け取る。相手の内部の工程、script、参考資料、設定に触れない。契約IDと版が違う、必要な公開Skillが無い、結果の`status`や必須keyが契約と違うときは、それを受け取った入口の停止条件に従う（[入れ子の段取りを呼ぶ](references/nested-playbook.md)）。

## 手順

1. 入口の手順に入る前に、この`SKILL.md`と、入口の工程が使う参照資料を同じ文脈で読む。発見の入口（`discover-*`）は入力根拠、ユビキタス言語、アクター、業務イベント、概念の関係、BDDの前提・トリガー・失敗理由、入れ子の段取りを読む。定式化の入口（`formulate-*`）はそれに加えて定式化へ進める見極めとQA観点を読む。同梱skill（業務イベントの洗い出し、永続化シナリオ、論理設計）は、その`SKILL.md`が指す資料を読む。
2. `grill`へ問いを渡すときは、入力根拠の規律で「調べれば分かること」を除き、QA観点で反証する主張と重要度を決めてから、答えで成果物の骨格または本文の変更が一つに決まる問いを成果を左右する順に並べる。上限と対話の作法は`grill`の公開契約に従い、返った`open_questions`は推奨を添えた未決として保持する。止まるか進むかは、呼び出した公開入口の停止条件が決める。
3. 根拠づけられた入力（`grounded_input`）を作るときは、確認済み・仮説・未確認の区別を保つ。既存資料の記載も仮説であり得るので、記載済みという理由で確定事項にしない。domain-ruleを作成または更新する入口では、既存資料と追加材料を判断基準の「domain-ruleへ残す候補」で分け、実現関心は本文へ写さず、業務上の意味と送り先を保持する。
4. BDDと条件マトリクスを書くときは、判断基準の「BDD 1件」を1件ずつ満たし、条件マトリクスJSONを入口が宣言する検査toolへ標準入力で渡してから資料へ写す。検査の合否は構造契約だけを示し、業務上の正しさは同じagentが読んで判断する。
5. `write-doc`へ渡すときは、同じagentが組み立てた本文を`{kind: text, content: ...}`で`material`に、入口が決めた`document_type`、確認済みの保存先（新規は`output_directory`と`name`、更新は`update_target`）、入口の`references`をそのまま渡し、返った`status`と`path`を入口の手順どおりに確かめる。本文の節構成と記法は、その`document_type`をwrite-docが所有するtemplateが定める。このpackageは資料のtemplateを持たない。

## 停止条件

**適用しない。** 適用先の入口または同梱skillが無い（何に適用するのかが無い）。この規律だけを呼ばれたときは、成果物を作らず、どの入口の中で働く規律かを返す。

**分からないことの渡し方。** 根拠へ辿れない候補、合意語の無い語、決まらない役割や必要条件は、確定として書かない。最も筋の良い候補を仮説として置き、仮説であることと根拠を該当箇所と未決に書いて返す。止まるか進むかは、呼び出した公開入口の停止条件が決める。

## 出力

成果物は無い。適用先の工程が作る`grounded_input`、BDD、条件マトリクス、完成本文と、`grill` / `write-doc`との受け渡しが、この規律を満たしている。
