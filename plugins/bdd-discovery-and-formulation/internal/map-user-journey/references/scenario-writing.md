# Journeyの場面をBDDで書く

## ストーリー全体と場面を分ける

ユーザーJourney全体には複数の意味ある場面がある。1つの巨大なGiven / When / Thenへ押し込まず、順番を持つ場面へ分ける。

```gherkin
### 場面 1: 目的が分かる名前

Given 開始地点または前の場面から受け取った状態
When 役割が行う主要な働きかけ
Then 役割が観測できる応答
And 次の場面へ渡る状態

接続: 次の場面は、この結果を前提として始まる
```

各場面は1つの主要な働きかけを持つ。ストーリー全体では場面ごとにWhen / Thenが繰り返されるため、長いインタラクティブな流れを表現できる。

各場面にはGiven、When、Thenを必ず一つ以上置く。WhenはThenを発生させる一つの業務アクションまたは業務イベントであり、状態の確認や期待結果の読解ではない。Givenにはその場面の結果に必要な開始状態と業務条件をすべて一件ずつ書く。前の場面から受け取る状態も、接続だけに任せず次の場面のGivenへ明記する。

失敗場面は、すべてのThenとAndの直後に`NOTE:`を置く。業務ルールが別資料にある場合は、`Source:`で正本の見出しを参照する。Journey資料へ業務ルール本文を複製しない。

## 書く高さ

- 主たるユーザーが行うこと、見えること、知らされること、判断できること、次にできるようになることを書く。判定は「この違いが起きたとき、主たるユーザーは何を見て気づくか」であり、気づかない違いは書かず、断り書きも書かない。
- `When`の役割は主たるユーザーか、主たるユーザーとやり取りする協働役割に限る。協働役割の働きかけを書く場合も、主たるユーザーの目的へどう届くかを切らない。システム上の主体は役割にせず、主たるユーザーが観測する結果へ畳む。
- `Then`と完了条件は主たるユーザーが観測できる結果にする。「期間が始まった」「論理上の対象になった」「状態が更新された」のような内部の成立だけでは完了にせず、利用者がその結果を何によって認識できるか、または何をできるようになるかまで書く。
- 成功に必要な前提は`Given`へ値ごと書く。業務知識の正本に境界値があっても、成功がその値に依存するなら値を書き、包含と除外を入れ替えない。その境界を満たすと利用者に何が見えるか、何ができるかとして結果へ写す。
- 入力根拠に現れる、利用者が実際に使う自然な動詞と状態の言葉を使う。内部実装の都合で作った状態名や、利用者が使っていない抽象的な造語へ言い換えない。必要な業務用語が未合意なら作らず、未決にする。
- 実現方式（UI部品、URL、API、通信形式、class、DB構造）と、テスト実行の関心（test runner、実行環境、試行回数、証拠、CI、flaky判定）は書かず、送り先を作業記録に残す。
- 業務ルールを新しく決めず、既存資料または確認済みの決定を根拠にする。データの保存方法や論理構造は設計せず、不足は業務知識またはデータモデルの未決へ送る。

内部状態しか根拠から確定できず、利用者が観測する結果を確定できない場合は、内部状態をJourneyの結果として採用しない。観測可能な結果を未決にし、内部状態の規律は業務知識またはデータモデルへ返す。

## 長さ

ストーリー全体の場面数とstep数は制限しない。長いこと自体を問題にせず、目的へ寄与しない場面、同じ結果を繰り返す場面、前後が接続しない場面を問題にする。
