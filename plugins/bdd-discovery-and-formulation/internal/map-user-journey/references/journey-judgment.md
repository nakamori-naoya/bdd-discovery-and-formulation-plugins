# Journeyを判定し接続する判断規律

Journey mapを作る工程とBDDを組み立てる工程で同じagentが適用する。初めて作る場合も、既存のJourney資料を反証する場合も同じ規律であり、既存本文を既成事実として追認せず同じ問いで判定し直す。

**判定の一問は「この違いが起きたとき、主たるユーザーは何を見て気づくか」である。** 気づくなら場面または分岐として書く。気づかないなら書かず、書かないことへの断り書きも書かない。

Journeyとして扱うのは、1人の主たるユーザーが1つの目的を持ち、開始地点から複数の意味ある場面を、状態の受け渡しによってつなぎ、観測可能な完了へ進む場合である。機能利用自体が目的、意味ある場面が一つだけ、対象システム一つの責任を問う内容はJourneyへ広げない。感情と接点はUX Journey、個別の業務判断は業務知識、保存する事実はデータモデルへ送る。既存本文がこれらへ変質していれば、同じ資料へ足さず移すべき資料と移動対象を報告する。

Journeyは目的ごとに1本である。同じ主たるユーザーと同じ目的で条件だけが違う流れは、本数を増やさず同じ1本の分岐として書く。目的または完了条件が二つなら同じJourneyに混ぜず、別Journeyにする。

各場面には、直前の状態、行う役割、一つの主要な働きかけ、観測できる応答、次の状態、次への接続を書く。行う役割は主たるユーザーか、主たるユーザーとやり取りする協働役割に限る。通知基盤や集計処理のようなシステム上の主体は役割にせず、主たるユーザーが観測する結果へ畳む。前の次状態と次の直前状態が意味上つながらなければ、最も筋の良い接続を仮説として書き、仮説であることと根拠を添えて未決にする。根拠のない接続を事実として書かない。

観測できる応答と完了は、主たるユーザーが何を見るか、何を知らされるか、何を判断できるか、または何をできるようになるかで判定する。内部の期間、記録、flag、対象集合などが成立したことだけではJourneyの応答にしない。時間境界が入力根拠にある場合は包含・除外を保ったまま、その境界によって変わるユーザーの観測または能力へ接続する。

分岐、中断、再開、役割移譲については、分かれる場面、残る状態、再開に必要な状態と期限、受け渡す責任と受け手が観測できること、目的達成へ戻るか別の終了になるかを示す。

Journeyから外した事項は、業務知識、非機能要件、別Journey、実現方式のどれへ送るかを区別して作業記録に残す。Journey資料には書かない。
