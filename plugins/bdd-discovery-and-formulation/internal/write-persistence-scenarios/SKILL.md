# write-persistence-scenarios（永続化シナリオを先に書く）

読み終えると、業務イベントと業務シナリオを資料上の順序で確認し、データの形を考える前に「何が起きたため何を残すのか」と「どの永続化保証が結果を左右するのか」を判定できる。採用した断面だけを永続化シナリオとして書き、作成・更新・削除の3操作と対象外理由を検討済みにする。エンティティ、テーブル、正本方式、投影はこのskillの外である。

## 入力

根拠づけられた入力、業務イベントの一覧と関係する役割、既存の業務シナリオまたは既存の論理設計資料を、この判断規律を適用するagentが同じ文脈に保持していること。資料に無い判断は補わず、未確認として止める。

## 判断基準

同梱の内部skill `write-bdd`の規律のうちアクターと利害関係者、業務イベント、ユビキタス言語、BDDの前提・トリガー・失敗理由を読んでから始める。

| 観察対象 | 述語 | 行動 |
|---|---|---|
| 業務シナリオ一覧 | 業務知識に掲載順がある | 順序を保って全件を棚卸しし、永続化シナリオに採用するか、業務知識だけに残すかを判定する。番号順へ並べ替えない |
| 正常系 | 現在状態、履歴、派生、または永続化された事実からの読み取り結果を作成・更新・参照する | 永続化シナリオに採用する |
| 拒否・失敗 | 一意性、参照整合、値域、原子性、冪等性、競合順序、履歴、または読み取り投影が結論を左右する | 永続化シナリオに採用し、どの保証が結果を決めるかを書く |
| 拒否・失敗 | 認可、未対応操作、または永続化前の入力受付だけで結論が決まり、論理制約、トランザクション、履歴、読み取り投影のどれも結果を左右しない | 永続化シナリオには採用しない。業務知識を正本として残し、対象外理由を対応表へ渡す |
| 変更なしのAfter | 全テーブルが変化しないことだけが採用理由である | 採用しない。変更なしでも一意制約や原子性などの永続化保証を検査するなら採用する |
| 作成の候補 | 業務上の事実が初めて成立する | 作成のシナリオにする |
| 更新の候補 | 別の事実によって現在状態が変わる。上書きか、新しい事実の追加かが決まっている | 更新のシナリオにする。訂正・取消は新しい事実の追加であり、物理削除と混ぜない |
| 削除の候補 | 保持理由が尽きて物理的に消せる条件が業務上決まっている | 削除のシナリオにする。業務上の取消・失効・終了は削除ではない |
| 各操作 | シナリオあり、または業務上存在しない理由がある | `covered`か理由つきの`not-applicable`として3操作すべてを記録する |
| 一つのシナリオ | 一つの業務イベントまたは技術的な失敗点と、一つの観測可能な永続化結果を持つ | 分ける。固定した識別子、値、時刻、到着順、失敗位置を使い、Whenを一つにする |
| 残す事実 | 現在状態だけでなく、後の判断、取消、訂正、説明に必要な事実が含まれる | 含める。誰が何を説明できなくなるかで判断する |
| 実現方法の語 | API、DTO、SQL、テーブル、ORMが混ざっている | 業務の言葉へ言い換える |
| 確からしさ | 業務を知る人が確認した | `confirmed`。未確認のシナリオは`assumed`（根拠のある仮説）または`unknown`として渡し、仮説に依存する記録は論理モデル側で仮説と明示させる |

## 手順

1. 利用者の業務シナリオ、業務イベントの一覧、業務資料を先に読み、業務知識の掲載順で全シナリオを棚卸しする。
2. 各業務シナリオを`採用 / 業務知識だけに残す`へ分け、`業務シナリオ / 永続化との関係 / 判定 / 永続化シナリオまたは対象外理由`として記録する。認可違反など永続化前に完結する拒否を、空のBefore/Afterを作る目的で採用しない。
3. 作成・更新・削除の各操作を`covered`（採用したシナリオあり）または`not-applicable`（業務上の理由）として記録する。
4. 採用した永続化シナリオを業務知識の掲載順で1件ずつ、`場合 / アクター / 事前状態 / 業務イベントまたは失敗点 / 条件 / 業務判断 / 業務上の結果 / 次状態 / 操作（作成・更新・削除） / 結果を左右する永続化保証 / 残す・変える・消せる事実 / 履歴（過去の何を残すか） / 保持（物理削除を許す条件） / 出所 / 確からしさ`で書く。原子性、冪等性、逆順到着、障害回復など永続化方式に固有のシナリオは、その後へ置く。
5. シナリオごとに条件マトリクスを作り、条件マトリクスJSONを標準入力で`python3 scripts/scenario_matrix.py check`へ渡す。pathはこのSKILLと同じdirectoryを基準にし、fileは介さない。stdoutにJSONを1行ずつ返し、終了codeは0が違反なし、1が違反あり（各行が`path` / `detail` / `howto`）、2が入力を読めない（空、不正JSON）。0以外なら診断に従ってシナリオを直す。単一失敗では検証対象以外の必要条件をすべて成立させる。

## 停止条件

**止まる。** 業務イベントの一覧と根拠づけられた入力が無い（何の永続化を書くのかが無い）。何が要るかを返す。

**仮説を明示して進む。** 次は止まらず、区別を保ってデータモデリングへ渡す。

- 3操作のどれかが`covered`とも`not-applicable`とも決まらない。業務の筋から最も筋の良い扱いを仮説として記録し、根拠を出力に書く
- 未確認（`assumed` / `unknown`）のシナリオが残る。確からしさをそのまま渡し、確認相手を出力に書く
- 業務上の取消と物理削除の区別が確認できない。更新（新しい事実の追加）を仮説とし、未決に書く

## 出力

- 永続化シナリオの一覧と操作別件数
- 業務知識の掲載順を保った採用・対象外の対応表と、対象外にした理由
- 3操作の検討状況（`covered` / `not-applicable`と理由）
- 追加記録にした変化、物理削除を許す条件
- 未確認のまま残ったシナリオと、確認相手
