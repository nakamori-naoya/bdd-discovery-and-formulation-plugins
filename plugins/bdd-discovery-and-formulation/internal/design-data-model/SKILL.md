# design-data-model（業務の永続化を論理設計する）

読み終えると、対応する業務知識と検査済みの永続化シナリオから、何を記録しないと業務が回らないかを先に決め、BDDシナリオを含むRDB論理設計の本文を作れる。保存の形から入らない。イミュータブルデータモデルは業務知識を分析した結果として選ぶ候補であり、業務イベントという語があるだけでは採用しない。記録の必要を説明できない要素は、手法が何であれ要らない。物理設計、移行手順、性能はこのskillの外である。

## 入力

| 入力 | 内容 | 満たさないときの扱い |
|---|---|---|
| 対応する業務知識 | 設計対象ごとに対応が分かる読み取り専用の業務知識資料。業務上の対象、状態、出来事、判断、取消・訂正を読む根拠 | 無ければ設計しない。テーブル、API、画面、既存DDLだけでは代替しない |
| 検査済みの永続化シナリオ | 3操作の検討状況と条件マトリクスの検査を通ったもの。確からしさ（`confirmed` / `assumed` / `unknown`）を保っている | 無ければ設計を始めず、何が要るかを返す。`assumed` / `unknown`のシナリオは仮説として写す |
| 手法（`modeling_method`） | 同梱の`fact-recording` / `normalized` / `dimensional`のID、または利用者の手法fileの絶対path。IDは`references/methods/<ID>.md`（[事実の記録](references/methods/fact-recording.md)、[正規化](references/methods/normalized.md)、[次元モデル](references/methods/dimensional.md)）に対応する | 依頼指定→文脈推定→利用者確認→仮説の順で決め、決め方を報告する。指したfileが無ければ止まる。先頭の候補だけを試さない |
| 既存の論理設計資料 | 更新の場合だけ | 新規なら無くてよい |

## 判断基準

[記録すべき事実のシナリオ](references/fact-recording-contract.md)、[Event Sourcing](references/event-sourcing.md)、[データモデル](references/data-models.md)、[イミュータブルデータモデルの型](references/immutable-data-modeling.md)、[技術処理のライフサイクル](references/technical-process-lifecycle.md)、[NULL回避](references/null-avoidance.md)、[関係データモデリングの原則](references/relational-data-modeling-principles.md)と、同梱の内部skill `write-bdd`の規律のうち業務イベント、概念の関係、BDDの前提・トリガー・失敗理由を読んでから始める。手法fileは選んだ1つだけを読む。利用者の手法fileは、同梱の3本と同じ節（先に決めること／成果物として出すもの／向くとき／向かないとき／見直しの問い）を持つことを確かめてから使う。

| 観察対象 | 述語 | 行動 |
|---|---|---|
| 業務知識のシナリオ | 正常系、または論理制約・トランザクション・履歴・読み取り投影が結果を左右する | 永続化シナリオとして業務知識の掲載順でBDDへ写す。認可や永続化前の入力受付だけで拒否が決まるものはBDDへ写さず、対応表へ対象外理由を残す |
| 記録候補の要素 | 記録が無かったとき、誰が何をできなくなるかを言える | 残す。「〜のため」で終わる説明しか無ければ外すか説明を足す |
| 成立済みの事実と現在状態 | 分けて表せる | 分ける。NULL、汎用属性、JSON、削除フラグで業務上の違いを隠さない |
| 分類表の `正式な定義` 列 | 複数の意味ある業務イベントがあり、順序、履歴、取消・訂正の事実を後から判断・説明する | 保存表現としてイベント列を候補にする。イベントが無いか乏しく履歴を使わないなら現在状態、設定値などの履歴そのものを業務で使うなら有効期間履歴、再計算できる読み取りなら派生を候補にする。列が選ぶのは保存表現であり、そこに保存する行は一次データ、投影が参照する列は再構築元として説明する。候補ではなく採用理由を資料へ書く |
| イベント表 | 一度成立した業務上の出来事を記録する | 更新・削除せず追加する。取消・訂正も元の行を書き換えず、元イベントを参照する新しい業務イベントとして記録する |
| イベント列と現在リソース | 同じ対象のイベントを現在リソースへ反映する | 現在リソースへ`current_version`を置き、最後に反映済みの対象内イベントversionと一致させる。直近イベントIDやイベント時刻は独立した記録理由がある場合だけ置く |
| イベント表の時刻 | 一つの出来事が起きた時点を表す | イベントの表ごとに時刻の列を一本だけ置く。業務イベントは基底イベントの`occurred_at`、技術イベントは出来事の過去分詞の`_at`にする。二本目の時刻が要るなら、それは別の出来事なので別のイベント表にする。リソースにはイベントから分かる時刻を写さず、業務が状態として読む時刻だけを置く |
| 業務知識と永続化設計 | 業務上の意味とデータモデル上の表現を区別できる | 業務知識は設計判断を拘束する正式な定義として読み、テーブル、列、保存表現、更新方式を追記しない。論理設計の `正式な定義` 列は保存表現の選択を記録し、その表現が保持する事実データと投影の再構築元は一次データとして本文に書く。意味の矛盾は業務知識の修正候補として分ける |
| 出来事の性質 | 顧客・業務担当者が意味を説明できる | 業務イベントにする。業務イベントを外へ知らせる、要求を回収して送る、再試行する、調停するといった技術的な処理は、業務イベントと分け、[技術処理のライフサイクル](references/technical-process-lifecycle.md)の要求・回収・成功・失敗の型で設計する。同じ入力で必ず失敗する要求が候補から外れる失敗の事実を必ず置く |
| `status`、完了日時、削除フラグ、条件付きNULL | 業務知識とBDDから、単なる実装都合ではなく独立した業務事実または現在状態として説明できる | 成立時点や種類が異なる事実なら関係またはイベントを分け、現在状態として必要なら理由を添えて残す。妥当性は名前の一致で機械判定せず、agentが業務知識とBDDを読んで判断する |
| Event Sourcing | 履歴が要るという理由だけで採りたくなる | 採らない。便益・費用・採否の問いで判断する |
| 手法 | 配置の仕方を決めるだけである | 何を記録するかは手法で決めない |
| モデルの各要素 | 記録理由を持ち、いずれかのシナリオへ対応する | 残す。対応しない要素は外す。仮説のシナリオにだけ対応する要素は、仮説であることと根拠を要素とBDDに明示する |
| 各永続化シナリオ | 本文末尾のBDDに独立した具体例として現れ、そのWhenで読む・書くテーブルと、変わらないことを確かめるテーブルだけが、BeforeとAfterに具体的な行で置かれている | 固定した識別子、値、時刻、到着順、失敗位置と一つのWhenで写す。関係しないテーブルは載せない。載せたテーブルは全カラムの見出しを持ち、0件なら見出し行と区切り行だけにする。拒否で変わらないことを示すテーブルは、Beforeと同じ行をAfterにも置く。変わったセルは太字にする |
| イベント列を選んだ対象 | 業務イベントを追加のみで記録する | [イミュータブルデータモデルの型](references/immutable-data-modeling.md)のリソース（`<対象の複数形>`）、基底イベント（`<対象>_base_events`）、詳細イベント（`<対象>_<過去分詞>_events`、主キーは基底イベントの識別子）で設計し、参照はリソース ← 基底 ← 詳細の一方向にする |
| 同時に進む操作 | 複数の行にまたがる件数や不存在が成立を左右する（上限、重複の禁止） | 許される結果と許されない結果を「並行実行で必要な保証」に書き、どの行の組が競合するかを示す。どの分離レベルとどの再試行で守るかは物理設計が決めるので書かない |
| 物理の関心 | RDB製品、DDL、index、パーティション、分離レベル、schema移行、性能測定が混ざっている | 外す。論理設計は論理テーブル、列、業務上のキー、関係、制約を確定する |

## 手順

1. 手法によらない部分を先に済ませる。永続化シナリオから、業務上の永続化が必要な事実を`モデル要素 / 記録する事実 / 記録しないと困ること / 必要とする人 / 出所 / 確からしさ`で洗い出す。
2. 業務知識の正式な定義を判断根拠に、分類表の`正式な定義`列で各記録対象の保存表現を現在状態、有効期間履歴、イベント列、派生から選び、理由を明示する。全論理テーブルを`系列 | 性質 | 論理テーブル | 正式な定義 | 時刻 | 変化 | 根拠`で一度だけ分類する。`時刻`にはイベント表の時刻の列名を一つだけ書き、リソースと詳細イベントは`なし`か業務が読む時刻の列名を書く。系列はリソース系／イベント系、性質は業務／技術／派生を区別する。業務イベント表は`変化`を`追加のみ`にし、保存するevent recordを状態再構築の一次データとして、そこから作る現在状態や検索用投影と区別する。
3. 選んだ手法fileの「先に決めること」に従って論理構造へ配置する。本文の節構成（目的と範囲、リソース系とイベント系、シナリオと記録の対応、論理データモデル図、論理テーブル定義、ライフサイクルと時間軸、並行実行で必要な保証、論理設計の完了条件、未決、BDD）と記法は、呼び出した入口が保存に使う`write-doc`の`rdb-logical-data-modeling`型（公開契約の`document_type`）が定める。このpackageは資料のtemplateを持たない。
4. 論理テーブルは`## 論理テーブル定義`の下へ`### \`table_name\`（業務上の名前）`として置き、列はbacktickで囲んだカラム名を1列目にした表で制約、型、NOT NULL、値域、業務上の意味を書き、業務制約は`#### 業務制約: <名前>`として根拠となるBDDへ結ぶ。この記法は`rdb-logical-data-modeling`型のtemplateが所有する機械可読契約である。イベント列を選んだ対象と技術的な処理は、型どおりの名前をER図、分類表、定義、制約、ライフサイクル、BDDで同じに使う。
5. 採用した業務由来の永続化シナリオを業務知識の掲載順で本文末尾の`## BDD`へ置き、その後へ永続化方式に固有のシナリオを置く。各BDDは`### [BDD-<連番>] <場合>`、`Given`、一つの`When`、`Then`を持ち、説明用の固定値を使う。`#### データの状態`の`Before`と`After`には、そのWhenで読む・書くテーブルと、変わらないことを確かめるテーブルだけを、同じ順序・全カラム見出しで具体的な行として置く。業務知識の全シナリオについて、対応するデータモデルBDDまたは永続化が関与しない対象外理由を対応表から追えるようにする。
6. 双方向で突き合わせる。モデルにあるのに記録の必要が説明されていない要素、記録すると決めたのにモデルに無いもの、入力された永続化シナリオがBDDとして本文に無いものが一つでもあれば、本文を完成扱いにせず直す。
7. 冒頭の段落は、誰が何を判断・説明するためにどの事実を残すのかを読み手の既知の語で文章として運ぶ。型の読み方の解説やメタ情報の一覧は本文に置かない。

## 停止条件

**止まる。** 設計しても成果にならない、または入力が契約に反する場合である。

- 検査済みの永続化シナリオが無い
- 対応する業務知識が無い、またはどの設計対象に対応するか分からない
- 指した手法fileが無い、または利用者の手法fileが同梱の3本と同じ節を持たない

**仮説を明示して進む。** 次は止まらず、仮説であることと根拠を本文に明示して完成させる。

- 手法が依頼・文脈・利用者確認のどれでも決まらない。記録対象・監査要件・分析目的から最も筋の良い手法を仮説として選び、決め方を報告する
- 双方向の突き合わせで片側にしかない要素が残り、根拠から解消できない。記録理由を説明できる側を仮説として残し、未決の節に問いを書く
- 仮説のシナリオに依存する要素がある。要素とBDDに仮説であることと根拠を明示する

## 出力

- 使った手法と、その決め方
- BDDシナリオを含む論理設計の本文（同じagentの文脈に保持する）
- 論理テーブル数、BDDシナリオ数、記録シナリオ数
- 未確認の記録と確認相手、手法の「見直しの問い」で引っかかった点
