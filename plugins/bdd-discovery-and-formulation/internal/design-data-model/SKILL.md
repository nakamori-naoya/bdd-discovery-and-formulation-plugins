# design-data-model（業務の永続化を論理設計する）

読み終えると、検査済みの永続化シナリオから、何を記録しないと業務が回らないかを先に決め、BDDシナリオを含むRDB論理設計の本文を作れる。保存の形から入らない。記録の必要を説明できない要素は、手法が何であれ要らない。物理設計、移行手順、性能はこのskillの外である。

## 入力

| 入力 | 内容 | 満たさないときの扱い |
|---|---|---|
| 検査済みの永続化シナリオ | 3操作の検討状況と条件マトリクスの検査を通ったもの。確からしさ（`confirmed` / `assumed` / `unknown`）を保っている | 無ければ設計を始めず、何が要るかを返す。`assumed` / `unknown`のシナリオは仮説として写す |
| 手法（`modeling_method`） | 同梱の`fact-recording` / `normalized` / `dimensional`のID、または利用者の手法fileの絶対path。IDは`references/methods/<ID>.md`（[事実の記録](references/methods/fact-recording.md)、[正規化](references/methods/normalized.md)、[次元モデル](references/methods/dimensional.md)）に対応する | 依頼指定→文脈推定→利用者確認→仮説の順で決め、決め方を報告する。指したfileが無ければ止まる。先頭の候補だけを試さない |
| 既存の論理設計資料 | 更新の場合だけ | 新規なら無くてよい |

## 判断基準

[記録すべき事実のシナリオ](references/fact-recording-contract.md)、[Event Sourcing](references/event-sourcing.md)、[データモデル](references/data-models.md)、[不変データモデリング](references/immutable-data-modeling.md)、[NULL回避](references/null-avoidance.md)、[関係データモデリングの原則](references/relational-data-modeling-principles.md)と、同梱の内部skill `write-bdd`の規律のうち業務イベント、概念の関係、BDDの前提・トリガー・失敗理由を読んでから始める。手法fileは選んだ1つだけを読む。利用者の手法fileは、同梱の3本と同じ節（先に決めること／成果物として出すもの／向くとき／向かないとき／見直しの問い）を持つことを確かめてから使う。

| 観察対象 | 述語 | 行動 |
|---|---|---|
| 記録候補の要素 | 記録が無かったとき、誰が何をできなくなるかを言える | 残す。「〜のため」で終わる説明しか無ければ外すか説明を足す |
| 成立済みの事実と現在状態 | 分けて表せる | 分ける。NULL、汎用属性、JSON、削除フラグで業務上の違いを隠さない |
| Event Sourcing | 履歴が要るという理由だけで採りたくなる | 採らない。便益・費用・採否の問いで判断する |
| 手法 | 配置の仕方を決めるだけである | 何を記録するかは手法で決めない |
| モデルの各要素 | 記録理由を持ち、いずれかのシナリオへ対応する | 残す。対応しない要素は外す。仮説のシナリオにだけ対応する要素は、仮説であることと根拠を要素とBDDに明示する |
| 各永続化シナリオ | 本文末尾のBDDに独立したシナリオとして現れ、BeforeとAfterへ全論理テーブルを同じ順序で全カラム見出し付きの表として置いている | 写す。0件でも見出し行と区切り行だけの表を省かず、変化しない表もBeforeと同じ全行をAfterへ再掲する。「レコードなし」「変更なし」のような説明文で表を代替しない |
| 物理の関心 | RDB製品、DDL、index、パーティション、分離レベル、schema移行、性能測定が混ざっている | 外す。論理設計は論理テーブル、列、業務上のキー、関係、制約を確定する |

## 手順

1. 手法によらない部分を先に済ませる。永続化シナリオから、業務上の永続化が必要な事実を`モデル要素 / 記録する事実 / 記録しないと困ること / 必要とする人 / 出所 / 確からしさ`で洗い出す。
2. 選んだ手法fileの「先に決めること」に従って論理構造へ配置する。本文の節構成（目的と範囲、リソース系とイベント系、シナリオと記録の対応、論理データモデル図、論理テーブル定義、ライフサイクルと時間軸、並行実行で必要な保証、論理設計の完了条件、未決、BDD）と記法は、呼び出した入口が保存に使う`write-doc`の`rdb-logical-data-modeling`型（公開契約の`document_type`）が定める。このpackageは資料のtemplateを持たない。
3. 論理テーブルは`## 論理テーブル定義`の下へ`### \`table_name\`（業務上の名前）`として置き、列はbacktickで囲んだカラム名を1列目にした表で制約、型、NOT NULL、値域、業務上の意味を書き、業務制約は`#### 業務制約: <名前>`として根拠となるBDDへ結ぶ。この3つの記法は、物理設計の入口が論理構造の指紋を計算する`rdb.py`が読む形であり、その型のtemplateが機械検査の記法として宣言する。
4. 全永続化シナリオを本文末尾の`## BDD`へ`### [BDD-<連番>] <場合>`、`Given`、`When`、`Then`の形で置き、BeforeとAfterの表で業務上の条件と結果をデータ構造から読めるようにする。拒否、取消、訂正、削除、同時進行で守るべき結果も必要に応じて追加する。
5. 双方向で突き合わせる。モデルにあるのに記録の必要が説明されていない要素、記録すると決めたのにモデルに無いもの、入力された永続化シナリオがBDDとして本文に無いものが一つでもあれば、本文を完成扱いにせず直す。
6. 冒頭の段落は、誰が何を判断・説明するためにどの事実を残すのかを読み手の既知の語で文章として運ぶ。型の読み方の解説やメタ情報の一覧は本文に置かない。

## 停止条件

**止まる。** 設計しても成果にならない、または入力が契約に反する場合である。

- 検査済みの永続化シナリオが無い
- 指した手法fileが無い、または利用者の手法fileが同梱の3本と同じ節を持たない

**仮説を明示して進む。** 次は止まらず、仮説であることと根拠を本文に明示して完成させる。

- 手法が依頼・文脈・利用者確認のどれでも決まらない。記録対象・監査要件・分析目的から最も筋の良い手法を仮説として選び、決め方を報告する
- 双方向の突き合わせで片側にしかない要素が残り、根拠から解消できない。記録理由を説明できる側を仮説として残し、未決の節に問いを書く
- 仮説のシナリオに依存する要素がある。要素とBDDに仮説であることと根拠を明示する

## 出力

- 使った手法と、その決め方
- BDDシナリオを含む論理設計の本文（同じagentの文脈に保持する）
- 論理テーブル数、BDDシナリオ数、記録シナリオ数
- 未確認の記録と確認相手、手法の「見直しの問い」で引っかかった点
