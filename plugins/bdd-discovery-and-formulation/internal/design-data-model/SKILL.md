# design-data-model（業務の永続化を論理設計する）

読み終えると、対応する業務知識と検査済みの永続化シナリオから、何を記録しないと業務が回らないかを先に決め、BDDシナリオを含むRDB論理設計の本文を作れる。保存の形から入らない。イミュータブルデータモデルは業務知識を分析した結果として選ぶ候補であり、業務イベントという語があるだけでは採用しない。記録の必要を説明できない要素は、手法が何であれ要らない。物理設計、移行手順、性能はこのskillの外である。

## 入力

| 入力 | 内容 | 満たさないときの扱い |
|---|---|---|
| 対応する業務知識 | 設計対象ごとに対応が分かる読み取り専用の業務知識資料。業務上の対象、状態、出来事、判断、取消・訂正を読む根拠 | 無ければ設計しない。テーブル、API、画面、既存DDLだけでは代替しない |
| 検査済みの永続化シナリオ | 3操作の検討状況と条件マトリクスの検査を通ったもの。確からしさ（`confirmed` / `assumed` / `unknown`）を保っている | 無ければ設計を始めず、何が要るかを返す。`assumed` / `unknown`のシナリオは仮説として写す |
| 手法（`modeling_method`） | 同梱の`fact-recording` / `normalized` / `dimensional`のID、または利用者の手法fileの絶対path。IDは`references/methods/<ID>.md`（[事実の記録](references/methods/fact-recording.md)、[正規化](references/methods/normalized.md)、[次元モデル](references/methods/dimensional.md)）に対応する | 依頼指定→文脈推定→利用者確認→仮説の順で決め、決め方を報告する。指したfileが無ければ止まる。先頭の候補だけを試さない |
| 既存の論理設計資料 | 更新の場合だけ | 新規なら無くてよい |

## 判断基準

[記録すべき事実のシナリオ](references/fact-recording-contract.md)、[Event Sourcing](references/event-sourcing.md)、[データモデル](references/data-models.md)、[イミュータブルデータモデルの型](references/immutable-data-modeling.md)、[技術処理のライフサイクル](references/technical-process-lifecycle.md)、[NULL回避](references/null-avoidance.md)、[関係データモデリングの原則](references/relational-data-modeling-principles.md)と、同梱の内部skill `write-bdd`の規律のうち業務イベント、概念の関係、BDDの前提・トリガー・失敗理由を読んでから始める。手法fileは選んだ1つだけを読む。利用者の手法fileは、同梱の3本と同じ節（先に決めること／成果物として出すもの／向くとき／向かないとき／見直しの問い）を持つことを確かめてから使う。

### それはデータか、情報か

データは、起きたことをそのまま記録したものである。情報は、データを目的に合わせて解釈し、加工したものである。論理データモデルが保存するのはデータ、すなわち起きた事実と、業務が与えた値だけにする。集計、件数、平均、順位、別の見方へ組み替えた一覧のように、データを加工して得る情報のテーブルや列は作らない。例外は一点だけで、リソースのいまの状態と`current_version`は、楽観ロックと業務の読み取りのために妥協として持つ。持つと、元の事実と導いた値が同じことを言い、片方だけが直されて食い違う。性能のために導いた値を保存する判断は、物理設計が理由と整合の保ち方を添えて行う。判断に使うが集計して得る値（借りている冊数、延滞の貸出があるか）は、BDDのGivenにはその元の事実の行を置き、読むときに導く。業務が与えた値（貸したときの返却期限）は、今の決まりで計算し直せるとしても、決めたときの値をデータとして残す。

### 記録しないと誰が困るか

記録候補の要素は、記録が無かったとき誰が何をできなくなるかを言えるときだけ残す。「〜のため」で終わる説明しか無ければ、外すか説明を足す。モデルのすべての要素は、いずれかの永続化シナリオへ対応する。仮説のシナリオにだけ対応する要素は、仮説であることと根拠を要素とBDDに書く。業務知識の全シナリオについて、対応するデータモデルのBDDか、永続化が関与しない対象外の理由を追えるようにする。認可や永続化前の受付だけで拒否が決まるシナリオはBDDへ写さない。

### どの保存表現を選ぶか

複数の意味ある業務イベントがあり、順序、履歴、取消・訂正を後から判断・説明するなら、イベント列を選び、[イミュータブルデータモデルの型](references/immutable-data-modeling.md)で設計する。リソース（`<対象の複数形>`、いまの状態と`current_version`を妥協として持つ）、基底イベント（`<対象>_base_events`）、詳細イベント（`<対象>_<過去分詞>_events`、主キーは基底イベントの識別子）を置く。参照はリソース ← 基底 ← 詳細の一方向で、競合はリソースの`current_version`と基底イベントの対象と`version`の一意で検出する。イベントが無いか乏しく履歴を使わないなら現在状態を、設定値などの履歴そのものを業務で使うなら有効期間履歴を選ぶ。選んだ理由を資料に書く。Event Sourcing は、履歴が要るという理由だけでは採らない。

### 一度成立した事実を書き換えていないか

イベントの表は追加のみにする。取消と訂正も元の行を書き換えず、元のイベントを参照する新しい業務イベントとして記録する。成立済みの事実と現在状態を、NULL、汎用属性、JSON、削除フラグで一行へ押し込めない。`status`、完了日時、削除フラグ、条件付きNULLは、業務知識とBDDから独立した事実として説明できるときだけ置き、成立時点や種類が違う事実なら関係かイベントを分ける。この妥当性は名前では判定せず、業務知識とBDDを読んで判断する。

### 時刻は出来事に一本か

イベントの表の時刻は、その出来事が起きた時点を表す`occurred_at`の一本だけにする。業務イベントの基底イベントも、技術処理のイベントも同じである。日付の列も時点であり、出来事が起きた日を別の列に持たない。業務が与えた日付（貸したときの返却期限）は起きた時点ではないので、詳細イベントの列にし、列の意味に「業務が与えた値」と書く。業務の時刻がコマンドの引数として与えられるなら、それを`occurred_at`にする。二本目の時刻が要るなら、それは別の出来事なので別のイベント表にする。

### 技術的な処理を分けたか

同期で行うと問題が起きる処理（メールの送信、外部への通知、投稿の後のタイムラインの更新）は、Outbox として業務イベントと分け、[技術処理のライフサイクル](references/technical-process-lifecycle.md)の要求・回収・成功・失敗の型で設計する。調停も同じ型で書く。同じ入力で必ず失敗する要求が候補から外れる失敗の事実を必ず置く。

### 同時に進んだとき何を許さないか

複数の行にまたがる件数や不存在が成立を左右するとき（上限、重複の禁止）は、許される結果と許されない結果、競合する行の組を「並行実行で必要な保証」に書く。どの分離レベルとどの再試行で守るかは物理設計が決めるので書かない。

### BDDの行で議論できるか

採用した永続化シナリオは、本文末尾のBDDに独立した具体例として置き、固定した識別子、値、時刻、到着順、失敗位置と一つのWhenで写す。BeforeとAfterには、そのWhenで読む・書くテーブルと、変わらないことを確かめるテーブルだけを、具体的な行で置く。載せたテーブルは全カラムの見出しを持ち、0件なら見出し行と区切り行だけにする。変わったセルは太字にする。

### 物理の関心が混ざっていないか

RDB製品、DDL、index、パーティション、分離レベル、再試行、schema移行、性能測定は書かない。論理設計は、論理テーブル、列、業務上のキー、関係、制約を確定する。業務知識には、テーブル、列、保存表現を追記しない。意味の矛盾は業務知識の修正候補として分ける。

## 手順

1. 手法によらない部分を先に済ませる。永続化シナリオから、業務上の永続化が必要な事実を`モデル要素 / 記録する事実 / 記録しないと困ること / 必要とする人 / 出所 / 確からしさ`で洗い出す。
2. 業務知識の正式な定義を判断根拠に、分類表の`正式な定義`列で各記録対象の保存表現を現在状態、有効期間履歴、イベント列、派生から選び、理由を明示する。全論理テーブルを`系列 | 性質 | 論理テーブル | 正式な定義 | 時刻 | 変化 | 根拠`で一度だけ分類する。`時刻`には、イベントの表なら`occurred_at`を、それ以外は`なし`を書く。系列はリソース系／イベント系、性質は業務／技術／派生を区別する。業務イベント表は`変化`を`追加のみ`にし、保存するevent recordを状態再構築の一次データとして、そこから作る現在状態や検索用投影と区別する。
3. 選んだ手法fileの「先に決めること」に従って論理構造へ配置する。本文の節構成と記法は、呼び出した入口が保存に使う`write-doc`の`rdb-logical-data-modeling`型（公開契約の`document_type`）が定める。このpackageは資料のtemplateを持たない。
4. 列の一覧は論理データモデル図（erDiagram）だけに書く。論理テーブルは`## 論理テーブル定義`の下へ`### \`table_name\`（業務上の名前）`として置き、何を一つの行にまとめるかと、図の一言で足りない列の意味だけを文章で書き、業務制約は`#### 業務制約: <名前>`として根拠となるBDDへ結ぶ。この記法は`rdb-logical-data-modeling`型のtemplateが所有する機械可読契約である。イベント列を選んだ対象と技術的な処理は、型どおりの名前をER図、分類表、定義、制約、ライフサイクル、BDDで同じに使う。
5. 採用した業務由来の永続化シナリオを業務知識の掲載順で本文末尾の`## BDD`へ置き、その後へ永続化方式に固有のシナリオを置く。各BDDは`### [BDD-<連番>] <場合>`、`Given`、一つの`When`、`Then`を持ち、説明用の固定値を使う。`#### データの状態`の`Before`と`After`には、そのWhenで読む・書くテーブルと、変わらないことを確かめるテーブルだけを、同じ順序・全カラム見出しで具体的な行として置く。業務知識の全シナリオについて、対応するデータモデルBDDまたは永続化が関与しない対象外理由を対応表から追えるようにする。
6. 双方向で突き合わせる。モデルにあるのに記録の必要が説明されていない要素、記録すると決めたのにモデルに無いもの、入力された永続化シナリオがBDDとして本文に無いものが一つでもあれば、本文を完成扱いにせず直す。
7. 冒頭の段落は、誰が何を判断・説明するためにどの事実を残すのかを読み手の既知の語で文章として運ぶ。型の読み方の解説やメタ情報の一覧は本文に置かない。

## 停止条件

**設計しない。** 設計しても成果にならない、または入力が契約に反する場合である。何が要るかを返す。

- 検査済みの永続化シナリオが無い
- 対応する業務知識が無い、またはどの設計対象に対応するか分からない
- 指した手法fileが無い、または利用者の手法fileが同梱の3本と同じ節を持たない

**分からないことの渡し方。** 手法が決まらない、双方向の突き合わせで片側にしかない要素が根拠から解消できない、仮説のシナリオに依存する要素がある、といった分からないことは、確定として書かない。最も筋の良い案を仮説として置き、仮説であること、根拠、採らなかった案を該当する要素とBDDと未決に書いて返す。止まるか進むかは、呼び出した公開入口の停止条件が決める。

## 出力

- 使った手法と、その決め方
- BDDシナリオを含む論理設計の本文（同じagentの文脈に保持する）
- 論理テーブル数、BDDシナリオ数、記録シナリオ数
- 未確認の記録と確認相手、手法の「見直しの問い」で引っかかった点
