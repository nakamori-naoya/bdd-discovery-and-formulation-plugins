# フォローの業務知識を判定する条件

この条件は、X のクローンのフォローの業務について、実行の担当が作った業務知識の資料（以下、資料）と grill の記録（以下、記録）を判定するためのものである。条件は判断の型だけを書き、正しい資料の中身は書かない。どの条件も、ほかの条件の出来、文体、見出しの形、表と文章の使い分けでは判定しない。資料や記録が存在しない、または空のときは、それを読む条件はすべて FAIL とする。

実行の担当は、要件と業務の分け方（split.md）だけを渡され、grill の問いには、要件にある事実で答え、要件に無ければ問いに添えた推奨を採り、推奨も無ければ未決に残すよう指示されていた。推奨を採った答えは、要件から決まったことではない。

## 業務と仕組みの境界

### boundary-no-mechanism

要件には、データベース、キャッシュ、非同期の反映、再試行、運用の目標、利用の回数の制限のような仕組みの話が、業務の成立条件と同じ段落に混ざっていた。

PASS：資料の業務の決まり、BDD の Given と Then、拒む理由のどこにも、仕組みを変えれば消える事柄（キャッシュ、反映の遅れや非同期、キュー、再試行、トランザクション、認証や認可の仕組み、画面の制御、製品名）が、成り立つ条件や結果として入っていない。仕組みに触れる文は、業務の外へ置いたことと送り先を述べる文に限られる。

FAIL：仕組みの事柄が、業務の決まりの条件、BDD の前提や結果、拒む理由として書かれている。

### boundary-value-placement

要件には、業務の判断を変える値と、応答の大きさや運用を守るための値が、同じ調子で書かれていた。

PASS：資料で業務の決まりとして書かれた値（人数、件数、回数、時間）は、何が成り立つか、何が表示対象か、どの順に並ぶかを変えるものだけである。一回に返す件数のように応答の大きさだけを変える値や、仕組みを守るための回数の制限は、業務の決まりに入らず、どこへ置いたかが一行で残っている。

FAIL：応答の大きさや仕組みを守るための値が業務の決まりとして書かれている。または、業務の外へ置いた値の行き場が書かれていない。

### boundary-kept-rules

要件では、仕組みの話と同じ段落に、フォローしたときに相手のどのポストが読める対象になるか、のような業務の決まりも書かれていた。要件を読んで、そうした決まりを確かめる。

PASS：仕組みの話を外すときに、同じ文脈にあった業務の決まりを捨てていない。その決まりの持ち主が別の業務なら、その業務へ委ねたことが資料に書かれている。

FAIL：フォローの変化で読める対象がどう変わるかのような業務の決まりが、書かれも委ねられもせずに消えている。

## 行いごとの決まり

### rules-who-can

PASS：資料の業務を変える行い（コマンド）と、業務を変えずに知る行い（クエリ）の一つひとつに、誰が行えるかが、その行いの節に書かれている。

FAIL：誰が行えるかが書かれていない行いが一つでもある。

### rules-command-and-query

PASS：コマンドの一つひとつに、成り立つ条件（境界の値を含む）、起こす業務イベント、拒む理由が書かれている。クエリの一つひとつに、何を表示するか（表示対象の条件）と、どの順に並べるかが書かれている。

FAIL：コマンドに成り立つ条件、業務イベント、拒む理由のどれかが欠けている。または、クエリに表示対象か並び順が欠けている。

### rules-rejection-linked

PASS：結果に拒否を含む BDD（行いが通らない、何も変わらない、という結果を持つもの。同時に起きた場面で通らなかった側も含む）はすべて、どの拒む理由によるかが結ばれている。根拠となる拒む理由が無い拒否を、確定した BDD にしていない。

FAIL：拒否の結果を持つのに、どの拒む理由によるかが結ばれていない BDD が一つでもある。

### rules-bdd-shape

PASS：BDD の Given は判断に要る前提を事実ごとに書き、「その他は正常」のような包括表現で前提を隠していない。When には業務の行いか業務イベントが一つだけある。ただし、同時に起きたときの決まりを示す BDD は、同時に起きる行いを When に並べてよく、どれが先に受け付けられたかを When か Given に書いていればよい。Then には業務上の結果が書かれている。

FAIL：Given に包括表現がある、同時に起きたときの BDD でないのに When に二つ以上の行いがある、または Then に業務上の結果が無い BDD が一つでもある。

### rules-concurrency

PASS：二つの要求が同時に来ると破れうる決まり（上限や重複の禁止）について、同時に起きたときの決まりが文章だけでなく BDD にも置かれ、通った側の結果と、通らなかった側に何が起きないかが書かれている。

FAIL：上限や重複の禁止があるのに、同時に起きたときの BDD が無い。または、通らなかった側に何が起きないかが書かれていない。

### rules-explanation

要件は、成立した事実と順序を後から説明できることを求めていた。誰に何のために説明するかが要件に書かれているかは、要件を読んで確かめる。

PASS：その要求が、誰に何のために説明するかと一緒に、常に守られることとして資料に書かれている。誰に何のためにかを要件から決められず、記録で推奨を採って決めたなら、資料の該当箇所か「まだ決まっていないこと」に、仮説であることが示されている。

FAIL：説明の要求が書かれていない。または、誰に何のためにかが書かれていない。または、記録で推奨を採って決めた相手や目的を、資料が仮説の印なしに断定している。

### rules-crud-coverage

PASS：フォローについて、作ること、変えること、なくすことのそれぞれに、BDD を置いたか、対象外としたかが資料から読み取れる。

FAIL：作る、変える、なくすのどれかについて、BDD も対象外の記述も無く、扱ったかどうかが読み取れない。

## 業務の言葉と持ち主

### language-naming

PASS：業務イベントは行った人が言う過去の形（「〜した」）で、状態はその状態にある人が自分の状況を言う言葉で名付けられている。業務の人が使わない説明のための語（「成立中」「有効フラグ」の類）や、テーブル名、列名、クラス名のような実装の名前で、業務の決まりや BDD を書いていない。

FAIL：業務の人が使わない説明のための語や実装の名前が、業務の語として資料に置かれている。

### language-ownership

この資料の書き手は、フォローの業務の語だけの持ち主である。利用者やポストのような語は別の業務の資料が持ち主で、その資料は書いた時点ではまだ存在しなかった。

PASS：ユビキタス言語の表で、別の業務が作り変える語は、持ち主をこの資料にせず、持ち主の資料へのリンクで示している。持ち主の資料がまだ無い語の英名を推測で書かず、`未定` として空けている。

FAIL：別の業務の語をこの資料が持ち主として定義している。または、持ち主の資料がまだ無い語に英名を推測で書いている。

### language-consistency

PASS：同じものを指す語が資料の中で揺れていない。一つのものを二つの語で呼んでいない。本文と BDD で使う語が、ユビキタス言語の表の語と一致している。

FAIL：同じものが二つ以上の語で呼ばれている。または、表に無い語で業務の決まりや BDD を書いている。

## 推測で埋めていないか

### guess-marked

PASS：資料に、仮説として置いたことと未決が、それと分かる形で書かれている。仮説の一つひとつに、仮説であること、根拠、採らなかった案が添えられている。未決の一つひとつに、何が決まれば決まるか、または誰に聞けば決まるかが添えられている。記録で推奨を採った答えは、どれも資料の仮説か未決に現れている。

FAIL：仮説や未決の印が無い。または、採らなかった案の無い仮説、誰に聞けば決まるかの無い未決が一つでもある。または、記録で推奨を採った答えが、資料で仮説とも未決とも示されずに断定されている。

### guess-foreign-owner

業務の分け方（split.md）は、業務の範囲と語の持ち主を決めていた。書かれていない持ち主の問いがあるかは、split.md を読んで確かめる。

PASS：別の業務が持ち主の事柄（ほかの業務の表示の決まり、配信の仕組み、利用者の登録など）を、資料が自分の決まりとして決めていない。split.md に無い持ち主の問いは、自分で決めずに未決か依頼元へ返す事柄として扱っている。

FAIL：別の業務が決めるべき事柄を、資料が自分の決まりとして断定している。

### guess-no-unmarked-specifics

PASS：資料で断定して書かれた業務の決まりに、要件から来ていない具体（数値、期限、役割、例外の経路、同時に来た要求のどちらを通すかの基準）が、仮説の印なしに混ざっていない。要件から来たかは、要件と記録を読んで確かめる。

FAIL：要件にも記録の要件の事実にも無い具体が、仮説の印なしに業務の決まりとして断定されている。

## grill の記録

### grill-answers

PASS：記録の問いが1問以上6問以下で、それぞれに推奨と、答えと、その根拠（要件のどこか、推奨を採ったか）が書かれている。要件を根拠に挙げた答えは、要件のどのファイルのどの記述かが特定され、その記述が要件に実際にある。要件の文から答えが一つに決まることを、わざわざ問いにしていない。最後に、決定と未決の一覧への合意が書かれている。

FAIL：上のどれか一つでも破れている。
