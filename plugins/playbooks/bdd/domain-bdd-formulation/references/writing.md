# シナリオの書き方

> **実装を一行も見ていない2人が、これだけを読んで同じ状況を再現し、同じ合否判定を下せること。**

迷ったらこの一文へ戻る。シナリオは試験コードの下書きではなく、ドメインエキスパート、エンジニア、PdMなどに繰り返し読まれる仕様である。自動化できることは価値ある副産物だが、実装へ寄せて意味を失ってはならない。

## 読み手の規律 — 曖昧さを残さない

### 値をどこまで書くか

上から順に判定し、どちらかに当てはまれば具体値を書く。

1. その値を変えると Then の合否が変わる。閾値、境界値、分岐を決める値がこれに当たる。
2. その step の主語が、その値を提供・主張する情報源である。申込者が自分の年齢を申告する、台帳が記録済みの残高を示す場合がこれに当たる。

どちらにも当てはまらない値は書かず、「有効な会員」のように合意済みの業務状態で書く。意味のないIDや日時を具体化すると、合否を決める値がノイズに埋もれる。

「正しい」「適切な」「十分な」のような評価語は既定では使わない。ただし、まだ値を知らない側が問い合わせる場面では使ってよい。具体値を書くと、その主体が知らないはずの正解を知っている状況になるからである。複数の主体が登場する場合は[登場人物と情報差](actors.md)も読む。

### 業務の言葉で書く

コードの変数名、条件式、関数名、テーブル名、task idを本文へ混ぜない。当事者が普段使う業務語、すなわちチームのユビキタス言語、制度名、正式な帳票名は残す。

コード上の根拠を残す場合は、シナリオ本文と分離したコメントまたは別の対応表へ置く。根拠が変わっても業務の振る舞いが同じなら、シナリオ本文は変えない。

### 主語を隠さない

一人称と代名詞を避け、「顧客」「担当者」「倉庫」のような役割名を書く。複数の主体が登場する文では、誰が、何を、誰に行うかを省略しない。

## シナリオ構造の規律

### Given／When／Thenの境界

| | 書くもの |
|---|---|
| **Given** | Whenより前から成立している静的な属性と、すでに起きた出来事 |
| **When** | これから検証する対象へ与える唯一の入力・契機 |
| **Then** | 実装を知らない人が観測して合否を判定できる業務上の結果 |

「内部で正しく判断する」は観測できない。誰が何を見られるか、何が成立するか、何をできないかで閉じる。Given、When、Thenの順序を入れ替えない。

**結果 → When → Given の順で考えてから、Given → When → Then の順に書く。** 結果から遡ると、必要な前提だけが残る。

### 1シナリオは1つの契機・1つの振る舞い

Whenは1つだけにする。Thenが複数行あってもよいのは、同じ業務上の振る舞いを別の観測点から判定する場合だけである。期待する振る舞いが違うなら分ける。

分割の基準は値の違いではない。

- Thenの種類が違う → シナリオを分ける
- Thenの種類は同じで、入力値だけが違う → 1つのシナリオテンプレートとExamplesを検討する

シナリオ名の枝番は、複数の振る舞いを詰め込んだ兆候として扱う。番号は必須にしないが、付ける場合は階層や文字サフィックスを持たないフラットな連番にする。どの状況を検証しているかは、番号ではなく一意で具体的なシナリオ名で説明する。

### Givenは事実ごとに1行

「〜であり、〜する」で複数の事実を結ばない。事実が増えたらAndで行を積む。必要な前提とstep上限の両立は[前提の書き方](given.md)に従う。

## 表（Examples）を使ってよいとき

次のどちらかに限る。

1. データの違いそのものが、その決まりの本質である
2. 1〜2語しか違わず、期待する振る舞いが同じシナリオが並ぶ

表の1列目には「何の場合か」を置く。行を足す前に、その値が何を意味するかを説明できるか確かめる。説明できない行は、網羅感のための水増しである。

## 背景と通しのシナリオ

Backgroundは使わないほうがよい。読む人が毎回先頭へ戻ることになり、1か所の編集が全シナリオへ効く。共通の前提が重複しても、各シナリオへ書くほうが読みやすい。

端から端までを示す通しのシナリオは数を最小限にし、個々の決まりを説明するシナリオとは別ファイルに置いて区別する。

## におい（見つけたら直す）

- 操作手順やコード上の条件を並べている
- 「または」で合否の異なる結果を1文にしている
- Whenが複数ある、またはThenが別々の振る舞いを扱う
- Givenの1行に複数の事実を詰め込んでいる
- 「正しい」「適切な」の中身を、値を知る側まで省略している
- Thenが内部判断で終わり、読み手が観測できない
- 名前が「テスト」「シナリオ8」のように意図を説明しない
- 自動化しやすくするために文言を変えている
- 表が巨大、列が使われていない、同じ意味の行が並ぶ

## 変えるとき

承認されたシナリオは、振る舞いが変わらない限り変えない。シナリオを変えることは仕様を変えることである。正しいと確信できないものは保存せず、答えの出ていない問いとして報告する。
