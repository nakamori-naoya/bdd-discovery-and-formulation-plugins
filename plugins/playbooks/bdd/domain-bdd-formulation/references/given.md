# 前提の書き方

前提の見落としは仕様の穴になる。読む人が別の初期状態を思い浮かべたまま、合意した気になるからである。同時に、結果へ影響しない前提を並べると、どれが決まりに効くのか読めなくなる。

## Givenに置くもの

Whenより前から成立している状態を宣言する。静的な属性だけでなく、すでに起きた出来事もGivenである。そこへ至る操作手順は書かない。

| 書く | 書かない |
|---|---|
| 予約が確定している | 予約画面で確定ボタンを押した |
| 締切を過ぎている | 締切時刻まで待った |
| 担当者が承認権限を持っている | 管理者としてログインした |

Givenは事実ごとに1行にする。別の事実が増えたらAndで積み、「〜であり、〜する」で結ばない。

## 要るか要らないか

各候補に2つを問う。

1. この前提が無かったらThenは変わるか。
2. この前提を反対の値にしたら、別のThenになるか。

変わらないなら消す。変わるなら残す。反対の値で別の結果になるなら、境界のシナリオ候補としても報告する。

「まだ本人確認をしていない」のような否定的前提も、同じ問いを通過した場合だけ書く。否定は無限に列挙できるため、後続の行為やThenを正当化しない否定は書かない。

## クロージャ宣言

候補を洗い出し、必要なGivenを残したら、シナリオの最後に次の1行をそのまま置く。

```gherkin
# クロージャ: このシナリオの Given に書かれていない業務条件は、成立・結果に影響しない。
```

これはstepではなく、このシナリオを閉じる仕様上の宣言である。書き漏らしと意図的な省略を読み手が区別できる。宣言できない条件が残っているなら、推測で閉じず、答えの出ていない問いとして報告して保存を止める。

## step上限に当たったら

上限を守るために、複数の事実を1行へ詰め込んだり、Thenに効く前提を省いたりしない。次の順に見直す。

1. 反対の値でもThenが変わらない前提を消す。
2. 複数の事実が合意済みの1つの業務状態と完全に同義なら、その状態名で書く。
3. 異なる振る舞いが混ざっているならシナリオを分ける。
4. それでも1つの振る舞いに必要なら、設定のstep上限を必要な範囲で上げる。

業務状態へまとめてよいのは、個々の事実が別々の分岐を作らない場合だけである。

## 見落としを探す問い

抜けやすい順に確認する。

1. **権限**: その人は、いつ権限を得て、いつ失うか
2. **過去の事実**: すでに一度行っていると結果は変わるか
3. **時間**: 締切の前後、ちょうどその時刻で結果は変わるか
4. **外部の状態**: 相手先の状態で結果は変わるか
5. **対象の存在**: 対象が無い、または消えているとどうなるか
6. **取り消せない履歴**: すでに確定して戻せないものはあるか
7. **他の人**: 同時に別の人が行動すると結果は変わるか

## 上向きに書く

結果から書き、次にWhen、最後にGivenへ遡る。前提から始めると、思いついた状況を全部並べやすい。Thenから遡れば、成立と合否へ必要な事実だけを選べる。
