# 工程間で受け渡すもの

入力は、`rdb-logical-data-modeling`型の既存RDB論理設計資料である。資料は、アクター、事前状態、業務イベント、条件、業務判断、業務上の結果、次状態、永続化する事実、残す履歴、物理削除を許す条件をBDDで結びつけている必要がある。白紙の業務理解から論理資料を新規作成するのは前段の責務である。

定式化では、作成・更新・削除に関係する既存BDDへ反例を当てる。更新は以前の事実を消すとは限らず、訂正、取消、差し替えを新しい事実として追加する場合がある。削除は、業務上の取消、失効、終了と、保持理由が尽きた後の物理削除を分ける。境界、順序、重複、同時実行、失敗によって残す事実が変わるなら、確認後にBDDと論理構造の両方へ戻す。

論理資料の更新先は入力と同じ絶対パスに固定する。新しい理解を別資料に置くと、発見時の代表BDDと定式化で得た境界BDDが別々の正本になる。未確認の問いは規則やThenとして確定せず、既存資料の未決へ戻す。

物理設計工程へ渡せるのは、確認済みの変更が同じ論理資料へ反映され、全BDDと記録すると決めた事実、論理テーブルが双方向で一致する場合だけである。

物理設計はBDDシナリオを再掲しない。論理設計で決めたテーブル、列、業務制約を増減・再編せず、対象RDBと版に固有の物理名、型、DB制約、index、分離レベル、パーティション、容量・性能・運用を加える。構造変更が必要なら物理設計で直さず、論理設計へ戻す。

indexを決める前に、業務で典型的かつ重要なReadを記録する。対象、絞り込み、結合、並び順、必要な鮮度、想定件数を持たないindexは採用しない。Readは物理設計の根拠であり、CUDへ関心を置く論理BDDには混ぜない。

分離性について、論理設計は許してはいけない同時実行結果と必要な保証を持つ。物理設計は`READ COMMITTED`、`REPEATABLE READ`、`SERIALIZABLE`などの分離レベル、併用する制約・ロック、競合時の再試行へ写す。対象製品・版で確認できない機能を使った物理設計は成果物として扱わない。
