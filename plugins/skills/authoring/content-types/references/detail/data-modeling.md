# RDB論理設計の型

**読み手**: 業務を知る人と、業務事実をRDBへ永続化する人

**目的**: 永続化の作成・更新・削除に関係する業務シナリオから、時間を越えて残す事実とRDBの論理テーブル構造を決める

**成功条件**: BDDシナリオ、記録する事実、論理テーブル・列・業務制約が双方向に対応し、物理設計の関心が混ざっていない

**境界**: RDBを前提に、業務イベントと事前状態から何を論理テーブルへ残すかを決める。論理テーブル、論理列、候補キー、参照関係、業務制約、正規化を扱う。DBMS製品と版、物理型、索引、分離レベル、DDL、API、DTO、ORM、画面は扱わない。

作成・更新・削除に関係する業務シナリオを独立したBDDにし、資料の最後にまとめる。BeforeとAfterには全論理テーブルを同じ順序で記載し、変化しない表も省略しない。モデルからBDDを説明でき、BDDから記録の置き場を辿れることを完了条件とする。
