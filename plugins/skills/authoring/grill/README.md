# grill

**合意に達するまで1問ずつ問い詰めて、曖昧さを潰す。**

**実装しないし、資料も書かない。** 決めたことと未決を残すところまで。

## 使う

```
/grill      詰める
```

## 3つの規律

**1問ずつ出す。** まとめて問うと、人は答えやすいものから答える。5問並べると難しい1問が黙って落ち、落ちたことに問うた側も気づかない。

**推奨回答を必ず添える。**「どうしますか？」は、考える仕事をそのまま相手へ渡している。推奨があれば、確認か修正だけで前へ進める。

**調べれば分かることは問わない。** 手元に答えがあるのに聞くのは怠慢である。調べて分かったら「この前提でいく」と宣言してから進む。

## 決定ログ

**このプラグインだけが状態を持つ。** 素材から作り直せるものは持たない、というのがこの一式の方針だが、**決定は会話の産物で再現できない**。「なぜそう決めたか」は、決めた場に居た人しか書けない。

```bash
scripts/decision.py add --topic <題材> --what <決めたこと> --why <理由> [--status decided|open|dropped]
scripts/decision.py render --topic <題材>     # 決定・未決・取り下げを並べる
```

**理由が空だと書けない。** 理由の無い決定は、後から読んだ人が覆せない（覆していいのかも分からない）。

**未決を無理に決めさせない。**「未決」と書いてあるほうが、間違った決定より役に立つ。

**取り下げたものも残す。** 消すと、同じ論点が数か月後にまた立つ。

## 設定

```yaml
# <repo>/.harness-plugins/grill.config.yml
version: 1
aspects: docs/guides/aspects.md   # 詰める観点を差し替える（同梱を使うなら business-rules のような名前）
log_dir: decisions                # 決定ログの置き場
instructions:
  questioning:
    directive: 観点を読み、調べて分からない未決事項を推奨回答つきで1問ずつ聞く
```

設定は自己完結させる。不足値を別の設定層から補わない。

**扱う題材によって観点は変わる。** 業務システムと社内ツールでは、詰めるべき場所が違う。

| `aspects` の値 | 使う観点 |
|---|---|
| 空（既定） | `default` — スコープ・不変条件・状態遷移・権限・境界値など10観点 |
| `business-rules` | 業務そのものを確定させる12観点。作りの都合を問わない |
| パス（`/` か `.` を含む） | そのファイル。repo root からの相対、または絶対 |

**指定したのにファイルが無ければ止まる。** 同梱の名前でもリポジトリのパスでもないものは、既定へ倒さず落ちる。

## しないこと

- 実装しない。資料も書かない
- **一度に大量の問いを浴びせない**
- 推奨回答なしで丸投げしない
- **中身を機械で検査しない。** 問いの数も観点の網羅率も数えない
