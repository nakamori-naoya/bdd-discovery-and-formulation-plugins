# RDB物理設計の成果物契約

物理設計資料は、対象RDBと版、入力となった論理データモデルを冒頭に明記する。BDDシナリオは論理設計資料にだけ置き、物理設計へ再掲しない。その後に、次の見出しをこの名前で一つずつ持つ。

- `## 対象と論理設計`
- `## 物理制約`
- `## 物理化の方針`
- `## index`
- `## トランザクションと分離レベル`
- `## パーティションと配置`
- `## 容量・性能・運用`
- `## 採用するRDB機能`
- `## 物理設計の完了条件`
- `## 未決`
- `## 代表的な読み取り`

論理モデルのER図、テーブル、カラム、CUDのBDD、Before / Afterは物理設計へ複製しない。入力論理資料を一つ明記し、`rdb.py fingerprint`が返す論理構造の指紋を記録する。`rdb.py check`は現在の論理資料から指紋を再計算し、物理設計時からテーブル・列・業務制約が変化していないことを検査する。その構造を固定したうえで、物理制約、物理化の方針、index、分離性、配置、運用だけを書く。論理構造の増減や再編が必要なら、物理設計で補わず論理資料へ戻す。

代表的な読み取りは`### Read-<連番>: <業務上の読み取り>`とし、利用者と目的、入力・検索条件、結合、並び順と上限、返す情報、必要な鮮度と一貫性、想定件数、SLO、支えるindex、対象版での実行計画を持つ。indexは`### index: <名前>`とし、根拠となるReadまたは制約、対象列・式と順序、列順の理由、書き込みへの費用、確認方法を持つ。分離性は`### 分離性判断: <判断名>`、採用機能は`### 機能: <機能名>`と書く。機能名は機能根拠台帳の名前と一致させる。

分離性判断は次の項目を一つずつ持つ。

- `- 同時に進む操作:`
- `- 許してはいけない結果:`
- `- 発生し得る現象:`
- `- 選択する分離レベル:`
- `- 併用する仕組み:`
- `- 対象バージョンでの確認:`
- `- 競合時の扱い:`

論理設計が要求する保証は業務上の必要条件であり、物理設計ではそれを対象RDBの分離レベルと実現機能へ写す。`READ COMMITTED`、`REPEATABLE READ`、`SERIALIZABLE`などの名称だけで済ませず、対象版の挙動と競合時の扱いまで決める。

資料の冒頭には次の3行を置く。

```text
- 対象DBMS: <製品>
- 対象バージョン: <版>
- 論理モデル: <入力ファイル名>
- 論理構造の指紋: sha256:<rdb.py fingerprintが返したdigest>
```

CREATE文やmigration全体は資料へ複製しない。分離性を説明する短いtransaction例は、競合検知、rollback、再試行を再現するために必要な範囲だけ置ける。中心は、論理構造を変えずに、対象版の制約、index、分離レベル、配置、容量・性能・運用へ落とすことである。
