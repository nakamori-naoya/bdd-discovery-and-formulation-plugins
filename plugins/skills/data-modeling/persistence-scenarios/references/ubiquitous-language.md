# ユビキタス言語を育てる

**ユビキタス言語は、業務の人の言葉を出発点に、専門家と作り手が同じ判断をできるところまで育てた言葉である。** 単語を集めた用語集でも、既存の社内語をそのまま正解にしたものでもない。会話、具体例、ルール、仕様、そしてドメインを表すコードで、同じ概念と関係を使う実践である。

## 言葉は使われ方によって意味を持つ

「予約」の意味は、一行の定義だけでは決まらない。予約できるのは何か、いつ成立するか、誰にどんな約束が生まれるか、期限を過ぎると何ができなくなるかを語る中で意味が現れる。同じ「予約」という音を使っていても、飲食店では席の確保、貸出業務では在庫と受取期限の確保、会計では将来計上の見込みを指すかもしれない。

したがって、ユビキタス言語を確かめるときは「この語の定義は何か」だけを聞かない。その語を使って、典型例、成立しない例、境界ぎりぎりの例を説明してもらう。何を同じものとして数え、何が違えば別の扱いになり、どの事実によって判断が変わるかを確かめる。

## 業務の言葉を出発点にする

候補は、業務に責任を持つ人が仕事を考え、相談し、判断するときに実際に使う言葉から探す。「申込みが届いた」「承認待ちである」「受取期限を過ぎた」「配送開始後の変更は拒否する」のような言葉は、業務で起きる事実、状態、役割、判断を表している。

ただし、現場で使われているだけでは十分ではない。同じ語を部署ごとに違う意味で使っていることも、長年の略語が本来別の状態を隠していることもある。専門家の言葉を尊重するとは、無批判に転記することではない。具体例でずれを見つけ、必要なら名前を分け、関係を言い直し、業務の人自身が判断に使える言葉へ整えることである。

## 何がユビキタス言語で、何がそうでないか

ユビキタス言語に属する語は、ソフトウェアをすべて置き換えても業務上の概念として残る。業務の人がその語で例の正誤を判断でき、その言葉を使うことで役割、状態、出来事、規則の関係が明確になる。そして、意味が通用する範囲が分かっている。

一方、`ReservationDto`、`POST /reservations`、`status_code = 409`、`reservation_table`、キュー名のような語は、実現方法を説明する技術言語である。技術設計には必要だが、それだけでは業務の言葉ではない。「409を返す」を「配送開始後の変更を理由つきで拒否する」と言い換えたとき、初めて業務判断が見える。ボタン名や画面遷移も、それが業務上の行為や出来事ではなく操作手段だけを表すなら、同じく後段へ置く。

境界は単語の見た目だけでは決まらない。「ステータス」は通常は曖昧な技術語だが、業務の人が正式な状態区分として使い、各状態で可能な行為と責任を説明できるなら、題材固有の言葉になりうる。反対に「顧客」のように業務らしい語でも、契約者、利用者、支払者を曖昧にまとめて判断を狂わせるなら、そのままでは共有言語として役に立たない。

## 意味の境界を定める

ユビキタス言語は組織全体で一つに統一する辞書ではない。ある業務判断のまとまりでは同じ意味で使えても、別のまとまりでは必要な属性、状態、規則が変わることがある。その違いを消さず、どこまで同じ意味が通用するかを明らかにする。その境界が、境界づけられたコンテキストを見つける手掛かりになる。

たとえば販売では「商品」が価格を付けて提供する対象を指し、倉庫では保管位置と取扱条件を持つ在庫単位を指すかもしれない。どちらかを正しい唯一の定義にするのではなく、それぞれの仕事で何を判断するための言葉かを確かめ、境界を越えるときに何を対応づけるかを決める。

## 育てるための問い

候補語が出たら、その言葉を誰がどんな判断で使うかを聞く。典型例だけでなく、「似ているがその語では呼ばないもの」「ちょうど扱いが分かれるもの」「同じ語なのに結論が割れる場面」を出してもらう。語そのものだけでなく、他の概念との関係、成立前後の状態、起点となる業務イベントまでつなぐ。

さらに、業務の人と作り手が会話、発見資料、BDDの具体例、ドメインを表すコードで同じ意味を保てているかを見る。語がコードに現れれば自動的にユビキタス言語になるわけではない。コードには技術語も必要であり、業務判断を表す部分で意味が保たれていることが重要である。

## この実践の限界

言葉を統一しても、利害の衝突や未決の方針は解決しない。そこでは誰が判断するかを別に決める必要がある。また、言葉は完成しない。新しい事例でこれまでの名前が判断を説明できなくなったら、過去の用語集を守るのではなく、会話、仕様、コードを一緒に直す。変化を避けることではなく、ずれを見つけて意味を合わせ続けることがユビキタス言語の実践である。
