# 業務イベントとEvent Sourcingの境界を判断する

**この資料の目的は、具体的な業務シナリオから「何が起きた事実か」「その事実を保存するか」「イベント列を正本にするか」を別々に判断することである。** Event Sourcingを採用することや、イベントらしい名前を増やすこと自体を目的にしない。

判断は次の一文を説明できたときに完了する。

> 誰が何をできなくなるため、どの成立済み事実を残し、その列を正本にする／しない。

答えられない場合は、イベントストアやテーブルの設計へ進まず、具体例へ戻る。

## まず一つの具体例を最後まで通す

8月24日10時に予約が成立し、10時20分に利用日時が変更され、11時に顧客都合で取り消されたとする。担当者は後日、「予約は一度成立したのか」「どの条件がいつ変わったのか」「取消時に返金義務があったか」を説明する。

この仕事で扱う事実は「予約確定ボタンが押された」ではなく、「予約が成立した」「利用日時が変更された」「予約が取り消された」である。ボタン押下やAPI受信は技術上の動作であり、別の画面や手作業でも同じ業務結果になるなら、業務イベントの名前にはしない。

成立、変更、取消を保存する理由は、現在値だけでは返金判断や顧客への説明を再現できないからである。一方、予約フォームへ入力中の未確定文字を直しただけなら、まだ約束や判断に使われていない。成立前の下書き修正まで永久保存する必要はない。

この一例から、次の三つを混同しない。

- **業務イベント**は、業務の側で一度起きた事実である。
- **event record**は、その事実を後で読めるように保存した表現である。
- **Event Sourcing**は、event recordの順序列を状態の正本にする選択である。

業務イベントを洗い出しても、すべてを保存するとは限らない。保存しても、現在状態を正本にして監査記録を添えるだけならEvent Sourcingではない。

## 事実を見つける5つの動き

### 1. 「同じもの」と「別のもの」を具体例で揃える

最初に、何を1件と数え、どこまでを同じものとして追うかを、識別子ではなく実際の扱いで確かめる。予約日時が変わっても同じ予約として問い合わせるなら、予約は同じ対象であり、日時変更はその対象について起きた別の事実である。

境界で結論が割れる例も置く。変更後を別予約として扱い、元予約の取消と新予約の成立が必要なら、単なる日時変更ではない。名前だけで分類せず、料金、権利、義務、後続作業がどちらの扱いを要求するかを見る。

### 2. 追跡する現在と、一度起きた事実を分ける

「予約はいま取消済みである」は変わり続ける現在状態である。「予約が取り消された」は一度起きた事実である。現在状態は成立、変更、取消を受けて変えられるが、成立済みの事実を後から別の内容へ上書きしない。

見た目が似ていても、予定日時や有効期間は、それだけでイベントではない。日時を持つ「モノ」と、業務上の行為が成立した時点を持つ「コト」を、データ型ではなく使われ方で分ける。

### 3. 一つの事実へ一つの業務上の成立時点を置く

予約の成立時刻と取消時刻が違うなら、一つの記録へ両方を詰めて後から列を埋めない。異なる時点で成立した二つの事実として扱う。

業務上起きた時刻と、仕組みが記録した時刻も分ける。外部から遅れて届いた取消は、受信時刻が遅くても取消自体の成立時刻を失わせない。前者は当時の判断、後者は配送や障害の追跡に使う。

### 4. 更新の背後にある出来事を言葉にする

「予約日時を更新する」だけでは、誰の依頼で、何を根拠に、どんな約束が変わったか分からない。業務の人が過去形で言える「顧客の依頼により利用日時が変更された」へ言い換え、残すべき固有情報を確かめる。

ただし、すべての更新をイベント化しない。成立前の入力誤りを直す場合と、成立後に顧客へ約束した日時を変える場合では扱いが変わる。境界は、変更前の値が誰かの判断、約束、権利、義務に使われたかで決める。

`updated_at`、`updated_by`、削除フラグ、種別コードは設計完了の印ではない。それらだけでは失われる変更理由、責任主体、異なる成立時点がないかを問い直す手がかりである。

### 5. 後から生じた関係を、過去への書き戻しで表さない

予約成立後に返金が決まったとき、予約成立記録へ返金IDを書き戻すと、後発の事実が先行する事実の形を変える。返金決定が予約成立や取消を参照するか、両者の対応自体を新しい事実として残す。

反対に、同じ時点で一体として成立し、片方だけでは業務上意味を持たない情報を、更新を避けるためだけに細切れにしない。分ける基準は記録時刻ではなく、独立した成立時点と業務上の意味である。

## 保存するevent recordを選ぶ

業務イベントを見つけたら、「記録がなければ、後で誰が何をできなくなるか」を問う。予約取消を残さなければ返金判断を説明できないなら保存する。画面を再表示したという技術動作を残さなくても業務判断が変わらないなら、業務上のevent recordにはしない。

保存するevent recordには、後から事実の意味と順序を復元できる情報が要る。予約取消なら、取消という過去形の種類、対象予約、対象内の順序、業務上の成立時刻、記録時刻、依頼者または判断者、理由、取消固有の条件を持たせる。再送があるなら同じ取消を二件にしない同一性も決める。

「種類」と自由なJSONだけへ押し込むと、取消には必須だが成立には不要な情報を検査できない。種類ごとの違いが業務判断を変えるなら、違いを読める形にする。

## 何を正本にするかを境界例で選ぶ

### 現在状態で足りる場合

表示名や作業中の並び順のように、過去値が後の判断、説明、権利、義務に影響せず、現在値だけ正確なら仕事が完了する場合は、現在状態を正本にする。更新があるという理由だけでEvent Sourcingを採用しない。

### 有効期間を持つ世代で足りる場合

料金表のように「いつからいつまでどの値が有効だったか」を引ければよく、変更を起こした出来事の順序から新しい状態を導出する必要がない場合は、有効期間を持つ世代データを正本にする。

境界は、過去時点の値が欲しいのか、当時までに起きた事実から判断過程を再現したいのかである。前者だけなら世代データで足りる。

### 現在状態と監査記録で足りる場合

現在値を正本とし、誰がいつどの値を変えたかを調査できれば十分なら、変更履歴や監査ログを添える。監査ログがあることと、ログから現在状態を再構成できることは別である。

新しい集計や状態を過去の事実から作り直す必要がなく、監査ログが欠けても現在状態の正しさが失われないなら、Event Sourcingの便益は小さい。

### イベント列を正本にする場合

予約の成立、変更、取消の順序から、当時の状態、返金判断、新しい読み取り方を再構成する必要があるなら、イベント列を正本にする。現在状態、一覧、検索、集計はその列から作り直せる派生物にする。

「履歴が欲しい」だけでは足りない。過去の事実列が失われると正しい状態を復元できず、逆に現在状態を捨てても事実列から作り直せる、という関係が必要である。

## 採用判断を反例で壊す

次の形は、名前にeventがあってもEvent Sourcingとは限らない。

- 現在状態を正本にし、変更後の値だけを監査ログへ書く。
- すべての技術メッセージを汎用JSONとして永久保存する。
- イベント表の行を訂正のたびにUPDATEする。
- 再生できない古いスキーマを「履歴」として保管する。
- 現在状態を作る規則がコードの外にあり、同じ列から再実行しても結果が変わる。

一方、Event Sourcingでも、読み取りのたびに全イベントを再生する必要はない。現在状態や検索用の投影、スナップショットを使える。境界は性能手段ではなく、それらを捨てたときに事実列から再構築できるかである。

取消と訂正も境界を露わにする。成立済みの予約を訂正で消すなら、事実列は正本になっていない。元の事実を参照する訂正や取消を新しく追記し、その主体と理由を説明できるなら、過去を保ったまま現在を変えられる。

## 採用前に再構築を実演する

Event Sourcingを選ぶなら、設計書の項目が揃っただけで完成にしない。予約の例を使って、少なくとも次を実行する。

1. 成立、日時変更、取消のevent recordだけを入力にし、現在状態と返金判断を再構築する。
2. 投影を削除して作り直し、反映済みの順序と業務上の集計が元と一致することを確かめる。
3. 同じ直前versionから二つの変更を追記し、後勝ちで消さず一方を競合として再判断させる。
4. 同じ取消要求を再送し、二つの取消事実にならないことを確かめる。
5. 古いevent recordを現在のコードで読み、読めなければ互換変換または再生停止を明示する。

一つでも実演できない場合は、「あとで再生できる」という便益をまだ証明していない。イベント列を正本にせず、現在状態、世代データ、監査記録のいずれかへ戻す判断も残す。

## 別の例で判断を見直す

料金表の改定へ同じ規律を当てる。4月から100円、10月から120円という値を過去時点で引くだけなら、適用期間を持つ世代で足りる。誰がどの審査を経て改定を承認し、その事実列から請求判断を再構成する必要があるなら、承認や改定のevent recordとEvent Sourcingを検討する。

最初の予約例ではEvent Sourcingが必要でも、料金表まで同じ方式にするとは限らない。新しい例で結論が変わらない設計は、一貫しているのではなく、技術選択を先に固定している可能性がある。

## 判断結果として残すもの

判断結果には、少なくとも次を書く。

- 判断に使った具体的な正常例と、取消・訂正・遅延・再送・競合の例
- 業務イベントの名前、成立時点、担い手、業務上の結果
- 保存するevent recordと、残さなければ誰が何をできなくなるか
- 正本に選んだものと、現在状態・世代・監査記録・イベント列からそれを選んだ理由
- 採らなかった選択肢が不十分になる境界例
- 再構築を実演した結果と、確認できなかった条件

未確認の条件が採否を変えるなら、推測でEvent Sourcingを選ばず、誰に何を確かめるかを残して止まる。
