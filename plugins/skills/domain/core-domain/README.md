# core-domain

**業務の話に線を引く。** どこまでが業務で、そのうちどこがコアかを決める。業務の決まりそのものは書かない。

## 何を返すか

`<scope_dir>/<題材>.md` に次の4節を持つ線引きを保存する。

| 節 | 何を書くか |
|---|---|
| `## コア` | そこが優れているから選ばれている領域と、そう判定した理由 |
| `## 支援` | 自社の事情に合わせて要るが、優位にはならない領域 |
| `## 汎用` | どこの組織でも同じ形で要る領域 |
| `## スコープ外` | 業務の話ではないとして落としたものと、その理由 |

**4節すべてが要る。** 該当が無ければ「なし」と書く。落ちていると、考えなかったのか無かったのかが読めない。

業務の線引きか実装の関心かは入力根拠と文脈から評価し、実装の関心は理由付きで`## スコープ外`へ置く。scriptは4節の存在・非空と保存操作を検査し、語の存在で意味を判定しない。

## 設定

`<repo>/.harness-plugins/core-domain.config.yml`（無ければ `${XDG_CONFIG_HOME:-~/.config}/harness-plugins/core-domain.config.yml`、それも無ければ同梱既定）。**1ファイルだけが選ばれ、層は混ざらない。** 選んだファイルが下のキーを全部持たなければ止まる。

```yaml
version: 1
scope_dir: domain/scope           # 線引きの置き場（repo root からの相対、または絶対）
instructions:
  marking:
    directive: 題材をコア・支援・汎用へ分け、実装の関心はスコープ外として理由つきで落とす
```

**コア・支援・汎用の分類結果はYAMLへ書きません。** 分類はプロダクトの戦略に依存する業務判断であり、設定層を切り替えたことで変わるものではないためです。YAMLが決めるのは保存先と作業方針だけです。

実際の分類は `<scope_dir>/<題材>.md` に、対象、区分、理由、判定日を含むリポジトリの成果物として残します。プロダクトの選ばれる理由が変わったら、設定を切り替えず、その理由と分類を見直します。

## 使うもの

| コマンド | 必要な場面 |
|---|---|
| `bash` | 設定の解決 |
| `jq` / `yq` v4系 | 設定の検証と読み取り |
| `python3` | 実装語の検査と保存（標準ライブラリのみ） |
| `git` | repository root の判定（無ければカレントを root として扱う） |

## 中身

| 場所 | 役割 |
|---|---|
| `scripts/prepare.sh` | plugin root を検証し、解決済みYAMLの一時パスを返す |
| `scripts/resolve.sh` | 設定を1件選び、完全性を検証して解決済みYAMLを返す |
| `scripts/check.py` | 必須節、保存先、上書き防止の検査と保存 |
| `references/boundary.md` | どこまでが業務の話か（3つの問いと、よく混ざるもの） |
| `references/domain.md` | 組織が価値を届けるために向き合う問題領域と、その理解の問い |
| `references/subdomains.md` | 問題空間の分割と、コア・支援・汎用という投資仮説 |
| `references/bounded-contexts.md` | 言葉とモデルの意味境界、翻訳と所有を確かめる問い |
| `references/concept-map.md` | 問題空間・モデル境界などの軸と、概念を混同しないための関係図 |
| `skills/mark-core-domain/` | 線引きの入口 |
