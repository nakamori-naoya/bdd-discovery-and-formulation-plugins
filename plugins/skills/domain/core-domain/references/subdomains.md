# 業務領域を分け、投資仮説を置く

**業務領域（サブドメイン）の分類は問題空間を分け、どこへ固有の投資をするかという仮説を明示するために使う。** 難しさ、規模、障害時の重大さに等級を付けるものではない。

## 実際の仕事で何を分けるか

業務領域は、まとまりのある業務目的、知識、判断を持つ問題領域である。処理、画面、部署、データベースを先に区切るのではなく、何を達成し、どの知識で判断するかを見て問題空間を分ける。

中核、補完、一般は、現時点の事業戦略に対する投資仮説である。外部設定との対応が必要な場合だけ、それぞれ識別子 `core`、`supporting`、`generic` を使う。

- 中核の業務領域: 選ばれる理由を直接支え、独自の学習と改善へ重点投資する領域
- 補完的な業務領域: 自組織の仕事には必要で固有対応も要るが、それ自体は選ばれる理由ではない領域
- 一般的な業務領域: 広く共通する解決で目的を満たしやすく、調達や標準化を検討する領域

分類は利用側が作る成果物であり、ツールのYAML設定ではない。対象、理由、判定日、保留事項を残し、戦略や市場が変われば見直す。

## 分割と分類の境界を探る

業務領域は、リポジトリや部署を分けるための箱ではない。達成する業務目的が独立し、判断に必要な専門知識と変化の理由がまとまる場所を、業務シナリオの違いから見つける。同じ役割が関わっていても、守る目的と判断基準が違えば分割候補になる。反対に、用語が違って見えても一つの判断を共同で成立させるなら、早く分けすぎない。

中核の業務領域は難しい領域ではなく、そこを他社と同じにすると選ばれる理由が失われる領域である。固有対応は必要だが優位に直結しないなら補完的な業務領域になる。既製の解決を使っても目的を損なわないなら一般的な業務領域になる。三つは概念の性質ではなく、現在の戦略と代替可能性に対する投資判断である。

分類するときは、対象範囲、区分、選ばれる理由との関係、判定時点を文章で残す。情報が足りなければ、無理に色を付けず、何が分かれば判断できるかを保留として残す。戦略が変われば分類も見直す。

## 例・反例・境界から確かめる

即日配送を強みにする小売事業で、問題空間を「配送枠の最適化」「請求」「従業員アカウント管理」に分けたとする。配送枠の提示速度と精度が選ばれる理由なら、そこを中核の業務領域とする。地域固有の締め処理が必要な請求は補完的な業務領域、標準サービスで満たせるアカウント管理は一般的な業務領域と仮置きする。

請求が難しく重大でも、それだけで中核の業務領域にはしない。反対に、配送枠の実装規模が小さくても、差別化に直結するなら重点投資の対象になり得る。成果物にはこの理由と判定日を残す。

競合も同じ配送枠の精度で選ばれ、標準サービスへ置き換えると約束できる時間帯が劣るなら中核という仮説が強まる。制度変更によって請求方法そのものが選ばれる理由になったなら、以前の分類を固定せず補完から中核へ見直す。分類は領域の永久的な属性ではない。

## この概念の限界

- 最初から完全で安定した分割を期待しない。学習に伴って境界は変わる。
- すべてを中核にしない。それでは投資先を選ぶ仮説として働かない。
- 一般を軽視の印にしない。法令、可用性、安全性の要求は別途満たす。
- 分類から実装境界や担当組織を自動決定しない。

別の商品、地域、事業戦略へ同じ分類を当てたときに理由を説明できないなら、色を維持するのではなく問題空間の分け方と投資仮説を見直す。
