# 業務知識の資料に共通する条件

この条件は、実行の担当が write-business-knowledge で作った業務知識の資料（以下、資料）と grill の記録（以下、記録）を判定するためのもので、どのお題のどの業務にも当てる。お題に固有の条件は、この後ろに続く。条件は判断の型だけを書き、正しい資料の中身は書かない。どの条件も、ほかの条件の出来、文体、見出しの形、表と文章の使い分けでは判定しない。各条件の「重み」は、判定を点数にまとめるときに使う値で、判定の厳しさは変えない。重み3は利用者の原則の芯（推測で埋めない、業務と仕組みの線引き、業務の言葉、拒む理由の結び）、重み2は行いごとの決まりの骨組み、重み1は細部である。資料や記録が存在しない、または空のときは、それを読む条件はすべて FAIL とする。

実行の担当は、要件と業務の分け方（split.md）だけを渡され、担当する業務を一つ指定されていた。grill の問いには、要件にある事実で答え、要件に無ければ問いに添えた推奨を仮置きして資料に未決として書き、推奨も無ければ未決に残すよう指示されていた。推奨を仮置きした答えは、要件から決まったことではない。ほかの業務の資料は、書いた時点では一つも存在しなかった。

## 業務と仕組みの境界

### boundary-no-mechanism

重み: 3

PASS：資料の業務の決まり、BDD の Given と Then、拒む理由のどこにも、仕組みを変えれば消える事柄（キャッシュ、反映の遅れや非同期、キュー、再試行、トランザクション、認証や認可の仕組み、画面の制御、製品名）が、成り立つ条件や結果として入っていない。仕組みに触れる文は、業務の外へ置いたことと送り先を述べる文に限られる。

FAIL：仕組みの事柄が、業務の決まりの条件、BDD の前提や結果、拒む理由として書かれている。

### boundary-value-placement

重み: 3

PASS：資料で業務の決まりとして書かれた値（人数、件数、回数、時間）は、何が成り立つか、何が表示対象か、どの順に並ぶかを変えるものだけである。一回に返す件数のように応答の大きさだけを変える値や、仕組みを守るための値は、業務の決まりに入らず、どこへ置いたかが一行で残っている。要件にある値のうち、担当の業務に関わるものが、業務の決まりにも置き場の一行にも無いまま消えていない。

FAIL：応答の大きさや仕組みを守るための値が業務の決まりとして書かれている。または、業務の外へ置いた値の行き場が書かれていない。または、担当の業務に関わる要件の値が行き場なく消えている。

## 行いごとの決まり

### rules-who-can

重み: 2

PASS：資料の業務を変える行い（コマンド）と、業務を変えずに知る行い（クエリ）の一つひとつに、誰が行えるかが、その行いの節に書かれている。

FAIL：誰が行えるかが書かれていない行いが一つでもある。

### rules-command-and-query

重み: 2

PASS：コマンドの一つひとつに、成り立つ条件（境界の値を含む）、起こす業務イベント、拒む理由が書かれている。クエリの一つひとつに、何を表示するか（表示対象の条件）と、どの順に並べるかが書かれている。業務の判断を変えないので業務知識に置かないもの（拒む場面の無い行いの拒む理由、表示対象を変えない並び）は、無いことか置き場が読み取れれば足りる。

FAIL：コマンドに成り立つ条件、業務イベント、拒む理由のどれかが、無いことも置き場も読み取れないまま欠けている。または、クエリに表示対象か並び順が、同じく欠けている。

### rules-rejection-linked

重み: 3

PASS：拒否の BDD（業務の決まりによって行いが通らないもの。同時に起きた場面で通らなかった側や、理由の持ち主が隣の業務のものも含む）はすべて、その BDD の中の NOTE で、どの拒む理由によるかが結ばれている。skill は拒否の Then を NOTE で拒む理由に結ぶよう定めているので、BDD の外の文章で結んだものは結ばれていないものとして扱う。根拠となる拒む理由が無い拒否を、確定した BDD にしていない。

FAIL：拒否の結果を持つのに、NOTE で拒む理由に結ばれていない BDD が一つでもある。

### rules-bdd-shape

重み: 1

PASS：BDD の Given は判断に要る前提を事実ごとに書き、「その他は正常」のような包括表現で前提を隠していない。When には業務の行いか業務イベントが一つだけある。ただし、同時に起きたときの決まりを示す BDD は、同時に起きる行いを When に並べてよい。Then には業務上の結果が書かれている。

FAIL：Given に包括表現がある、同時に起きたときの BDD でないのに When に二つ以上の行いがある、または Then に業務上の結果が無い BDD が一つでもある。

### rules-concurrency

重み: 2

要件と資料を読み、二つの要求が同時に来ると破れうる決まり（上限、重複の禁止、一度きりの登録など）が担当の業務にあるかを確かめる。

PASS：そうした決まりがあるなら、同時に起きたときの決まりが文章だけでなく BDD にも置かれ、通った側の結果と、通らなかった側に何が起きないかが書かれている。そうした決まりが担当の業務に無いなら、どちらかを拒む制約を作っていない。

FAIL：そうした決まりがあるのに、同時に起きたときの BDD が無い。または、通らなかった側に何が起きないかが書かれていない。または、要件に無い、どちらかを拒む制約を作っている。

### rules-explanation

重み: 2

要件が、担当の業務で成立した事実を後から説明できることを求めているかを、要件を読んで確かめる。誰に何のために説明するかが要件に書かれているかも確かめる。

PASS：求めていないなら、資料もその要求を作っていない。求めているなら、その要求が、誰に何のために説明するかと一緒に、常に守られることとして資料に書かれている。誰に何のためにかを要件から決められず、記録で推奨を採って決めたなら、資料の該当箇所か「まだ決まっていないこと」に、仮説であることが示されている。

FAIL：要件が求めているのに、説明の要求が書かれていない、または誰に何のためにかが書かれていない。または、記録で推奨を採って決めた相手や目的を、資料が仮説の印なしに断定している。

### rules-crud-coverage

重み: 1

PASS：担当の業務が持ち主になる対象について、作ること、変えること、なくすことのそれぞれに、BDD を置いたか、対象外としたかが資料から読み取れる。持ち主になる対象が無い業務なら、そのことが資料から読み取れる。

FAIL：作る、変える、なくすのどれかについて、BDD も対象外の記述も無く、扱ったかどうかが読み取れない。

## 業務の言葉と持ち主

### language-naming

重み: 3

PASS：ユビキタス言語の表のすべての語と、本文と BDD で決まりを述べるのに使う語の一つひとつが、業務の人が仕事の会話と判断で使う言葉である。業務イベントは行った人が言う過去の形（「〜した」）で、状態はその状態にある人が自分の状況を言う言葉で名付けられている。業務の人が使わない、説明のために作った語（「成立中」「有効フラグ」の類）や、テーブル名、列名、クラス名のような実装の名前が、表にも本文にも業務の語として置かれていない。

業務の人の言葉の出どころは、業務の人が書いた要件と業務の分け方である。そこにある語は業務の人の言葉として扱い、問うのは資料が持ち込んだ語だけである。判定の前に、表の語と、本文や BDD で決まりを述べるのに使っている語のうち、資料が持ち込んだものの一つひとつについて（問うのは語であり、拒む理由や BDD の見出しのような文ではない）、その業務の利用者や担当者が仕事の会話でその語をそのまま口にするかを判定し、根拠に一覧として書く。一覧の一行は「- <語>: 使う」か「- <語>: 使わない（業務の人なら何と言うか）」とする。ほかの業務の資料が持ち主の語も、この資料で使っている限り一覧に入れる。

FAIL：一覧に「使わない」が一つでもある。

### language-ownership

重み: 2

担当の業務が持ち主になる語は、split.md に書かれている。

PASS：ユビキタス言語の表で、担当の業務が持ち主の語は、この資料を持ち主にして英名を決めている。別の業務が持ち主の語は、持ち主をこの資料にせず、持ち主の資料へのリンクか範囲の外の印で示している。持ち主の資料がまだ無い語の英名を推測で書かず、`未定` として空けている。

FAIL：別の業務の語をこの資料が持ち主として定義している。または、持ち主の資料がまだ無い語に英名を推測で書いている。または、担当の業務が持ち主の語の英名を空けている。

### language-consistency

重み: 3

PASS：同じものを指す語が資料の中で揺れていない。一つのものを二つの語で呼んでいない。本文と BDD で使う語が、ユビキタス言語の表の語と一致している。

FAIL：同じものが二つ以上の語で呼ばれている。または、表に無い語で業務の決まりや BDD を書いている。

## 推測で埋めていないか

### guess-marked

重み: 3

PASS：資料に、仮説として置いたことと未決が、それと分かる形で書かれている。仮説の一つひとつに、仮説であること、根拠、採らなかった案が添えられている。未決の一つひとつに、何が決まれば決まるか、または誰に聞けば決まるかが添えられている。記録で推奨を採った答えは、どれも資料の仮説か未決に現れている。

FAIL：仮説や未決の印が無い。または、採らなかった案の無い仮説、誰に聞けば決まるかの無い未決が一つでもある。または、記録で推奨を採った答えが、資料で仮説とも未決とも示されずに断定されている。

### guess-foreign-owner

重み: 3

split.md は、業務の範囲と語の持ち主を決めていた。書かれていない持ち主の問いがあるかは、split.md を読んで確かめる。

PASS：別の業務が持ち主の事柄を、資料が自分の決まりとして決めていない。split.md に無い持ち主の問いは、自分で決めずに未決か依頼元へ返す事柄として扱っている。

FAIL：別の業務が決めるべき事柄を、資料が自分の決まりとして断定している。

### guess-no-unmarked-specifics

重み: 3

PASS：資料で断定して書かれた業務の決まりに、要件から来ていない具体（数値、期限、役割、例外の経路、同時に来た要求のどちらを通すかの基準）が、仮説の印なしに混ざっていない。要件から来たかは、要件と記録を読んで確かめる。要件の文に無くても、要件と資料のほかの決まりから一つに導ける帰結は、要件から来たものとして扱う。

FAIL：要件から導けない具体が、仮説の印なしに業務の決まりとして断定されている。

## grill の記録

### grill-answers

重み: 1

PASS：記録の問いが1問以上6問以下で、それぞれに推奨と、答えと、その根拠（要件のどこか、推奨を採ったか）が書かれている。要件を根拠に挙げた答えは、要件のどのファイルのどの記述かが特定され、その記述が要件に実際にある。要件の文から答えが一つに決まることを、わざわざ問いにしていない。最後に、決定と未決の一覧への合意が書かれている。

FAIL：上のどれか一つでも破れている。
